## What step 8c found (inputs to Q14's verdict arm)

Some words first. A "prompt record" is the transcript's own entry for a prompt. An "attachment" is a side entry the transcript files inside a turn that is already running. "Keys" are a record's field names, and the words in code font are the transcript's own: field names, and after a colon, a field's value. Each of Briggsy's prompts below was sent the way he said he sent it, or was asked to send it (`live-groundtruth.txt` says which). Asked later, he put every laptop one on the laptop for certain but two: the one-word go-ahead that started a turn at 11:37:00 and the test message sent mid-turn at 11:37:13, which he is "very sure" came from the laptop, though not certain. A re-run at 17:20 the same day, with his word at the time, read the same as the 11:37:13 one (logged in `live-groundtruth.txt`). On CLI 2.1.309:

| | Starts a turn (session idle) | Arrives while a turn is running |
|---|---|---|
| **Laptop keyboard** | its own prompt record, `promptSource: typed`, and no queue entries (9 of 9: 8 laptop by his own account, 1 he is "very sure" of) | no prompt record of its own: an attachment of type `queued_command` with `origin.kind: human`, `humanTurn: true` and no `promptSource`, plus two queue entries (in, then out as absorbed into the running turn) (2 of 2: 1 by his word at the time, 1 he is "very sure" of) |
| **Phone (Remote Control)** | its own prompt record, `promptSource: queued`, plus two queue entries (in, then out) and one extra field, `queueSkipSlashCommands` (3 of 3) | the same as the laptop's: an attachment with the same keys and the same values for `commandMode`, `origin` and `humanTurn`, and the same two queue entries (1 of 1) |

**What the verdict arm can actually read:** from the transcript, the recorder's captures hold only a turn-starting prompt's own record (`promptSource`, `origin.kind`, `turnOrigin`, `entrypoint`, and its keys, `queueSkipSlashCommands` among them). The mid-turn column and the queue entries came from Claude reading the transcript by hand; the recorder never reads an attachment or a queue entry. In the captures, a prompt that arrives mid-turn shows only as a hook line with its own opening (how its text starts, and its length) but the turn opener's record. A verdict that needs those fields needs a recorder change and a new measurement.

- **Phone and laptop can be told apart only for a prompt that starts a turn, and only after the hook has finished.** When the hook looked (19 to 38 ms after it started), none of the 16 prompts that started a turn had a record yet: the table's 11, plus a task notification, an agent's message back, two /loop ticks and a message from another session. ## Landmines

- **Writes to Claude Code's own config get blocked.** Auto mode's safety check stops any write to `~/.claude.json` or `~/.claude/settings.json` as self-modification unless a standing rule names it. Ask Briggsy for the exact write in his own words, then run the same write again.
- **The leak gate now refuses a push that puts these in `playbook/`:** any uuid (even a made-up one, or the one in a `claude.ai/code/artifact/` link), a user-folder path even with a placeholder name (the dashed form Claude Code names a project's folder by included), and any binary file, a screenshot for one. Write paths as `~/...`, a project folder as `<slug>` and ids as `<id>`; screenshots go in the ignored `playbook/temp/`.
- **Every CLI version starts with no passed probes.** Briggsy updates the CLI before each session, so rerun the full probe suite on each new version, from a Bash tool in this session: `cd "$TEMP" && node <repo>/projects/hooks/probes/run.mjs`, then `report.mjs`, then `--cleanup <run dir>`.
- **Read a surprising probe run's own record before blaming the CLI** (`modelUsage`, `permission_denials`). Probe sessions can switch models mid-run (insight 003).
- **Tracked settings files outside the leak gate hold user-folder paths.** `projects/burned/.claude/settings.local.json` is public with four of them in its allow list; the gate scans only `playbook/` and `projects/hooks`. Found during U4, not U4's to fix; scrubbing it and widening the gate is its own item.
- **Build lanes share one scratchpad.** Give each lane's scratch files a prefix of its own: two lanes overwrote each other's scripts on 2026-10-23 (harmless that time).
- **Tests that make git repos can't run from a session scratchpad folder.** Its path is long enough that git's object files pass Windows' 260-character limit ("Filename too long"; it showed as 4 failing tests, measured 2026-10-24). A mutation run's copy can sit in the scratchpad, but leave the tests' own temp folder as the system one.
- **Tests never build fixture paths with the code under test.** Mutation runs go on a copy and compare the real temp folder before and after (insight 006).
- **A new laptop needs per-machine setup again,** including the probes' one-time trusted-folder approval (the steps are in the private backup folder for step 8b).
- **The live hook runs the recorder straight from the repo.** Every line carries `recorder`, a fingerprint of the file's bytes on disk when the process that wrote the line started (the hook, or the helper it left behind, which reads the file again), committed or not. So any saved edit to `projects/hooks/probes/live/q14-recorder.mjs`, even a comment, changes the fingerprint on every line written after it. Step 8c's lines are the first 35 in the captures file, all `5ed869b0dee2` (two later lines carry it too), and its docs edits brought new fingerprints. The verdict arm counts each fingerprint separately and reads only fingerprints of committed recorder code; which of those it reads is its plan's call (Next #2).
- **`run.mjs --cleanup` reads `made.json` one folder down.** It takes a run folder and looks for `<run folder>/<sub>/made.json`, so an ad-hoc script that writes `made.json` straight into its output folder is cleaned with `--cleanup <that folder's parent>`. Pointing it at the output folder itself deletes nothing and says nothing.
- **Every capture line carries its CLI version (`cli`).** The verdict arm counts each version separately, and each new version needs the full probe rerun first (see "Every CLI version starts with no passed probes", above).
