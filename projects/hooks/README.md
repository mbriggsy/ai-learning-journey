## Platform Findings

Discovered through empirical testing. Filed as [anthropics/claude-code#42250](https://github.com/anthropics/claude-code/issues/42250).

1. **`additionalContext` reaches the model on PostToolUse and Stop, and a Stop context extends the turn** (probe Q1, CLI 2.1.306 and 2.1.307): both words a probe's hooks handed over were in a request sent to the model (a transcript's `api-request-blob` or `api-request-shape` record), and the model repeated them. The Stop hook then fired again on turn 1's `prompt_id` with `stop_hook_active` true, so its context kept the turn going, like a block does. Q1 measures that firing itself and ties it to the turn by `prompt_id`, because an async Stop hook can set the flag for the whole session: a context delivered without it reads PARTIAL, a measured deviation. VERIFIED also needs the Stop word's first request record to come before turn 2's prompt record, a check the last 2.1.306 run and every 2.1.307 run made and passed: one after it is a measured PARTIAL (the turn extended, but the context reached the model only on turn 2), and one that no turn-2 prompt record places reads INCONCLUSIVE. Every no is guarded. A word the model repeated that no request record holds reads INCONCLUSIVE (the records missed a delivery). An API error ends a turn in StopFailure, not Stop, and leaves no re-firing to see, so a StopFailure, an `is_error` result or a stream that didn't end `done` turns every reading short of VERIFIED into INCONCLUSIVE (a re-firing on turn 1's prompt still VERIFIES). And a CONTRADICTED needs the model to have repeated the session-start word, so a model that repeats nothing never reads as one that got nothing. This retires the 2026-04 finding filed as #42250, that only error-path output (`{"decision":"block"}`, exit 2's stderr) reached the model.
2. **PostToolUse block delivers without undoing the tool result** — useful for reminders after skill completion.
3. **PreToolUse hooks don't fire on user slash commands** — only on Claude's programmatic Skill invocations. PostToolUse and Stop hooks fire in both cases.
4. **A `Skill` hook sees the skill name in `.tool_input.skill`** — exactly the string passed to the Skill tool: a plugin skill as `<plugin>:<skill>` (e.g. `compound-engineering:ce-code-review`), a `~/.claude/skills` or project skill bare (e.g. `ultramode-code-review`). A case-arm name that is not in the installed roster never matches and never says so — `check-config-liveness.mjs` exists to say so.
5. **`onFailure: "block"` makes a guard fail CLOSED** (Claude Code ≥ 2.1.295, set per hook in `settings.json`). Without it, a hook that can't start, times out, or exits with an unexpected code is a non-blocking error and the tool runs anyway. The two PreToolUse guards (`block-webfetch.sh`, `enforce-brief-before-work.sh`) carry it since 2026-10-08 — proven with a missing-script hook in a headless run: with the flag the call was refused (`failed; blocking because onFailure is "block"`), without it the same call ran. It is **ignored on Stop / SubagentStop / TaskCompleted / TeammateIdle** (the binary logs `onFailure: "block" is ignored on Stop`), so `stop-distill-gate.sh` does not carry it; the advisory SessionStart / PostToolUse / Notification hooks don't either — a broken reminder must not block work.
6. **PreToolUse still honors the deprecated top-level `{"decision":"block"}`** (probe Q2, 2.1.306 and 2.1.307), which `block-webfetch.sh` and `enforce-brief-before-work.sh` use; it maps to a deny, and the model reads the reason. When one output carries both forms and they disagree, the deny won both ways on 2.1.306 and 2.1.307. Those mixed arms don't make Q2 VERIFIED, but one whose read ran (the allow won) lowers it to PARTIAL, so a later version's pass rules out an observed flip without proving deny-wins: a mixed arm the model skipped, or whose run failed, leaves VERIFIED standing.

## Tests

```bash
cd projects/hooks && node --test "tests/*.test.mjs"
```

Quote the glob: on Node 24, `node --test tests/` fails with MODULE_NOT_FOUND. CI runs this suite and the squeaky-clean one (`.github/workflows/hooks-tests.yml`) on every change to this folder or to the four skill folders the leak test covers. Each step lists its suite's `tests/*.test.mjs` with bash and fails when none match, because `node --test` reads a glob that matches nothing as 0 tests and exits 0 (a file with no tests still counts as one, so the file count is the guard). The job times out at 15 minutes. Its version step runs `node`, `jq`, `bash` and `python3` with `--version`, so a missing one fails there by name: without it, a missing Python would only make `statusline.test.mjs` and `session-start.test.mjs` skip. The paths filter stays: GitHub skips a filtered run only when a push's diff tops 3,000 files with no match in the first 3,000, CI runs after the push anyway, and the leak stop before a push is the pre-push gate (see The Pre-push Leak Gate). U3 built it; it runs only once `install-git-hooks.mjs --go` installs it in the monorepo (U3's live step 8).

- **`tests/harness.mjs`** runs a hook from an argv array (no shell) with a fixture on stdin, under `tests/hook-runner.mjs` (see Background processes), then reads the result the way Claude Code does: `outcome(event, run)` follows the hooks reference's exit-code, JSON-output and per-event decision rules, and `assertBlocks` / `assertPasses` assert on it. A run whose decision nobody knows is undecided: the harness killed the hook before the CLI's limit (see Timeouts), a background process held its stdout or stderr open (see Background processes), the runner's 1 MB buffer cut it short (see Output past 1 MB), or its JSON breaks a rule no probe has measured (below). Both asserts refuse such a run, even under `onFailure: "block"`, each naming the way out, and its `blocks`, `continues`, `stops` and `failure` throw when read: they are non-enumerable, so JSON, a spread and `deepEqual` leave them out, and a gate test's raw `assert.ok(!o.blocks)` can't pass the run. `assertPasses` also refuses a PreToolUse `ask` or `defer`, since the session decides whether that call goes ahead, not the hook: a `-p` run, where nobody can answer, denies an ask, and a defer ends a `-p` turn with the call unrun, while an interactive session prompts for an ask and ignores a defer with a warning. `assertBlocks` fails both and says why. `decision` is never a pass signal: exit 2, a failure `onFailure: "block"` blocks, and an undecided run all leave it null, so a gate test asserts with `assertPasses` or `assertBlocks`, never on `decision` alone. `harness.test.mjs` plants hooks a careless reading scores wrong (exit 1, JSON after a profile echo, exit 2 with an allow) and proves the assertions catch them. It also checks the output's shape (`validateOutput`: a `hookEventName` that isn't the event or a `permissionDecision` outside its values decides nothing; a PreToolUse `updatedInput` that isn't an object is undecided instead, through `unmeasuredProblems`: the reference gives it no type and no probe has measured what the CLI does with one, so both asserts refuse it, even under `onFailure: "block"`, while exit 2 over it still blocks), drops the fields an event ignores (all of them on StopFailure, SessionEnd, Setup and InstructionsLoaded; `continue` alone on CwdChanged, FileChanged and DirectoryAdded, whose `systemMessage` still counts), scores a Stop hook's context as keeping Claude going, requires a non-empty reason on a Stop or SubagentStop block by decision (the reference calls it required and what the CLI does without one is unmeasured, so `assertBlocks` fails closed), treats exit 2 from a script that doesn't exist as a failure where the reference says so, refuses the events it doesn't model (PermissionRequest, Elicitation and the like) instead of scoring them, and reads only a run shaped as `runHook` returns it. Where the reference and the CLI disagree, the CLI wins and the harness says which probe measured what: Q1 (a Stop context extends the turn), Q2 (a deny, the deprecated block and exit 2 each stop the call; the mixed arms, a deny in one form and an allow in the other, don't make Q2 VERIFIED, but one whose read ran lowers it to PARTIAL, so a later pass rules out an observed flip without proving deny-wins: a mixed arm the model skipped, or whose run failed, leaves VERIFIED standing) and Q11 (the hook env's session id). Every other rule rests on the reference alone.
- **The hook's environment** is this process's minus every `CLAUDE*` variable and the git location variables (lib's `GIT_LOCATION_VARS`: `GIT_DIR`, `GIT_INDEX_FILE` and the rest, matched case-blind), plus 4 of the 11 `CLAUDE*` variables probe Q8 measured on hook envs: `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID` (the input's `session_id`, as Q11 measured) and `CLAUDE_PROJECT_DIR`. The rest depend on how the session was launched, so a test of a hook that reads ENTRYPOINT, ATTENDED, PID, EFFORT or ENV_FILE passes them in `env`, which wins over everything. `CLAUDE_PROJECT_DIR` is the `cwd` option, else `input.cwd`: Claude Code keeps it at the launch root while `input.cwd` follows a cd or a worktree, so a test of that case passes the root as `cwd` (or `env.CLAUDE_PROJECT_DIR`) and the subfolder as `input.cwd`.
- **Timeouts.** `runHook`'s 15 s timeout is the harness's, not the CLI's. `outcome()` takes `hookTimeoutS`, the hook entry's own `timeout` in seconds as the entry sets it (fractions allowed), else the event's default: 600 s, or 30 s on UserPromptSubmit and PostModelSwitch; the outcome's `cliTimeoutMs` is that limit in ms. Any other option throws, so a misspelled or ms-sized one can't fall back to the default unseen, and a timeout-named one such as `cliTimeoutMs` gets an error naming `hookTimeoutS`. SessionEnd hooks share a 1.5 s budget that a hook's own timeout raises up to 60 s, and a plugin hook's does not. A run that reaches that limit is a CLI timeout: a failure whose output is dropped, which `onFailure: "block"` turns into a block on an event exit 2 blocks, less the four Finding 5 says ignore it. A hook the harness killed sooner is undecided, and both asserts refuse it. At the harness timeout the hook dies with everything it started (`taskkill /T` on Windows, its own process group on POSIX; a POSIX process that left the group by `setsid` escapes it, as does a Windows one whose parent already exited), and `harness.test.mjs` checks that a child it started is gone after the kill. `elapsedMs` is the hook's own run time, to its exit or to the harness's kill, never to the close of its pipes. The runner re-arms its deadline until the clock reaches it (one `setTimeout` can fire about 2 ms early), so a killed hook's `elapsedMs` is never under the harness timeout; a fake-clock test of `atOrAfter` holds that.
- **Background processes.** `runHook` runs the hook under `tests/hook-runner.mjs`, which times the hook's exit apart from the close of its stdout and stderr: `spawnSync` alone waits for the close, so a background process left on the hook's output would stretch the run and pass its late output off as the hook's. Claude Code finishes reading shortly after the hook's own process exits (hooks reference, "Hooks that start a background process"): a decision printed later is ignored, and an allow followed by an unredirected background process is blocked. So a run whose stdout or stderr stays open more than `PIPE_HELD_MS` (250 ms) past the exit is undecided (`heldOutput`; the run carries `heldMs`), and both asserts refuse it, naming the documented fix: print the decision first, then redirect the background process (`cmd >/dev/null 2>&1 &`). The runner reads on at least twice that margin past an exit that lands just before the harness timeout, so such a run reads held, never closed with its exit; a run built by hand with no `heldMs` reads as closed with its exit. When a run ends with a background job still holding the output, the job dies with the hook's process group on POSIX (a test Windows skips); on Windows it runs to its own end, since nothing built in reaches it once the hook has exited: `taskkill /T` starts from a live parent, and the dead hook's pid can name another process. A runner that gives no result makes `runHook` throw, never a hook that couldn't start, which `onFailure: "block"` would score as a block; `harness.test.mjs` shows it with stand-in runners, one that exits with no JSON and one that hangs past its slack, set through `setRunner` (a setter only that test calls, never the environment). `harness.test.mjs` plants a hook whose background process prints a deny after the hook exits and one that prints an allow and leaves an unredirected job running, each as a node and a bash hook (so the suite needs `bash`, as `block-webfetch.test.mjs` does): both read undecided. A job that holds only stderr open (a node one, and bash's `sleep 0.7 >/dev/null &`) reads held too. A hook that prints and exits, and the documented redirected pattern, read as usual.
- **Output past 1 MB.** The runner keeps at most 1 MB of each stream (spawnSync's `maxBuffer`, which `runHook` used before it). A hook that writes more is killed there, and the run names the stream in `overflowed`, never in `error` (unless the harness's deadline killed it first: bytes still in the pipe after that kill name no stream and kill nothing again, so the run stays a timeout; `bufferStep`): the reference gives the CLI no output size at which a hook fails, so the cut is the harness's, and the run is undecided, refused by both asserts even under `onFailure: "block"`, with the way out (send a `set -x` trace or other bulk output to a file). A buffer kill shortly before the harness timeout stays the buffer's: the deadline leaves that run to the kill already under way, so it is never relabeled a timeout, which at an entry's own limit would read as the CLI's. `harness.test.mjs` plants a flood before an allow, one after it, and one just before the deadline.

- **`tests/leak.test.mjs`** fails on a UUID, a Windows user-profile path, a transcript-only field written as a JSON key (parentUuid, isSidechain, requestId and the like), an API id (`msg_01…`, `req_01…`, `toolu_01…`, `session_01…`, matched with no left edge, so one the API glues a word to, as a server tool's `srvtoolu_01…`, still counts) or a binary, anywhere git would commit under `projects/hooks` and `projects/skills/{ultramode-code-review,deepen-verify,squeaky-clean,distill-and-brief}`, and in what is staged there (below). The user-profile rules also catch the folder-name form the CLI names project folders by (the profile path with its drive colon and each slash turned into a dash), and a drive colon or separator written percent-encoded (`%3A`, `%2F`, `%5C`), the form an editor's `file:` URI carries. A binary is what git's own sniff calls one: a file holding a NUL byte (searched for in the whole file, not git's first 8000 bytes) that doesn't decode as UTF-16 text. Every binary fails as `binary`, whatever its kind or extension, since no rule can read what one holds: a font stores its names as UTF-16 and a WOFF compresses them, a PDF's streams and a zip's bodies are compressed, and an image can carry text in a compressed chunk or as UTF-16 in its EXIF. The one way through is `REVIEWED_BINARIES` in `leak.mjs` (empty, and pinned empty by the test): an entry for one path, holding the sha256 of the bytes a person read, so a changed byte or the same bytes at another path fail again. Encoded content is out of scope: base64, or a short compressed stream that happens to hold no NUL, reads as lossy UTF-8 in which no rule finds anything, and passes. The scan guards against a captured payload pasted in by accident, not a deliberate encoding, and a strict UTF-8 read would fail any cp1252 text a peer commits, refusing every push that carries it. UTF-16 text is decoded and scanned, and read again as lossy UTF-8 with every NUL byte dropped, so UTF-8 written into a UTF-16 capture, and UTF-16 text an odd-length UTF-8 part has shifted by a byte (both of which the UTF-16 view decodes as CJK), are scanned too. That view joins the parts as the text reads, so a uuid is not seen there when the nearest non-NUL byte beside it is an ASCII hex digit: a UTF-16 hex digit glued straight to it, as in a file of one encoding, but also a UTF-16 character whose byte on that side is one (U+4E61 is `61 4E` in little-endian, which reads `aN` after a uuid). A UTF-8 uuid glued to such a character is missed by both views, where a file of one encoding would hit it; a character between them with no hex-digit byte (a space, or U+4E00, `00 4E`) lets it hit. A hit both views find on one line is listed once, but a UTF-16 character holding a 0x0A byte (U+4E0A, say) moves the second view's line count, so a hit after one can be listed twice, under two line numbers. A symlink is scanned as the link text git commits. Names are scanned as well as bodies: every rule runs on each path segment and on the whole repo-relative path, and a name hit is reported at line 0, so a scrubbed copy that keeps a session-uuid file name or a profile-slug folder name still fails. Names are checked before any body is read, so binaries, symlinks and a tracked file deleted on disk are name-checked too. **Staged blobs (A7):** a plain `git commit` records the index, not the disk, so a leak staged and then fixed on disk without being staged again would pass a scan of the disk alone. Every path staged under the scope (its index entry differs from HEAD, or from the empty tree before the first commit) is read from the object store and scanned with the same rules, and its hits read `staged:<path>`. A staged blob byte-identical to the file on disk is skipped (the disk pass reported it), a staged submodule entry is name-checked only (the disk pass reads every listed path as a file, so a submodule folder on disk makes the scan throw, EISDIR, failing it), and an unmerged path during a conflict is scanned on disk. The scanner's own git calls drop lib's `GIT_LOCATION_VARS` in any case and run with `GIT_OPTIONAL_LOCKS=0`. Hooks see real session ids and paths, so a captured payload pasted into a fixture is the failure it guards against. The pre-push gate scans with these same rules and this scope, imported from `leak.mjs`, so the rules live in one place.

## Probes

`probes/` answers the platform questions the flow's design relies on (Q0–Q16 in the our-setup plan) by running throwaway headless Claude Code sessions whose hooks point at `probes/capture.mjs`, then reading what fired.

```bash
cd "$TEMP" && node <repo>/projects/hooks/probes/run.mjs [--only Q1,Q2] [--out <dir>]
node <repo>/projects/hooks/probes/run.mjs --cleanup <run dir>   # delete that run's probe sessions (and Q8's --bg job folder)
node <repo>/projects/hooks/probes/report.mjs [--notes <json>] [--doc <file>]   # regenerate the private probes.md (--doc: a file outside every repo)
```

- **One file per probe** in `probes/defs/` (`qNN-<slug>.mjs`), each stating its question and the assumption it tests, with a control arm wherever a broken instrument could read as a "no". A def imports only `../lib.mjs` and `node:` builtins. Every def that runs a session exports its verdict rule as pure functions `run()` returns through (`decide()` in most, beside Q0's `replica()` (and `realSkip()`, which gates its real-tree run), Q1's `delivery()`, Q3's `scratchIsolation()`, Q9's `junctionVerdict()` / `skillCCs()` and Q12's `agentFacts()`; Q13's `callArms()` / `outsideShape()` / `finalVerdict()`, with `nestNote()` only shaping its summary; Q15's `decide()` over `decideC()`, itself over `toolVerdict()`, `bashAttempts()` and `bashResult()`, for its tools part and `decideB()`, over `bPath()` rows, for its omitClaudeMd part), so the rule is tested offline while it stays inside the hashed def file. Verdicts: VERIFIED, CONTRADICTED, PARTIAL (some arms need a human or a later unit; a def flags one whose only open arms are unsettled or blocked, every settled arm agreeing, with `unsettledOnly: true`), INCONCLUSIVE (a control failed), BLOCKED. The runner files anything else as ERROR: a probe that crashes, a def that fails to import, one that returns no verdict or an unknown one, or one that outruns its ceiling (45 min, or the def's own `timeoutMs`). The runner files that one and moves past it once it has ended its own child processes, each with its tree (found by `ParentProcessId` and ended with `taskkill /T /F` on Windows; a `ps` tree sent SIGKILL elsewhere), naming each, and whether it ended, on stderr and in the record's evidence, and exits once the run is filed. A child the Windows listing gave no creation time is named with that reason and left running: its parent id may be one an earlier process held, and `taskkill /T` would take that process's tree. A grandchild whose parent already exited is out of that reach, and the probe's own code may still start more, so the runner still says to wait before `--cleanup`. A def's result can add fields but never replace its id, version, load-bearing flag or hash.
- **Isolation.** A probe session gets this environment minus every `CLAUDE*` variable (a nested session would inherit its parent's session id and messaging socket), the git location variables (`gitEnv()`: `GIT_DIR`, `GIT_INDEX_FILE` and the rest, matched case-blind, so no git call can land on a repo an outer hook names), and `AI_AGENT`, every name shaped like a credential and the gateway pair (lib's `SECRET_ENV`: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `DATABASE_URL`, any name ending in `_API_KEY`, `_ACCESS_KEY`, `_SECRET_KEY`, `_PRIVATE_KEY`, `_TOKEN`, `_SECRET`, `_PASSWORD`, `_PASS`, `_PWD` or `_CREDENTIALS` or holding `_TOKEN_`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS`, `ANTHROPIC_PROFILE`, `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID` and `ANTHROPIC_WORKSPACE_ID`, case-blind): a probe signs in with the CLI's own login, straight to Anthropic, never with a key a sourced `.env` left in the shell, through a gateway it named, or as another profile or federated identity (those rank above the login). `ANTHROPIC_BASE_URL` makes a gateway the endpoint, so it receives the login with every request, and `ANTHROPIC_CUSTOM_HEADERS` can carry an `Authorization` header; proxy and CA variables still pass, since a proxy only carries the connection to Anthropic's endpoint. That is a deny list, never an allow list, since the CLI needs `PATH`, its profile folders, `TEMP` and the rest; a def's own variables (Q3's `CLAUDE_CONFIG_DIR`, Q15's `ENABLE_TOOL_SEARCH`) pass as given. It loads no user settings (the live user hooks touch machine-wide `/tmp` markers) and works in a fresh folder under the system temp dir. The one exception is Q3's user-scratch arm, whose user source is a scratch `CLAUDE_CONFIG_DIR`. It launches only after a pre-flight of the same session (same env, sources and workspace) with `disableAllHooks: true` in `--settings`, which outranks user settings, no tools and a debug file. The pre-flight must fire no capture and no hook event, list the scratch skill and none of the live user skills, put `memory_paths.auto` under the scratch folder, and load user skills from it per its debug log; its settings watcher, when that line appears, must list the scratch `settings.json` and never the live one. Otherwise the arm never runs, and its row is isolation-unproven. Every launch carries `--strict-mcp-config`, so no configured, project or user MCP server ever starts. The one MCP server a probe runs is Q15's probe-local stub, a small stdio JSON-RPC script whose source sits in the Q15 def (so the verdict hash covers it), written into Q15's own workspace and passed with `--mcp-config`; Q15's sessions also set `ENABLE_TOOL_SEARCH=false`, so the stub's tool is offered by name, not deferred. Every launch carries a `--settings` file whose `claudeMdExcludes` keeps `~/.claude/CLAUDE.md` and `~/.claude/rules/**` out: the temp dir sits under the home dir, so the pilot's instructions otherwise load as project memory too. The same file sets `crossSessionInbound: "refuse"` unless a def sets that key itself: a `-p` session binds an inbox like an interactive one, so a live session's message could otherwise land in a probe's turn, and a `--settings` value outranks user settings for this key (settings reference; a project or local value can only be stricter). A def that spawns the CLI itself uses `baseArgs()` for the same flags, and a settings file the def wrote is rewritten whenever that merge changes it. A probe that runs a shell command allows exactly that command by a pattern rule (`Bash(node wait.js)` in Q5 and Q14, `Bash(node q8env.js)` in Q8), never a whole shell tool. Q0, the one probe that starts a session in the real tree (`projects/the-back-nine`), passes `--settings` with `disableAllHooks: true` there (flag settings outrank project and local ones; hooks reference, "Disable or remove hooks"), so no hook the real settings chain declares fires. The real run starts only when a replica run under the same flag finished cleanly, fired nothing and listed the same settings files on its watcher line, the replica logs gave a load kind, and the replica alone gave no verdict (`replica()`: a replica whose git top-level isn't its own repo folder, a control hook that never fired, a parent file that loads nowhere, or a deviation in the replica itself), since `decide()` returns that verdict without reading the real tree. Otherwise it is skipped, leaving the real tree unread (PARTIAL, unsettled only, where the replica decided nothing), and the skipped evidence line gives `realSkip()`'s reason, so no session runs in the real tree whose reading can't be used. Each real settings file (`{exists, size, sha256}`) and the names in `the-back-nine/.claude` are taken just before and just after the real run. Any change reads INCONCLUSIVE, ahead of every VERIFIED or CONTRADICTED, and is left as found: restoring it would be a second write to the live tree, over whatever a live session there saved. Q8's interactive arm reads the environment of the session `run.mjs` was launched from, and counts only when that session's CLI is the version under test: `AI_AGENT` and the version in `~/.claude/sessions/<CLAUDE_PID>.json` (read only when that file's pid and session id are that environment's) must name no other version, and at least one must name it. Otherwise the arm is BLOCKED, since a running session keeps its old binary after an update. That launcher reading stands for hook env through Q8's bridge, built from readings only: a PostToolUse whose Bash output carried a `Q8ENV` line with its hook's own session id. A Bash call that printed none is no evidence either way; an arm, or the workflow agent, with no reading leaves the bridge open there (unsettled only), and a reading that disagrees with its hook env is a measured PARTIAL that never says `unsettledOnly`. Q8's claim about workflow agents covers `-p` sessions only, where the main thread and its agents both read `sdk-cli` / `0`; whether an interactive session's agents carry its `cli` / `1` is an open arm, named in every summary and never claimed. Not isolated: each session still writes its project entry to `~/.claude.json`, and Claude Code rotates that file's backups; `--cleanup` leaves the file alone, since live sessions write it too.
- **Results are private.** Captures hold real session ids and paths, so they go to `~/.claude/flow/probes/<cli version>/<UTC stamp>/`, never into this folder. That default may sit in a repo only where git ignores it: both `results.json` and a random extensionless name in the run folder, so a name-only pattern (`results.json`, `*.json`), which hides that one file and leaves the captures beside it committable, reads as visible and the run refuses to start. `--out` refuses any folder inside a git work tree, ignored or not, as `report.mjs` refuses an explicit `--doc` (see The record), and each of these checks fails closed where git can't tell: a folder under a `.git` that git won't open, or one inside a `.git` dir. Each probe writes `<id>/made.json` as it makes folders, so `--cleanup` finds them even after a crash; `results.json` is rewritten after every probe. `--cleanup` deletes only what derives from a `claude-probe-*` workspace in the temp dir that a run listed: the workspace, its transcript folders under `~/.claude/projects` (listed, or found by name: the folder named for the workspace or for a folder inside it, even when no def listed it), and the CLI's task-output folders named the same way under `%TEMP%\claude` (its temp root on Windows; nothing else in that live folder is touched, and on Linux and macOS, where the CLI uses a `claude-<uid>` folder, the default root finds nothing), plus the folders named the same way in the CLI's per-cwd cache, where Q15's stub server leaves its MCP logs (`%LOCALAPPDATA%\claude-cli-nodejs\Cache` on Windows; no default elsewhere). It also deletes the job folder Q8's `--bg` session leaves (O24): `claude --bg` keeps each background session's state in `~/.claude/jobs/<short id>/`, beside every real background session's folder, so the target is named only by the id Q8's own launch record gives (`<run dir>/Q8/bg/bg-launch.json`, read with the def's patterns, and 8 lowercase hex), must sit directly under the jobs root as a plain folder, not a link, and must show in its `state.json` that it is this run's ended session: a `cwd` or `originCwd` that is a workspace the run made or a folder in one, a `sessionId` (when there is one) that starts with the id, and a state of `done`, `failed` or `stopped`. A folder that fails any of these is kept, and a printed line says why (for one still running: `claude stop <id>`, then `claude rm <id>`, or `--cleanup` again once it has ended). A folder `--cleanup` could not delete makes it exit 1. A run during which `claude --version` changed is marked invalid and files nothing.
- **What counts (KTD 10).** `passes.json` files each probe's latest `{verdict, run, hash, at, seen}` per CLI version, the hash covering the def plus `lib.mjs` and `capture.mjs`, and `seen` the measured verdicts filed on that hash. `passedOn(version)` returns a boolean and `passCheck(version)` the detail (`{passed, failing}`); both re-hash those files on disk now: a version passes only when every probe in `LOAD_BEARING` (pinned in `run.mjs`, never read from a def's flag) has a VERIFIED verdict whose hash still matches, and every probe Q0–Q16 has a def. Neither throws: when the check itself can't run (two def files claiming one id, an unreadable passes.json), the version is not passed, with a failing entry whose id is `*`. Editing a def, `lib.mjs` or `capture.mjs` voids the verdicts it backed until they re-run, and two measured verdicts that disagree on one hash fail the probe until its hash (def, `lib.mjs` or `capture.mjs`) changes, so a re-roll never decides it. VERIFIED, CONTRADICTED and PARTIAL count as measured, except a PARTIAL its def flags `unsettledOnly` for a probe pinned in `UNSETTLED_OK` (`run.mjs`: Q0, Q3, Q5 and Q7–Q14, each of which flags its unsettled-only PARTIALs): that one measured as little as an INCONCLUSIVE, so a VERIFIED after it is no conflict. Q1, Q2 and Q15 are never pinned, since their PARTIALs are measured deviations. The gate calls `passedOn` (a boolean); the stored `loadBearingPassed` is only true as of its filing. Re-run the set whenever a session reports a CLI version that isn't in that file.
- **The record.** `report.mjs` rewrites only the block between `<!-- generated:begin -->` and `<!-- generated:end -->` in `~/.claude/docs/plans/our-setup/probes.md`, under the passes.json lock, so evidence recorded by hand outside it survives. It marks a verdict whose `result.json` is missing or disagrees, whose def or instrument changed since, or whose measured runs disagreed. Design notes come from `--notes <json>` (default `~/.claude/flow/probes/notes.json`). An explicit `--doc <file>` must sit outside every git work tree, as `--out` must, or report.mjs exits 1 before writing: the scrubber aliases session ids, API ids and paths, but the workflow and agent ids and transcript keys a finding quotes stay. The default probes.md is never checked: it lives in `~/.claude`'s local-only repo, which tracks `docs/**` on purpose.
- **Q14's live recorder.** The headless Q14 probe can't make a typed or a Remote Control prompt, so `probes/live/q14-recorder.mjs` is a UserPromptSubmit hook for real sessions. It goes in `projects/.claude/settings.local.json`, written there through the settings writer at U3's live step 8 (Briggsy's ruling C29, 2026-10-20, authorizes adding it there); no code in this folder installs it. For each prompt it looks once for the prompt's own record in the transcript (the user record carrying its prompt id) and writes an `atHook` line saying what it saw; a hook that waited would hold up every prompt. When the record isn't there, it starts a poller and exits: the same script run with `--after-return`, detached, with no console window and its stdio ignored, handed the transcript path and prompt id in its environment, never on its command line. The poller looks every 150 ms until the record turns up or `Q14_LIVE_BUDGET_MS` after the hook started (10 s by default, and at most; 0 starts no poller), then writes an `afterReturn` line that joins the atHook line on `promptTag`. No poller starts either when the input has no transcript path or no prompt id: the atHook line's `readError` then says `no-transcript-path` or `no-prompt-id`. A polling atHook line with no afterReturn line means the poller died before it wrote: on Windows the CLI may end a hook's whole process tree when the hook exits, which stays unmeasured until the install step. The hook's look reads the transcript's last 4 MB, moved back to the start of the line the cut falls in (at most 64 MB back), so a big record is read whole; the poller's first look reads the last 64 MB. The atHook line's `record.window` (`{from, bytes, whole}`) says what the hook's look read, so a record that window missed can be told from one that landed after it. Lines go to `~/.claude/flow/probes/q14-live/captures.jsonl` (`Q14_LIVE_OUT` names another folder). It never writes what was typed (only whether the prompt opens a task notification or a slash command, and its length), a raw session id, prompt id or transcript path (`sessionTag` and `promptTag` are the first 8 hex of each one's sha256), or a record value that isn't a short token (anything else shows as its type). It prints nothing, since a UserPromptSubmit hook's stdout becomes context for the model, and always exits 0, the poller too; a failure writes an error line naming its stage and code, never the error's message, which can quote the input or a path. The poller never re-creates a captures folder someone removed.

### enforce-brief-before-work.sh

| **Runs** | Every session start, `/usr/bin/timeout 3 node <the session-start hook's own folder>/check-config-liveness.mjs` (~0.1 s; a PATH `timeout` is used only if it reports GNU coreutils) |
| **Prints** | NOTHING when all green; otherwise a short `CONFIG LIVENESS WARNINGS` block, appended to the manifesto's `additionalContext` |

Added 2026-09-30 after one research pass found three dead-and-silent wiring defects at once (the `ce:review` arm, the `web_search` redirect, a stale Serena permission). A hook that never matches looks exactly like a hook with nothing to say, so the check looks for the wiring itself:

1. **A skill name in a hook's case-arm that is not installed.** It reads every `case` whose subject variable was assigned from `.tool_input.skill`, in every `.sh` a settings hook command names plus `~/.claude/hooks/*.sh`, and judges **each alternative on its own** — a dead alias beside a live one is still flagged, because a whole dead arm can hide inside a mixed one (the original `ce:work|…|ce:review|…` arm was exactly that). The roster: every **enabled** plugin in `~/.claude/plugins/installed_plugins.json` (`installPath` → `skills/<dir>` and `commands/*.md`, in bare and `<plugin>:<name>` form, plus each `SKILL.md`'s frontmatter `name:`), `~/.claude/skills/*`, `~/.claude/commands/*.md`, and `<dir>/.claude/skills/*` + `<dir>/.claude/commands/*.md` for the project dir and every ancestor.
2. **A settings.json hook (or `statusLine`) command whose script path does not exist** — a token with a script/executable extension and a directory part, after expanding `~`, `$HOME` and `$CLAUDE_PROJECT_DIR`.
3. **A `~/.claude/skills` (or `<project>/.claude/skills`) entry that is a junction/symlink whose target does not resolve.**

**It must never break the manifesto injection.** Each check runs in its own try/catch and an error drops that check's findings (a half-built roster never produces false alarms — an unreadable `installed_plugins.json` skips the skill-name check); the whole script is wrapped and always exits 0; the output is ASCII-only; the session-start hook runs it under `timeout 3`, skips it if `node` or a GNU `timeout` is missing (Windows `system32\timeout.exe` is never used — it rejects the arguments and would silently skip the check), and discards its output on any non-zero exit. Fault-injected 2026-09-30 (syntax error, top-level throw, infinite loop, non-zero exit, `node` absent from PATH): every case still emitted valid JSON carrying the manifesto byte-for-byte.

**Run it by hand:** `node ~/.claude/hooks/check-config-liveness.mjs --debug` (roster size and scanned scripts on stderr). Test-only overrides: `--claude-dir`, `--settings`, `--hook <file>` (repeatable), `--skills-dir`, `--project-dir` — point them at scratch copies, never at a live hook.

**What it does not check:** MCP tool names inside hook text or CLAUDE.md (e.g. the `search_with_grounding` redirect) — enumerating a server's tools means starting the server, which a session-start hook must not do.

## The Full Chain

```
User: "run ce-work on Phase X plan"

1. Claude invokes compound-engineering:ce-work
   → PreToolUse BLOCKS: "run /brief first"

2. Claude invokes /brief
   → PreToolUse: marker created, allowed through
   → /brief loads insights into conversation

3. Claude re-invokes compound-engineering:ce-work
   → PreToolUse: marker consumed, allowed through
   → PostToolUse: drops /tmp/.distill-needed (silent)
   → ce-work loads, agent follows instructions

4. ... work happens ...

5. Claude tries to stop
   → Stop hook: marker exists → BLOCK: "run /distill"

6. Claude invokes /distill
   → PreToolUse: clears marker, allowed through
   → Agent captures insights (or confirms nothing to capture)

7. Claude tries to stop again
   → Stop hook: no marker → allowed through
```

A code review (`compound-engineering:ce-code-review` or `ultramode-code-review`) enters at step 3's PostToolUse: no brief gate, but the distill marker drops the same way.

## The Status Line

`statusline.py` is the Claude Code status line once the first deploy (U3's live step 6) points `statusLine.command` at a version folder's copy; until then settings run the old `~/.claude/statusline.py`. Claude Code runs the status line after each assistant message (debounced 300 ms) with a JSON description of the session on stdin, showing the first line it prints:

```
[Model] dir  branch | context bar pct% | 5h x% wk y% | session/all-time tokens | time | effort
```

U3 brought it here from `~/.claude/statusline.py` (the old script, still the live one until the first deploy) and rewrote it, so CI tests it and `deploy.mjs` ships it in each version folder. Python 3.8+, standard library only. A run by hand that reads the real transcripts without writing the real caches:

```bash
echo '{}' | CLAUDE_STATUSLINE_CACHE_DIR="$(mktemp -d)" python3 projects/hooks/statusline.py
```

- **UTF-8 everywhere.** Every file is read as UTF-8. The settings read used the locale default (cp1252 on this Windows Python), which raised on the 2026-10-16 mojibake and showed `?` for the effort; it now reads `utf-8-sig` with bad bytes replaced, so neither a BOM nor one bad byte hides the effort.
- **Effort** is the CLI's live stdin `effort.level`. Without one it falls back to settings.json, where a `modelSettings` entry whose key the model id starts with overrides the top-level `effortLevel`. No stdin value and no readable settings file reads `?`; one that parses but has no `effortLevel` and no matching override reads `default`.
- **All-time tokens** are input plus output tokens (cache tokens excluded, as /stats excludes them) over every `*.jsonl` under `~/.claude/projects`, subagent transcripts included, linked folders not followed. Each message id counts once, at its largest usage, across all files: the CLI writes one transcript line per streamed content block, each carrying the same `message.id` and a growing `output_tokens`, and a resumed or forked session copies earlier lines into a new file. Summing every line counted 64.7M where each id once, at its largest, gave 43.5M (measured 2026-10-21). A usage line with no id counts once, keyed by its byte offset in its file.
- **Incremental.** Transcripts only grow, so `statusline-index.json` keeps, per file, its size, how far it was read, each id's largest usage and the earliest timestamp seen. A file the same size is reused; a bigger one is read from where the last read stopped to its last newline (a half-written line waits); a smaller one is read again from byte 0, and its old ids leave the total; a deleted one leaves the index and the total. `statusline-cache.json` (`{v: 2, total, since, complete, mtime}`) is read on every refresh, the index only when the total is recomputed. Both sit in `~/.claude` (`CLAUDE_STATUSLINE_CACHE_DIR` moves them) and are replaced whole, a temp file renamed over each. Their names differ from the old script's `token-cache.json` on purpose: a session still running the old script after the switch never reads the new caches, nor the new script the old one's.
- **Recompute** runs when the small cache is older than 30 s, and on every refresh while `complete` is false. One run at a time recomputes, holding `statusline-index.lock`; any other prints the last cached total. A lock is taken over when its owner process is gone, when it is older than 120 s, or when it holds no owner token (a run killed between creating it and writing to it) and is older than 10 s. Reading stops 1.5 s after launch, so a first build over gigabytes of transcripts spreads over several refreshes instead of freezing the line.
- **The label says what it covers:** `43.5M since 9/15` (the local date of the earliest counted line, plus `/YY` when that is not this year); `12.3M…`, with no date, while a recompute hasn't caught up (the first build, or any later one that ran out of its read budget); `…` alone while nothing is cached and another run holds the lock. A count is rounded before its unit is chosen, so 999,999 reads `1.0M`, never `1000k`.

It refuses nothing, and a failure shows in the line, not as an exit code: any exception in the token part shows `?` for the total while the rest prints, stdin that isn't JSON still gets a line, and a field of an unexpected type replaces the whole line with `[status line error: <exception class name>]`. Its seams are for tests and measurements only, and the live command sets none: HOME and USERPROFILE (the home folder), `CLAUDE_STATUSLINE_CACHE_DIR`, `CLAUDE_STATUSLINE_BUDGET_MS` (the read budget, 1500 by default; 0 reads one chunk per run) and `CLAUDE_STATUSLINE_THROTTLE_SEC` (the recompute interval, 30 by default; 0 recomputes on every run).

## The Settings Writer

`tools/settings-write.mjs`, with `lib/encoding.mjs`, is the writer every change of ours to `~/.claude/settings.json`, any `settings.local.json` (through `--file`) and, key by key, `~/.claude.json` is meant to go through (KTD 14). Nothing live calls it yet. Its first live write is U3's live step 2 (the em-dash fold), and steps 3 and 4 (six `autoMode.allow` rules, then `env.DISABLE_AUTOUPDATER`), 6 (the first deploy, which `deploy.mjs` makes through it) and 8 (the Q14 hook into `projects/.claude/settings.local.json`, and Q8's trusted folder into `~/.claude.json`) write through it too. The CLI goes on writing these files itself (an "always allow" saves a permission rule, and it rewrites `~/.claude.json` all the time), which is why the writer checks for a change before its rename and, always for `~/.claude.json` and on request for settings, for a clobber after it. On 2026-10-16 a tool read settings.json as Windows-1252 and wrote it back as UTF-8, and every em dash came back as mojibake; a hand edit or a tool's own rewrite can also reorder or reformat the file, so a diff no longer shows what changed. The writer refuses a damaged file, keeps settings text pure ASCII so no cp1252 round trip can garble it again, changes only the paths a patch names, and records the ops that undo each write.

```
node projects/hooks/tools/settings-write.mjs --target settings|claude-json
     (--patch <file> | --reformat | --apply-inverse <file>)
     [--file <path>] [--expect-sha <sha256>] [--dry-run] [--diff]
     [--inverse-out <file>] [--create] [--persist-check]
     [--lock-wait-ms <n>] [--persist-delay-ms <n>]
```

- **A patch** (`--patch <file>`) is `{"ops": [...]}`, applied in order to a copy: any op that fails refuses the whole write. A path is an array of keys and indices, never a dotted string (keys hold dots and slashes: model ids, project paths). The ops: `test` (the path holds `value`, deep-equal; or `absent: true`; or `sha256`, the hex sha256 of the value's JSON with object keys sorted, never of its raw text, so a string's hash covers its quotes: the hash an inverse's test and a redacted value carry); `set` (the parent must exist unless `create: true`; `after: <key>` places a new key after a sibling); `delete` (`ifExists` makes a missing path a no-op); `push` (onto an array; `unique` skips a deep-equal duplicate); and `replaceInStrings` (`from` to `to` in every string value under the path, never in a key; a given `expectCount` must match the total exactly). An unknown op or field is refused, however it is spelled.
- **Input it refuses:** invalid UTF-8 (by byte offset, always); a BOM; text that isn't JSON holding an object; and text that isn't canonical, `JSON.stringify(parsed, null, 2)` plus a trailing newline exactly when the original had one. Canonical input is what makes "bytes outside the patch are unchanged" hold by construction: the writer serializes the same way. `--reformat`, alone and with no ops, is the one write that canonicalizes and drops a BOM.
- **Output it refuses:** mojibake (`lib/encoding.mjs`: a run counts only when mapping its characters back through the cp1252 table gives bytes that decode as one UTF-8 character, so a real em dash is never damage), named by path (for settings, by run and repair too, unless the string sits under `env` or is secret-shaped; a `~/.claude.json` run is part of a value, so it is never shown): a patch never writes a new run, and a damaged file is written only by a patch whose output holds none. `replaceInStrings` repairs a run in a value; it never touches a key, so a run in a key takes a `delete` and a `set`. For `--target settings`, any non-ASCII in the output, naming each path that holds it (`replaceInStrings` is the fix); `~/.claude.json` is exempt, since the CLI writes non-ASCII there itself. The rule judges the whole output, not what the patch changed, so a settings file that already holds non-ASCII refuses every patch (exit 2) but one that folds it all. The live `~/.claude/settings.json` holds 15 em dashes (in `autoMode` rules), so every patch to it but the fold, deploy's first switch included, refuses until the fold (U3's live step 2, before the first deploy at step 6) has run. A `--reformat` keeps the mojibake it found, never more, named in a warning, and warns on any non-ASCII its output holds instead of refusing it (re-serializing writes an escaped character raw, so a reformat can hold non-ASCII its input spelled as an escape); so a file with a BOM or a non-canonical layout and damage is fixed by `--reformat`, then a patch.
- **The write:** take the lock; read, the bytes' sha256 being `before`; check the input as above; apply the ops; serialize, keeping the newline choice; check the output as above. Output equal to input is "no change": exit 0, nothing written. `--dry-run` stops here, after the output checks, so an output they refuse refuses a dry run too (exit 2). Then a temp file beside the target (`<name>.sw-<pid>-<rand>.tmp`, UTF-8, no BOM, fsynced); the target read again, where any other sha256 is a concurrent change (exit 3, nothing written); the rename, retried on EPERM, EBUSY and EACCES for about 3 s (a Windows reader without share-delete); and a re-read that must give back exactly the bytes written and, for settings, hold no BOM, invalid UTF-8, mojibake or non-ASCII (after a `--reformat`: no more mojibake than it kept, and non-ASCII allowed), else exit 4. For `~/.claude.json` always, and for settings with `--persist-check`, every changed path must still hold its new value about 1.5 s later (`--persist-delay-ms`), else exit 4, "clobbered by another writer".
- **Locks.** Settings: the writer's own `<file>.sw.lock` (exclusive create, owner token inside); one older than 60 s is a crashed owner's, broken by moving it aside and checking. `~/.claude.json`: the CLI's own lock, taken as the CLI takes it, a `<file>.lock` folder made by `mkdir` (proper-lockfile's, checked against the 2.1.307 binary), held well under the CLI's 10 s stale age and never refreshed. Either lock is waited on up to 10 s (`--lock-wait-ms`), then exit 5. A CLI lock older than 30 s outlived any live owner: it is reported as stale (exit 5), never broken. The writer removes only a lock folder it made, and only while it is still the same folder.
- **What it prints:** one JSON object on stdout, `{ok, exit, target, file, before, after, written, noop, dryRun, changes, warnings, inverse, ...}`, `before` and `after` being sha256s of the file's bytes; errors also go to stderr with the exit code. No `~/.claude.json` value is ever printed: a changed one shows as `{type, length, sha8}`. For settings, so does a value under `env` or a secret-shaped one. `--diff` (settings only, and never with `--reformat`: exit 2) adds a unified line diff of the settings text in which such a line reads `~ env.<KEY> changed` or `~ <path> changed`. Secret-shaped means a key on the path named like key, token, secret, password, auth, credential, bearer or cookie, or ending in `_PASS`, `_PWD` or `HEADERS` (any case), or whose own text holds a secret; a string holding a known token prefix, a Bearer or Basic credential, an assignment whose name holds KEY, TOKEN or SECRET with a value of 12 or more characters and no `$`, a password assignment (a name holding PASSW or ending in `_PASS` or `_PWD`, a value of 6 or more), a `--password` value, a key or token flag's value, an `X-Api-Key` style header, a JWT, an Azure SAS signature or a password in a URL; or an argument right after a secret flag. It is deep: an object or array holding any of these is secret-shaped whole.
- **Inverses (rollback).** Every write that changes the file also writes an inverse file (`--inverse-out`, by default `~/.claude/flow/settings-writer/<UTC stamp>-<target>-inverse.json`): ops that undo it, each restore preceded by a `test` that the value is still what this write left, so a rollback refuses if anything changed it since. Before anything is written, the inverse is applied to the new document and must give back the original bytes, or the write is refused as an internal error. `--apply-inverse <file>` runs one through the same procedure, on its own target and file only. A secret-shaped old value is never stored: it becomes `{"redacted": true, "sha256": ...}` and its op is marked irreversible, and `--apply-inverse` refuses such a file whole, naming those paths. An array is one value, so a write that changes a list holding one secret-shaped item (a `permissions.allow` rule carrying a token, say) stores the whole list redacted, and neither `--apply-inverse` nor deploy's bare rollback can undo it. `--apply-inverse` also refuses, by the output rules above, an inverse that would put back non-ASCII or mojibake (the writer warns so when it writes one), so the em-dash fold and a mojibake repair can't be undone this way. The inverse of a `--create` write restores `{}`, not a missing file. A `--reformat` changes bytes, not values, and writes no inverse.
- **Which file.** `--target settings` refuses the CLI's own config: `~/.claude.json` and the other places the CLI may keep it (by identity, so a link or another spelling counts), and any file named `.claude.json` or `.claude-<suffix>.json`. `--target claude-json` refuses a settings file: any `settings*.json`, and the settings files by identity. Without `--file`, a `CLAUDE_CONFIG_DIR` in the environment refuses the default path rather than guess, as do, for `~/.claude.json`, a custom OAuth URL and a `~/.claude/.config.json`, which move the CLI's own file. `--create` starts a missing settings file as `{}`; `~/.claude.json` is never created.
- **As a library**, `settingsWrite({target, file, ops, reformat, applyInverse, expectSha, dryRun, diff, create, persistCheck, inverseOut, lockWaitMs, persistDelayMs})` returns exactly the object the CLI prints and never throws; `deploy.mjs` calls it. A caller that read the file to plan its ops passes that read's sha256 as `expectSha`, so exit 3 means "changed since you read it: read again and re-plan".

Exit codes: 0 written, no change, or dry run; 1 internal error; 2 refused (a bad patch or argument, a failed `test` op, damaged or non-canonical input, output that would hold mojibake, non-ASCII settings output, an `expectCount` mismatch, an irreversible inverse op, the wrong kind of file for the target, a missing file without `--create`, an `--inverse-out` file that already exists, `--diff` with `--reformat` or for `~/.claude.json`); 3 the file is not the one the caller read (`--expect-sha` differs, or it changed before the rename; nothing written either way); 4 written, but the post-write check failed or a later re-read shows it clobbered; 5 lock busy or stale.

## Deploys

`deploy.mjs` (KTD 12) builds hook versions into `~/.claude/hooks/v-<sha12>/` from a commit's blobs and switches `~/.claude/settings.json` over to them with one settings-writer call. Copying the hooks flat into `~/.claude/hooks/` by hand (see Deployment) could leave a live session running a half-copied set, never recorded which commit was live, and had no way back but another hand copy.

```
node projects/hooks/deploy.mjs deploy [--commit <rev>] [--patch <extra.json>] [--dry-run]
node projects/hooks/deploy.mjs snapshot-flat [--commit <rev>]
node projects/hooks/deploy.mjs rollback [--to v-<x>] [--dry-run]
node projects/hooks/deploy.mjs status
```

Every action takes `--hooks-dir <dir>`, `--settings <file>`, `--repo <dir>` and `--log <file>` (by default `~/.claude/hooks`, `~/.claude/settings.json`, the git top of `deploy.mjs`'s own folder, and `~/.claude/flow/deploys.jsonl`); deploy and rollback also take `--inverse-out <file>` (by default the writer's own path) and `--persist-delay-ms <n>` (1,500 by default), passed to the writer. With `CLAUDE_CONFIG_DIR` set and no `--settings`, every action, status included, refuses (exit 2) rather than guess which file the CLI reads; `--hooks-dir` and `--log` never follow `CLAUDE_CONFIG_DIR`. Tests pass the four common flags and `--persist-delay-ms 50`, with HOME and USERPROFILE on a temp home, so the writer's default inverse path lands there.

- **What a version holds:** `MANIFEST` in `deploy.mjs`, an explicit list, never a glob, so a stray file never goes live: the six hooks, `statusline.py`, `tools/settings-write.mjs` and `lib/encoding.mjs`, laid out as in the repo (the writer imports `../lib/encoding.mjs`). The manifesto is not in it. A test checks that every relative import a MANIFEST `.mjs` makes is in MANIFEST, or the deployed copy could not load it.
- **deploy** reads each manifest file's blob at `--commit` (HEAD by default), so a dirty work tree doesn't matter and `v-<first 12 hex of the commit>` means exactly those bytes. In order, so a refusal leaves nothing half done: (1) plan the switch from the current settings; (2) build into `v-<sha12>.tmp-<rand>/`, read each copy back and compare it with its blob, write `DEPLOYED.json` (`{version, commit, source, files: {path: sha256}, builtAt}`) and rename the folder to `v-<sha12>/`, while a failed compare removes the temp folder and leaves settings alone, and a `v-<sha12>/` that already exists is re-verified against its DEPLOYED.json and the blobs and reused (any mismatch refuses); (3) the peers gate; (4) one writer call, bound by `expectSha` to the settings read the plan came from, so any change since (a hooks command added during the build, say) refuses with nothing written; (5) settings, read again, must point where the plan said, and one line goes to the log. `--patch <extra.json>` (the writer's `{"ops": [...]}`) adds ops to that same write; later units add hook entries this way. `--dry-run` builds and writes nothing and reports the switch it would make; the writer still checks its output, so a switch the writer would refuse refuses the dry run too (exit 2).
- **The rewrite rules.** Every string under a key named `command`, at any depth (hook commands, `statusLine.command`), is scanned for the hooks folder in any spelling. Only a tilde form at the start of a word rewrites: `~/.claude/hooks/<file>`, `~/.claude/hooks/v-<12 hex>/<file>` and `~/.claude/hooks/v-flat-<12 hex>/<file>` become `~/.claude/hooks/v-<new>/<file>` for every file the new version holds, and the legacy `~/.claude/statusline.py` in `statusLine.command` becomes `~/.claude/hooks/v-<new>/statusline.py`. Anything else that names the hooks folder (a file the version lacks, `$HOME/...`, an absolute path, a quoted tilde) refuses the whole deploy, so settings are never half switched. A command that names neither (the Notification PowerShell one) is left alone. Each rewritten command's `set` op follows a `test` op holding its current value. After every op is applied in memory, each reference must name the new version and a file it holds, or the deploy refuses. A hooks-folder mention outside a command (a permission rule, prose) is left as it is and named in a warning, as is a deployed file that calls a sibling by its flat path.
- **The peers gate (KTD 23).** `settings.json` is user-global, so just before the write `peers.mjs` (`projects/skills/squeaky-clean/scripts`) must answer `ok: true` and `busyAnywhere: false`. A busy session in any repo refuses, named by pid, name and status (never a socket path or a full session id), and a registry that can't describe this session refuses as unknown. `--dry-run` reports the gate without refusing. A refusal leaves the built folder, which isn't live and is reused by the next deploy of that commit.
- **snapshot-flat** (the bootstrap, run once) copies the six flat hooks into a kept folder, so the first versioned deploy has a rollback target. It never switches settings, and refuses when a flat hook is missing. The folder is named by a walk of `git log` over the six hooks' paths, back from `--commit` at most 1,000 commits: the newest commit that touched one of them and whose six blobs equal the flat files byte for byte, which is the commit that last changed them to that state (a later commit that left them alone, HEAD say, never names it). When none matches, it is `v-flat-<12 hex of a hash over the copied files>`, with a warning; its DEPLOYED.json says `source: "flat"`. `~/.claude/statusline.py` is copied in too when it exists (under `extras`), since the first deploy moves `statusLine` into the version folder. A deploy of the very commit a snapshot is named by refuses (the snapshot is never rewritten), so the first deploy is a later commit.
- **rollback**, bare, undoes the newest switch still in force. The log replays as a stack: a deploy or a `rollback --to` pushes its entry, and a bare rollback pops one (its line says `{undoes: <id>}`), so repeated bare rollbacks step back one switch at a time, never toggling between the last two. Settings must still point at that switch's version (else they changed outside deploy, and `--to` is the way on), unless they are byte for byte what the switch found, when the undo is logged with nothing written. The switch's logged inverse (the writer's inverse file for that very write) is applied in memory, putting back what the switch replaced, `--patch` ops included; the result is switched onto the switch's previous folder (for `flat`, the newest snapshot-flat folder), which must pass its DEPLOYED.json check; and both go to the writer as one write, behind the peers gate. An inverse that is missing, belongs to another write, holds an irreversible op or no longer applies refuses by name, with nothing written.
- **rollback --to v-<x>** is a pointer switch: the rewrite rules, restricted to the files that folder holds, applied to settings as they are. The folder must exist and pass its check. It is pushed like a deploy, so a bare rollback after it returns to where the jump started, and it leaves alone what a switch wrote beyond command pointers (a `--patch`'s env or permissions). A `--to` that finds settings already pointing at the folder writes nothing. It logs the newest switch's undo when the folder is that switch's previous and settings are byte for byte what it found, a resync when the log's newest switch in force names another version, or the log holds none (so the log agrees with settings again), and nothing when the log already agrees; a log that doesn't replay as a stack gets neither, only a warning. A `--to` on settings where no command names the hooks folder refuses.
- **The manual way back.** A rollback that can't plan (a `--to`, or a bare one once the newest switch's inverse has applied) offers that switch's logged inverse, applied by the writer by hand (`fallback.command` as argv, `fallback.commandLine` as text), only where it lands somewhere sound: every command reference afterwards must name a kept folder that passes its check and holds the file named, a flat hook that exists, or a legacy status line that exists. It runs the writer deployed in the folder it lands on, else the work tree's, never the writer of the version being escaped. The line is `node`, bare, then single-quoted arguments, which Git Bash, sh and PowerShell 7 read as the same words; when an argument holds a single quote (straight, or curly U+2018 to U+201B, which PowerShell also reads as one), the words say it is for a POSIX shell (Git Bash) only; a double quote needs no note. They also say it skips the peers gate and the deploy log, and what the log then makes of it: where it lands on a version folder, what `rollback --to` that folder records; where it lands on none (the flat files, a mix, no hooks command), that a later bare rollback records it as the switch's undo while that switch is the newest in force and settings are then byte for byte what it found, and that otherwise the log goes on naming the switch as in force. A bare rollback refused before its inverse applies (the log doesn't replay, nothing to undo, settings changed outside deploy, a resync on top, an inverse missing, another write's, irreversible or no longer applying) offers none: that inverse is unknown there, or no longer fits settings.
- **After an exit 4** (a write that landed but failed a check after it; exit 1 instead when the writer's own failure after its rename was an internal error, logged and advised the same way), the result's `recovery`, `{how, to}`, names the way back the facts support then, with settings and the log read again: `bare rollback`, `rollback --to`, `in force` (a rollback that landed where it was going), `by hand`, or `none`. A `--to` is named only where it would plan, never while settings hold no command naming the hooks folder. Beside it, the words name the paths the switch wrote that a pointer switch leaves (for a deploy, its inverse by hand is offered after the `--to` when that lands somewhere sound), or say in plain words why its inverse can't be read: irreversible ops (at which paths), no inverse file logged, the file missing, or a file that can't be read as this switch's inverse.
- **status** reports the active version (from settings: every hooks-folder command must agree, else "mixed"), each kept folder with its DEPLOYED.json summary and check, leftover temp folders, which flat files still exist, and the last log entries. It writes nothing.
- **The log**, `~/.claude/flow/deploys.jsonl`, gets one line per switch, each a single `O_APPEND` write so a concurrent append is never lost: `{id, at, action, version, previous, commit, settingsBefore, settingsAfter, inverse}` (sha256s of the settings file, and the writer's inverse file), plus `undoes`, `postcheck: "failed"`, `noop` or `resync` where they apply. snapshot-flat logs one line when it builds a folder (a run that reuses an existing one logs nothing).
- **No version folder is ever deleted.** A live process may still be running a hook from one: KTD 12 keeps every version until each live process shows a heartbeat from its successor, which U7 and U9 build. There is no prune command.

Output: one JSON object on stdout, `{ok, exit, action, ...}`; errors also go to stderr. A secret-shaped command shows as `{type, length, sha8}`. Exit codes: 0 done (or dry run, or nothing to change); 1 internal error (including a log append that failed after a switch: the result then says `switched: true`; and a writer that failed internally after its rename, logged with `postcheck: "failed"`); 2 refused (a failed cmp, an unknown hooks-folder reference, a version folder mismatch, peers busy or unknown, nothing to undo or an inverse that can't be applied, a `--to` with no hooks-folder command in settings, the writer refused or its lock was busy, bad arguments); 3 settings changed after deploy read them to plan (nothing written: run it again); 4 written, but a check after the write failed, logged with `postcheck: "failed"`.

## The Pre-push Leak Gate

`tools/pre-push-leak.mjs` (D8) is the monorepo's pre-push gate once `install-git-hooks.mjs --go` installs it (U3's live step 8; until then nothing runs it before a push): it refuses a push that would publish a leak into the scanned folders. CI's leak test runs after a push, too late for a public repo; this runs the same rules and scope (`tests/leak.mjs`: its rules, the binary and UTF-16 handling, the path checks) over what the push is about to send. Git runs it as `pre-push-leak.mjs <remote name> <url>`, with one stdin line per ref: `<local ref> <local sha> <remote ref> <remote sha>`.

- **Every commit the push publishes** is scanned, not just the tip, since the remote receives them all: `git rev-list <local sha> --not <remote sha>`, or `--not --remotes` (every commit no remote-tracking ref holds) for a new remote ref or a remote sha this repo lacks. A leak added in one commit and removed in a later one of the same push is still refused. A delete publishes nothing. It never runs `git fetch`.
- **What it reads:** every path under the scope a commit adds or modifies, from one `git diff-tree -r --root --raw -c` call fed all the commits. `-c` reads a merge: it lists the paths whose merged blob differs from every parent, so content written during the merge is scanned, while a path taken unchanged from a parent carries a blob some earlier commit introduced, scanned there or already public. Each path's name and each blob's body go through `leak.mjs`, every blob read in one `git cat-file --batch`.
- **Never scanned:** commit and tag messages, which carry the `Claude-Session` attribution trailer by rule and would match the api-id rule. The remote URL is never printed, since it can carry a credential.
- Stdin is read to its end in a loop (`leak.mjs` `readFdSync`). Git ends every ref line with a newline, so input that stops partway through a line was cut short, and fails closed.

Exit 0: no commit to publish, none touching the scope, or all of it clean; a line on stderr says which. Exit 1: a hit, listed as `<commit12> <path> <rule id>` with its line numbers, never the matched text, plus the advice to rewrite the listed commits (a later commit that removes the text doesn't help); or an internal error, which fails closed too, because this guards a public repo, and whose message says `git push --no-verify` skips the gate, to be used only knowingly.

`tools/install-git-hooks.mjs` puts the gate in a repo's pre-push hook, or takes it out:

```
node projects/hooks/tools/install-git-hooks.mjs [--repo <dir>]                      say what it would do
node projects/hooks/tools/install-git-hooks.mjs [--repo <dir>] --go                 install it (or upgrade an earlier version's hook)
node projects/hooks/tools/install-git-hooks.mjs [--repo <dir>] --uninstall [--go]   remove it
```

Without `--go` it changes nothing: it prints what it would do and exits with the code that action would have. `--repo` defaults to the repo the file sits in. The gate runs only in a repo where `--go` has installed it; for the monorepo that is U3's live step 8, and tests install into temp repos only.

- **The hook runs HEAD's committed gate**, never the work tree's. Every session shares one work tree, so a gate run from there would run whatever a session is halfway through editing: a syntax error would refuse every clean push, and a rule weakened there would pass a leak. At each push the hook (`#!/bin/sh`, a marker line, LF endings, mode 755) extracts the whole `projects/hooks` folder from HEAD into a fresh `mktemp -d` folder (in TMPDIR, falling back to /tmp when TMPDIR can't take one, so a stale TMPDIR can't refuse every push) in two steps, `git archive --format=tar HEAD -- projects/hooks` into a file there, then `tar -xf` of that file: never a pipe, whose status under `sh` (no pipefail) is `tar`'s alone and would hide a failed `git archive`. It runs that copy of the gate from the work tree's top with git's arguments and stdin, and removes the folder on every way out. HEAD, not the remote's main, so a committed fix to a false positive applies to the push that carries it from the checked-out branch (a push of another branch still runs HEAD's gate). The whole folder rather than a list of the gate's files, so a gate that gains an import needs no reinstall (measured 2026-10-22: `git archive` of the folder took 0.26 s and wrote 942 KB). It fails closed by name when no temp folder can be made, `git archive` or `tar` fails, or HEAD has no gate. Tests keep symlinks out of that folder (Git Bash's tar can't unpack one, so every push from Windows would be refused), and the `export-ignore` and `export-subst` attributes off it and the folders above it (`git archive` obeys both, dropping or rewriting the gate's files).
- **Which hook is its own:** a file whose bytes are exactly `HOOK_TEXT`, or exactly one of `PRIOR_HOOK_TEXTS` (an earlier version's text; empty, since no earlier version of the hook was ever installed on a real repo). `--go` replaces an earlier version's hook, and `--uninstall` removes either. Anything else at the hook path is refused by name and left byte for byte: a hook without the marker line, or one with the marker and other text, since replacing or removing it could drop someone's own lines. Installing the same text again writes nothing. A test pins `HOOK_TEXT`'s sha256: changing the hook fails it, naming the upgrade steps (append the old text to `PRIOR_HOOK_TEXTS`, run `--go` on the monorepo before pushing, and keep the old gate paths in HEAD until then).
- **Where it goes:** the hooks folder of the repo's common git dir, where git looks (a linked worktree shares it). It refuses while `core.hooksPath` sends git to another folder, where a hook in `.git/hooks` would never fire; a `core.hooksPath` naming `.git/hooks` itself is accepted. `--uninstall` skips that check: it removes its own hook from the common git dir's hooks folder either way. The hook runs `node` from PATH, and a missing node fails the hook, which refuses the push.

Installer exit codes: 0 done, would do, or nothing to do; 1 internal error; 2 refused (a hook that isn't exactly one this tool writes or wrote, `core.hooksPath` naming another folder, not a work tree, bad arguments).

## Deployment

Scripts deployed flat at `~/.claude/hooks/` (until the first versioned deploy, below). The Elite Engineer manifesto deploys alongside at `~/.claude/manifesto/elite-engineer.md` (sibling directory — content vs code separation). Configuration in `~/.claude/settings.json`:

```json
{
  "hooks": {
    "SessionStart": [
      { "matcher": "", "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/elite-engineer-session-start.sh" }] }
    ],
    "PreToolUse": [
      { "matcher": "WebFetch", "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/block-webfetch.sh", "onFailure": "block" }] },
      { "matcher": "Skill", "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/enforce-brief-before-work.sh", "onFailure": "block" }] }
    ],
    "PostToolUse": [
      { "matcher": "Skill", "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/remind-distill-after-work.sh" }] }
    ],
    "Stop": [
      { "matcher": "", "hooks": [{ "type": "command", "command": "bash ~/.claude/hooks/stop-distill-gate.sh" }] }
    ]
  },
  "statusLine": { "type": "command", "command": "python ~/.claude/statusline.py" }
}
```

The two PreToolUse guards carry `onFailure: "block"` (Finding 5): a copy of this block without it lets a broken guard fail open. The live file also holds a Notification hook (a PowerShell message box), which nothing here ships and `deploy.mjs` leaves alone.

This project folder is source control. The deployed copies at `~/.claude/hooks/` (and the manifesto at `~/.claude/manifesto/`) are the live versions. The status line is set apart from the hooks, in `statusLine.command`, which names the old copy, `~/.claude/statusline.py`, until the first deploy below.

**`deploy.mjs` replaces the copy steps below once its first run switches settings** (see Deploys). That is U3's live step 6, after the U3 code lands and after the em-dash fold (live step 2): the writer refuses a patch whose settings output would hold non-ASCII, which on today's settings (15 em dashes) is every patch but the fold itself (see The Settings Writer). So until the fold, deploy's switch refuses (exit 2), and so does `deploy --dry-run`, since the writer checks its output before its dry-run stop; snapshot-flat, which writes no settings, can run. `node projects/hooks/deploy.mjs snapshot-flat` keeps today's flat hooks (and `~/.claude/statusline.py`) in a version folder as the first rollback target, then `node projects/hooks/deploy.mjs deploy` at the landed commit (`--commit <rev>`, HEAD by default) builds `~/.claude/hooks/v-<sha12>/` and, in one write, points every command above and `statusLine.command` at it. If the flat hooks were re-synced to the landed commit (below) and that commit changed one of the six, snapshot-flat names its folder by that commit, and the deploy of that commit then refuses, since a snapshot is never rewritten: deploy a later commit (an empty one does). A deploy that succeeds leaves no command naming a flat file; `deploy.mjs status` then names the live version, and a hook change ships as a commit followed by `deploy.mjs deploy`, never a copy. Until that first deploy has run, the flat copies are live and the steps below stand. The manifesto is not in `deploy.mjs`'s MANIFEST, so its copy step stays either way.

**Install / re-sync** (the hooks: until the first deploy; the manifesto: always):

```bash
# Shell hooks + the liveness check the session-start hook calls (until the first deploy)
cp projects/hooks/*.sh projects/hooks/check-config-liveness.mjs ~/.claude/hooks/
chmod +x ~/.claude/hooks/*.sh

# Elite Engineer manifesto — goes to a sibling dir, NOT ~/.claude/hooks/ (always: deploy.mjs doesn't ship it)
mkdir -p ~/.claude/manifesto
cp projects/hooks/elite-engineer.md ~/.claude/manifesto/elite-engineer.md
```

After any source edit in this folder, re-run the copy that applies, then `cmp` each pair — the live and tracked copies must stay byte-identical (a deployed version folder is compared with its commit's blobs by `deploy.mjs` itself). The hook reads the manifesto at `~/.claude/manifesto/elite-engineer.md` at session start, so the runtime copy is what Claude sees.
