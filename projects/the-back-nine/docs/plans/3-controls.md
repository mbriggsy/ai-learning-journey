# Act 3 — Controls

> **Status: IN PROGRESS — U9 SHIPPED, U10 next.** U9 (the budget builder — engine + UI) shipped and cold-read-cleared 2026-07-02: `src/budget/` is live (`budgetModel.ts` + `budgetToSpending.ts`), the two-track floor/lifestyle evaluation runs in the engine, and the builder UI mounts from the Result surface. U10–U13 are scoped and build-ready, **not started**. Per-unit build status lives in the roadmap's You-Are-Here table, which wins on conflict.

**The goal.** Deliver the "pull it toward you" half of the product as a **shippable cold-read milestone before the solver exists**: the itemized **budget builder** (essentials = the survival floor, discretionary = the surplus), the **two manual controls** (withdrawal **sequencing** + **Roth conversion**, both driving the Act-1 overlays the solver will later search), the **healthcare surfaces** (ACA cliff, IRMAA, HSA) over the Act-1 healthcare overlay, the **sharpen loop** (every assumption visible and editable, each edit *sharpening* the answer), and **returning-user re-entry** with honest per-surface staleness. After Act 3 a friend can build a real budget, hand-tune both controls, see the survivor's tax cliff move, and come back tomorrow to a calm, honestly-stale saved answer — all without a recommendation yet.

**Why this is Act 3.** These surfaces all *consume* the first answer (Act 2) and the validated spine + overlays (Act 1) — they make sense only once the confidence statement exists and the engine is deterministic. They are also the entire input + reasoning substrate the Act-4 solver searches: the budget's two-tier essentials/surplus split *is* the lexicographic objective's two tiers; the two manual controls *are* the solver's search axes; the healthcare overlay is the cliff the solver must not silently optimize over. Building and **cold-reading** them by hand first means the solver in Act 4 inherits proven, honest control surfaces instead of inventing them — and the manual milestone is itself a real, usable tool. The honesty bar rises here, not later: every control readout that moves real money must wear its hedge.

**The chain in one line.** `budget → controls → healthcare → sharpen → re-entry`: **U9** compiles an itemized, time-boxed budget into the two-tier (essentials-floor / lifestyle-surplus) reading; **U10** lets the user hand-tune sequencing + the Roth conversion over the Act-1 overlays and **introduces the `require-the-hedge` copyGuard lint**; **U11** surfaces the income-dependent healthcare reality (the ACA cliff, IRMAA, HSA) over the Act-1 overlay; **U12** makes every assumption editable so each edit *sharpens* the answer; **U13** brings the returning user (and the surviving spouse) back to a re-derived saved answer with honest per-surface staleness.

## The eight cross-cutting contracts

*These eight contracts span the five units below. Each is named once here so a reader sees the seams, then enforced in the unit that owns it — mirroring the contract sets that govern the earlier acts. Several are seams Act 1 / Act 2 explicitly handed forward into an Act-3 home; this section is that home. The tax and healthcare overlays are **dependencies on Act 1**, consumed here, not re-specified.*

1. **The tax + healthcare overlays are CONSUMED as Act-1 dependencies — never re-specified here (the de-duplication).** The Roth/sequencing controls (Unit 10) **drive** the Act-1 (U2) **tax-and-accounts overlay** (per-person pre-tax / Roth / taxable buckets, ordinary-income tax on pre-tax withdrawals + RMDs + the conversion, **Social-Security provisional-income taxation** as a per-year bounded fixed-point, the **MFJ→single** switch at the sampled first death) and the Act-1 (U1) **sequencing substrate** (`sequencing.ts`'s named drawdown policies). The healthcare surfaces (Unit 11) **read** the Act-1 (U3) **healthcare overlay** (the two distinct MAGI calculators — **ACA-MAGI ≠ IRMAA-MAGI** — the pre-65 ACA cost as a per-year fixed-point with explicit 400%-FPL-cliff branching, the IRMAA 2-year-lagged surcharge, the HSA fourth bucket). `roth.ts` here **orchestrates the two arms + the conversion event over those overlays; it does NOT re-implement decumulation, taxes, RMDs, the SS fixed-point, or the ACA fixed-point** — it reuses the same per-year update function so order-of-operations can never drift between the spine and a control. The **reduce-to-spine byte-identity** is inherited from [docs/architecture.md §5](../architecture.md), re-asserted by each control's OFF arm, never re-derived. All tax/health numbers live in `src/engine/constants/`, never inlined.

2. **The single-shared-market-draw / CRN rule is structural and now MORE load-bearing (inherited from Act-1's CRN contract; one-line restatement).** All account buckets — pre-tax / Roth / taxable / **HSA** — share **one** market-return draw per year (the same normals stream as the spine); buckets differ ONLY in tax treatment, never in return assumption. Tax / RMD / conversion / ACA / IRMAA are deterministic post-draw arithmetic consuming **zero** random draws. This lets the two control arms (Unit 10) and the budget's two-track evaluation (Unit 9) read off **identical** futures (signal, not luck), and it **structurally forecloses asset-location**. Per-bucket draws are forbidden. The full contract lives in [docs/architecture.md §3](../architecture.md).

3. **The death-order conditional-FILTER contract (owned cross-cutting by Units 10 + 12; consumes Act-1 longevity).** Death-order is an editable hypothetical in **both** the control surface (Unit 10) and the sharpen loop (Unit 12). It is committed to ONE reading: **a CONDITIONAL view that FILTERS the existing path population — never a re-draw, never a re-index of which spouse is the survivor.** Selecting "if one of you outlives the other" conditions on the **sub-population of paths where the chosen spouse dies first** — same seed, same draws, zero re-index — CRN-safe by construction. This is buildable only because Act-1 longevity **samples per-path, per-spouse death years and retains which spouse died first per path**. **Semantics:** the **default** readout is the engine's full probability-weighted **mixture** ("whoever outlives the other" — the honest number); the conditional view is clearly labelled a hypothetical, **never a prediction** (R12), never a deterministic to-age horizon. **Thin-subpopulation guard:** below a minimum path count the conditional view **widens its hedge / declines a precise frequency** rather than show a noisy number. Death-order, survivor-spending ratio, and per-person retirement years are **single model fields** — an edit from either surface recomputes **both** the spine and any open control under the unchanged seed. The survivor's **MFJ→single threshold flip for BOTH IRMAA and the ACA-FPL basis** rides this same filter.

4. **The require-the-hedge copyGuard lint (owned by Unit 10; extends Act-2 U7's copyGuard).** The Act-2 copyGuard was a ban-list (certainty-hygiene, catastrophe-lexicon, the catalog-enumeration). **Unit 10 adds the new lint shape the reset demands: a positive/require assertion** that **every control readout and every recommendation-class headline CONTAINS a probabilistic hedge** drawn from the typed hedge-token catalog. **It must NOT hand-duplicate the phrase list it checks — it reads the same single-sourced hedge-token set `copy.ts` uses to author the strings** (`burned/063` single-source-the-gate). The surviving ban-list checks (certainty verbs, catastrophe lexicon) stay. **`src/viz` stays string-free** (`TwoFutures` receives all text as props from `copy.ts` at the `src/ui` layer); **all control + healthcare surfaces route through the catalog**, and the slot-discipline allowlist gains the new numeric slots (tax-bracket %, user-echoed conversion amount/years, the survivor tax-cliff `~$X`, the ACA/IRMAA cost `~$X`, the shadow-marginal-rate `~X%`). The securities/IA **attorney-gate has LAPSED** (personal-tool reset): the categorical framing of the Roth surface (Unit 10) is now an **honesty/calm** choice, **not a legal shield** — it is **not** carried as a live gate, and no fixture or copy is blocked on it. *"It's just for friends" never softens this — the hedge is required because the readout moves real money* (R25, [docs/product.md §2](../product.md)).

## Unit 9 — Budget builder (itemized, time-boxed, two-tier)

*Essentials = floor / discretionary = surplus; the two-tier lexicographic headline reading.*

> **The two-date split rides this unit — no new budget mechanism.** The fuck-off date's **floor vs lifestyle dates** (R27) are this unit's two-track compilation consumed by the date-search (C3, shipped in Act 1): the two dates **coincide** in the degenerate single-total-spend case via this unit's existing **degenerate-collapse**, and separate when the budget splits the tracks — C3 consumes whatever two tracks `budgetToSpending` emits; nothing in the date-search is rebuilt. The mixed date outcomes — `{floor: date, lifestyle: no-date}` and the `floor > lifestyle` 100%-FPL-floor signature — are dark until this unit lands; the result *shape* already admits them from C3, the behavioral tests ride here. **U9 follow-on (owed when the itemized budget lands):** the budget's **medical line and the date-route's per-year `oopMedical[t]` stream must reconcile to ONE source** — the HSA qualified-spend cap rests on the cap-only containment premise (the household spend figure already *includes* out-of-pocket medical), so an itemized medical line that ALSO feeds `oopMedical[t]` would double-count medical, and one that silently replaces it would zero the HSA cap — never silently double- or zero-count.

**Goal.** Let the user build their real spending as an itemized, categorized, **time-boxed** budget whose structure *is* the lexicographic floor/surplus split — and read the answer as a **two-tier verdict** (essentials safe in X of 10; full lifestyle holds in Y of 10) over the *same* outcome-state set, never a new state.

**Requirements.** R20 (itemized, categorized, time-boxed; essentials = floor, discretionary = surplus); R2 (survival-vs-lifestyle separation, Kitces "trim, not go hungry," no color-alone); R19 (budget sanity); R8 (the budget is the *deepening* of the single-total-spend answer, reached via the sharpen loop, never the on-ramp). The requirement text is in [docs/product.md §7](../product.md).

**Dependencies.** Act-1 U1 (the spine — evaluates both tracks on one draw set), Act-1 U2/U3 (overlays — the pre-65 healthcare-gap line's cost is income-dependent, computed by U3, not user-typed), Act-2 U5 (the `memoryModel` orchestrator — a budget edit recomputes through it; R19 grammar), Act-2 U6 (viz tokens for the two-tier readout), Act-2 U7 (outcome-state set + copyGuard catalog).

**Files.**
- Create: `src/budget/budgetModel.ts` (the line-item shape + tier + time-box window), `src/budget/budgetToSpending.ts` (compiles the itemized budget → the **two** per-year spending vectors the engine reads), `src/ui/BudgetBuilder.tsx`, `src/ui/BudgetLineItem.tsx`, `src/ui/TwoTierHeadline.tsx`
- Modify: `src/shared/model.ts` (the `budget` field, under the single schemaVersion bump — contract #5), `src/store/memoryModel.ts` (budget edit → recompute), `src/ui/copy.ts` (the two-tier headline + line-item strings)
- Test: `src/budget/__tests__/budgetModel.test.ts`, `budgetToSpending.test.ts`, `src/ui/__tests__/budgetBuilder.test.tsx`

**What it delivers.**
- **Line-item shape (decided):** `{ category, label, annualAmount, tier: 'essentials' | 'discretionary', window: { startYear, endYear | null } }` — `endYear: null` = lifelong. **Time-boxed** is first-class: a travel item runs years 1–N then stops; the **pre-65 healthcare-gap** item runs retirement→65. Forward-looking **planning** input, not back-looking expense tracking (the tracker lane is explicitly out — see the scope boundaries in [docs/product.md §7](../product.md)). `startYear`/`endYear` are **offsets from each owner's retirement year**; a window clamps to `[0, horizon]` and truncates at a per-path death per the survivor-spending composition rule below. **All `annualAmount`s are today's-dollar (real) figures** — `budgetToSpending` emits real per-year vectors and the engine applies the methodology inflation default, matching the spine's inflation-adjusted convention so reduce-to-spine holds for itemized budgets too.
- **The pre-65 healthcare-gap line is a special, income-dependent slot (the seam to Unit 11):** the budget **reserves** the time-boxed slot (retirement→65 per spouse, Medicare being individual), but its **net cost is computed by the Act-1 U3 overlay** (ACA premium − PTC, MAGI-dependent), **surfaced through Unit 11** — it is **not** a user-typed flat amount, or the model would silently miss the conversion↔subsidy interaction. The gap line is **`tier: 'essentials'`** (you cannot go uninsured pre-65 — it is part of the survival floor, counted in Tier-1), one window per spouse ending at that spouse's age 65. Because the dollar is MAGI-dependent and the two tracks spend differently, **it resolves to a *per-track* value** — the essentials-only track's lower spend yields lower MAGI, more PTC, and a **lower net premium** than the full track; U3 computes its dollar inside *each track's own* MAGI fixed point.
- **Two-track compilation (the structural realization of the two-tier reading):** `budgetToSpending` emits **two** per-year spending vectors from one budget — an **essentials-only** track (Tier-1 floor) and a **full** track (essentials + discretionary). The engine evaluates **both thresholds against the SAME path population on the SAME single shared draw set** (contract #2): "essentials covered every year" (Tier-1) and "full lifestyle covered every year" (Tier-2). ONE shared draw set but **two decumulation + overlay passes** — essentials-only and full are distinct portfolio trajectories, never the full-spend run read twice. This is the engine half of R21's lexicographic structure the Act-4 solver later optimizes (objective ≡ headline metric); Unit 9 builds the *reading*, Act 4 builds the *objective over it*.
- **Two-tier headline reading (NOT a 7th state):** the headline composes **two** outcome-state-tagged readings over the *same* engine-owned six-state enum (Act-2 U7) — an essentials-floor verdict + a lifestyle-surplus verdict ("your essentials are safe in 10 of 10 futures; your full lifestyle holds in 7"). The negative-tier copy is **action-first / Kitces** ("in the other 3 you'd trim discretionary, not go hungry"), and the non-color signal grammar carries each tier's state independently. State-*selection* stays engine-owned in `confidence.ts`; `TwoTierHeadline.tsx` is a pure presentation composition of two already-tagged states. **Degenerate collapse:** when the full track is byte-identical to the essentials track (no discretionary present), `TwoTierHeadline` renders the **single-metric** statement verbatim, not two identical tier verdicts — this is precisely what keeps the reduce-to-spine headline byte-identical.
- **Spending shape is user-set, never solver-recommended:** a go-go-years front-load is a user-set per-year multiplier on the **discretionary** track only (the solver optimizes *funding*, not how you live). U9 owns the shape control and surfaces its honest consequence on the surplus tier; it never proposes a shape.
- **Reduce-to-spine invariant (the budget's golden anchor):** a budget that is a **single lifelong essentials line equal to the first-answer total-spend figure** must compile to the *exact* single per-year spending vector the first answer fed the engine → the **saved seed/headline is byte-identical** to the single-total-spend answer. The single-total-spend answer is the **degenerate budget**; itemization is the deepening, never the on-ramp (R5/R8). Migrating single-total → itemized preserves the seed.
- **Survivor-spending composition (the seam to the survivor floor — R17, the product's emotional core).** The survivor-spending ratio (the Act-1 U1 default) is applied **per-path at the sampled first death** to the compiled tracks: it scales the **discretionary** track and the **discretionary portion of essentials only** — **sticky survival essentials (the survivor's healthcare-gap / single-enrollee Medicare premium, housing, property tax) do NOT scale by the couple ratio**, so the Tier-1 survivor floor is never silently understated. **Degenerate-inert:** in the degenerate single-essentials-line budget the composition is inert (the ratio falls back to flat-on-total) so the survivor-year vectors stay byte-identical. The composition lives in `budgetToSpending`, not `simulate`, and is surfaced as an R7-editable assumption (Unit 12); a simpler ratio-on-total reading is the documented fallback if the cold-read finds the split too fiddly.
- **R19 (contract #7):** non-negative `annualAmount`; `endYear ≥ startYear`; a zero-essentials "everything discretionary" budget is **coherent** (Tier-1 floor trivially safe) but **warned** calmly. Reuse Act-2 U5's R19 grammar.

**Test scenarios.**
- Happy path: a multi-line budget (lifelong essentials + a 20-yr travel discretionary item) compiles to two per-year vectors; the headline reads two tier-verdicts; the discretionary track drops out after year 20 (time-box honored).
- Edge (reduce-to-spine): a single lifelong essentials line = the first-answer total → the compiled vector is **byte-identical** to the single-total-spend answer under the same seed, the survivor-spending composition is **inert** (flat-on-total), and the rendered headline is the **single-metric** form, not a doubled tier pair (the budget's golden anchor).
- Edge (tier-ordering monotonicity — golden invariant): for any budget, Tier-1 (essentials) `X-of-10` ≥ Tier-2 (full) `X-of-10`, asserted **path-for-path** on the shared draw set (every full-success path is an essentials-success path). The two tracks are distinct trajectories with different MAGI, so this is not assumed — it rests on a three-link proof chain: **(1)** essentials-only spend ≤ full spend every year; **(2)** on identical CRN draws, depletion is monotone in spend (less spent ⇒ never-lower balances); **(3)** the per-track healthcare-gap dollar is itself monotone in spend (lower spend → lower MAGI → ≥ PTC → ≤ net premium → ≤ cash need). The three links compose. **Honest caveat:** if any link can break (a cliff/CSR branch where a *lower* MAGI crosses into a regime that *raises* a different cost), the invariant is **narrowed to the region where it provably holds and the exception is documented**, never asserted universally and left to block a correct engine. Pair the subset-assert with a presence companion that ≥1 path stressed the discretionary gap (`burned/027`); a planted budget whose two passes diverge inside the proven region fails loud.
- Edge (survivor floor): on paths past the sampled first death, Tier-1 essentials reflect the ratio per the composition rule — sticky essentials are **not** scaled by the couple ratio, while discretionary is.
- Edge (real convention): a constant-real multi-year line compiles to the engine's expected **real** per-year vector, not a nominally-flat one.
- Edge (two-tier split over one draw): essentials safe in 10/10 while full lifestyle holds in 7/10 — both read off the **same** path population/draw set (assert identical normals consumed), not two sims.
- Edge (income-dependent healthcare-gap line): the gap line's dollar comes from the overlay (Unit 11), not a typed amount; removing the gap line does not zero a typed value.
- Edge (zero-essentials coherent-but-warned): an all-discretionary budget yields a trivially-safe floor with a calm warning, never an error/indeterminate.
- Error (R19): negative amount and `endYear < startYear` are caught calmly inline, no falsely-confident answer.
- Integration: editing a budget line in the sharpen loop (Unit 12) recomputes both tiers through `memoryModel` under the unchanged seed; the spending-shape multiplier moves only the surplus tier.

**Verification.** A user builds a real itemized, time-boxed budget; the answer reads as two honest tiers (safe floor + lifestyle surplus) over the same state set; a single-total budget reproduces the first answer byte-identically; spending shape is user-set with honest consequences, never recommended. **Passing the N=1 cold-read on the two-tier headline (relief-with-honesty, not two competing verdicts) is an Act-3 exit condition** (contract #8).

**Feeds forward to Act 4.** The two-tier essentials/surplus split **is** the lexicographic objective's two tiers — essentials = the Tier-1 floor, discretionary = the Tier-2 surplus the solver optimizes the *funding* of. The budget is **read-only input** to the solver (it never moves a budget line). See [docs/plans/4-recommendation.md](4-recommendation.md), contracts #4 and #8a.

- **R8 honestly — "sharpens," not unconditionally "tightens" (band-narrowing is mechanically true for only ONE edit class):** **(a) CONFIRM/NARROW** an epistemic default (replace a wide conservative assumption with a more confident one) → the band genuinely **narrows** (R8's rewarding case); **(b) OVERRIDE a value** (real higher spending, a longer longevity table, a higher σ) → the band **shifts and may widen**, and the verdict can worsen — framed calmly as "a truer picture," never a failure. **"Monotonic, no jitter" is the SEED-stability guarantee** (same seed → no sampling noise), NOT a promise every edit narrows.
- **This unit seats the stateful sticky-rounding (the seam Act-1 U1 + Act-2 U5 handed forward).** It adds `lastDisplayedHeadline` / `lastDisplayedDollar` / `lastState` to `memoryModel` and the sticky rule, applied to edits of an **already-complete** answer: **(a) two distinct margins** — headline + `lastState` (copy-state / verb-tense) gate on the **band-edge** margin; `lastDisplayedDollar` gates on the **independent display-rounding-step** margin (conflating them is the "one sticky while the other flickers in one sentence" failure); **(b) notify-once write ordering** (`burned/017`) — one recompute writes all displayed slices + the `lastDisplayed*` stickiness **before** the single notify; **(c) lifecycle** — the baseline is captured at the **resolve→verdict transition** (free-moving while indeterminate); `lastDisplayed*` are **session-only, NOT persisted**, re-seated on re-entry from Unit 13's deterministic recompute, so the first post-unlock edit is sticky against the exact number the user last saw and a genuinely-moved answer (staleness) is never held to a stale screenshot value. (Why the stateful stickiness lives here, not in pure `confidence.ts`: [docs/architecture.md §9](../architecture.md).)
- **Honest about the epistemic vs aleatory floor.** Sharpening narrows input uncertainty but cannot narrow market randomness — copy for "you've hit the floor, more precision won't narrow it" and for "sharpening revealed bad news" (real higher spending worsens the verdict — handled calmly). The worsening transition carries the **non-color signal grammar** (word + shape + dollar magnitude, never a hue shift — the reader is color blind) and is a cold-read subject (contract #8). **Floor detection (decided, MVP-minimal):** a **Unit-12-local heuristic** — when an edit collapses an input's uncertainty toward a point and the band-width change is below a defined threshold, surface the floor copy. The alternative (a `confidence.ts` inputs-vs-returns decomposition emission) would re-open Act 1 and is deliberately NOT chosen for the MVP; escalate only if the cold-read finds the heuristic too coarse.
- **Escape hatch:** jump straight to any assumption without walking the guided path (R6), reachable even while the answer is **indeterminate** — the sticky seam applies only to a complete answer, so an escape-hatch edit on an indeterminate answer has defined (non-sticky) behavior (Act-2 U5's indeterminate render).

**Test scenarios.**
- Happy (narrow): confirm a wide conservative default with a more confident value → band **narrows**; same seed → no jitter.
- Edge (override): enter higher real spending → band **shifts/may widen** and the verdict can worsen → calm "a truer picture" copy, not a cheerful tightening (proves the two edit classes are distinguished).
- Edge (aleatory floor): an edit whose band-width change is below the floor threshold → the floor copy appears; a normal edit does not falsely trip it.
- Edge (sticky two-margin split): an edit crossing the **dollar** step **without** crossing a **band edge** updates only the dollar (headline + verb-tense hold); the mirror case holds the dollar while the headline crosses (margins wired separately).
- Edge (notify-once): a near-margin edit yields either both-stable or both-changed in one frame, never a one-frame mixed pair (`burned/017`).
- Edge (every new assumption present + editable): budget lines, sequencing policy, conversion, tax-payment-source, SLCSP, enhanced toggle, HSA, survivor-SS step-down, survivor-spending ratio, death-order are all reachable and editable (R7 completeness).
- Edge (required-fact edit): clearing savings returns the answer to **indeterminate** with Act-2 U5's indeterminate copy.
- Integration (escape hatch): sets an assumption directly, consistent with the guided path; an escape-hatch edit on an indeterminate answer is defined (non-sticky).
- Integration (shared assumption single-source): editing death-order / survivor-spending recomputes **both** the spine and any open control under the unchanged seed (contract #3).

**Verification.** Every assumption behind the answer — including the budget, both controls, and the healthcare inputs — is reachable and changeable within one interaction; edits move the answer stably (seed-stable, no jitter), narrowing on precision and shifting honestly on a correction; the dollar and headline never flicker against each other. **Passing the N=1 cold-read on the bad-news sharpen transition (honest recalibration, not a gut-punch) is an Act-3 exit condition.**

**Feeds forward to Act 4.** R7 gains weight under recommend-second: a recommended strategy must expose its inputs **and its reasoning** for the user to approve it. The assumption panel + escape hatch built here are the substrate the recommendation surface reuses to make every recommendation input editable. See [docs/plans/4-recommendation.md](4-recommendation.md), Unit 16.

## Unit 13 — Returning-user re-entry + per-surface staleness

*The returning user and the surviving spouse come back to a re-derived saved answer; per-surface staleness across the tax, healthcare, and budget clocks — including the date answer's vintage clocks.*

**Goal.** A calm re-entry that shows the saved answer (re-derived, not a replayed string) with honest, per-surface staleness awareness across the tax, healthcare, and budget clocks — and routes the surviving spouse back in.

**Requirements.** R4 (the saved answer surface), R8 (re-entry, not re-intake), R15/R16/R17 (unlock + the survivor recovery door + the two-person posture). Text in [docs/product.md §7](../product.md).

**Dependencies.** Act-1 U4 (the unlock/recovery/migration mechanisms it consumes — [docs/architecture.md §7.3](../architecture.md)), Act-2 U5 (`memoryModel` — re-entry re-derives through it), Act-2 U7 (the statement surface), Unit 9 (the budget clocks), Unit 10 (the controls are bracket-/RMD-vintage-sensitive; reads the tax-vintage stamp Unit 10 writes), Unit 11 (reads the healthcare-vintage stamps Unit 11 writes), Unit 12 (a confirmed balance/split change routes into the sharpen loop).

- Test: `src/ui/__tests__/reentry.test.tsx`, `src/store/__tests__/staleness.test.ts`

**What it delivers.**
- **Unlock surfaces ALL of Act-1 U4's outcomes — including the survivor's primary door. ⚑ STATUS: the unlock/recovery/restore flows themselves SHIPPED IN U8 (2026-07-02)** — `UnlockScreen`/`RecoveryFlow`/`RestoreFlow` are live-verified, covering: **wrong-passphrase** → calm retry, no lockout; **data-damaged** → "use your export" restore; **no-vault / post-eviction** (Safari ~7-day) → restore as a first-class entry; and the **in-place recovery-passphrase unlock** — forgotten daily passphrase + intact vault → unlock via the **second user-chosen recovery passphrase** (the U8 rework; the BIP-39 phrase is gone) → set a new daily passphrase behind the **MANDATORY blocking gate** (no write path reachable until the new `passphraseWrap` is re-minted, fresh salt+IV — or the survivor could save while the on-disk wrap still encodes the forgotten passphrase, silently degrading the vault to recovery-credential-only access). *The recovery door is the surviving spouse's primary way back in — the flow the product exists to serve.* **U13's remaining work is the RE-ENTRY layer on top of those shipped doors:** re-derive-at-unlock, the per-surface staleness clocks, and the balance-drift confirm below. (The synchronous lock authority / write-gate conjunction is owned by [docs/architecture.md §7.3](../architecture.md).)
- **Show the saved confidence statement by RE-DERIVING it at unlock** (not replaying a stored string): `memoryModel` recomputes the saved model under its **persisted seed** → byte-identical to the saved displayed value → and this **re-seats Unit 12's session-only sticky baseline** so the first post-unlock edit is sticky against the exact number the user last saw. **Re-PRESENTATION uses the SAVED fixture vintage** (so the number matches what the user screenshotted) with the staleness flag as the honest signal; any **re-RUN** (entering the sharpen loop or re-opening a control) recomputes under the **CURRENT** fixture and explicitly states the assumptions were updated — never silently stale, never silently changed. **Forward hand to Act-4 U17:** once a *recommendation* can be saved, a stale saved recommendation is a real **executed action** and its staleness must **invert to re-solve under current fixtures** — "the action we recommended may no longer be advised," not "your number drifted." In Act 3 only the spine + the manual-control results are saved, so the re-present-under-saved-vintage rule holds — a saved **manual-control** result stays a what-if (re-presented under its saved vintage), and **only a saved *recommendation* inverts** to re-solve-under-current (the boundary the reset turns on: a saved control what-if ≠ a saved executed action); U13 lays the per-surface clock groundwork U17 inherits (see [docs/plans/4-recommendation.md](4-recommendation.md), contract #8b).
- **Per-surface multi-clock staleness (contract #6 — a clock exists iff the engine consumes a year-stamped parameter, and gates only its surface):**
  - **wall-time since last edit** + the **app methodology-default vintage** (new conservative-return/longevity defaults shipped since save AND never user-overridden → a calm "we've updated our default assumptions" note; user-overridden assumptions are immune) → gate the **spine verdict**.
  - **tax-table vintage** (the bracket/standard-deduction fixture, carrying its **OBBBA-2025 legal-basis as provenance** so a statutory change reads as a vintage bump, not inflation drift) + the **RMD-age rule** (birth-year-derived; the legislated 73→75 step in 2033) + the **senior-bonus-deduction sunset** (a calm note when a pre-2029 answer is viewed in/after 2029) → gate the **controls/lever only** (the spine is tax-blind). *(SS provisional-income thresholds are frozen/not-indexed, so they have **no clock**.)* A saved control result is flagged stale when **any** of {bracket vintage, RMD-age rule, senior-bonus-deduction sunset} has moved; when stale and the user **opens** the control, the surface shows the vintage at the control ("computed with [year] tax brackets") and does not present the survivor-cliff figure as current — `staleness.ts` exposes a queryable "tax-table stale" flag.
  - **Healthcare vintages (net-new) → gate the healthcare surfaces:** the **ACA legislative status** (the load-bearing clock — cliff-on vs enhanced; the re-verify-at-build status), the **applicable-% table**, the **IRMAA brackets**, the **Part B premium**. A saved healthcare cost is flagged stale when any has moved; the ACA-status clock is the most consequential (it can flip the whole pre-65 calculus). The status note is dated and honest.
  - The **undetectable balance-drift clock** (real portfolio drifted; no aggregation): a calm **"is this still your balance?"** confirm before presenting the saved verdict as current. **For an accounts vault it confirms the per-bucket split** (pre-tax / Roth / taxable / **HSA**), not just the total — the pre-tax pool's drift relative to Roth changes the control calculus more than the total does; a changed split routes into the **Unit-10 mini-intake**, a changed total into the **Unit-12 sharpen loop**. SS staleness is folded in as "are these still your benefit amounts?" (SS benefits are user-entered, not a year-stamped fixture — no separate clock).
  - **Budget time-boxed clocks (net-new) → gate the budget surface:** a budget line whose **window has advanced** since save (a travel item now past its `endYear`; the pre-65 healthcare-gap item once a spouse has reached 65) gets a calm **re-confirm** ("your travel budget was set to end last year — is that still right?") rather than silently spending past its window.
- **The date answer joins the per-surface staleness/re-entry machinery (the most time-denominated answer in the product would otherwise have no clock):**
  1. **Fixture-vintage clocks (per contract #6), gating the DATE surface:** the **contribution-limit table vintage** (answer-relevant, not intake-only: the per-runway-year catch-up step-down shapes the projected stream, so a vintage move shifts the date) and the **ticker-blend / TDF static-snapshot vintage** (a stale snapshot silently misstates the household stock weight).
  2. **User-entered re-confirms ride the existing balance-drift confirm class, NEVER vintage clocks** (the SS precedent above): account values / contributions / salary join the "is this still your balance?" confirm; the entered **ACA quote** gets an **"is this still your marketplace quote?" plan-year re-confirm** (marketplace premiums reprice annually — user-entered, so a confirm, not a fixture clock).
  3. **The date re-presentation rule:** re-presentation renders the **wall-time-stable calendar label** (`startCalendarYear + Y` — byte-identical under the saved vintage) and **RE-DERIVES the relative "~N years out" framing from current wall-time** — never a replayed relative string (the date answer decays with pure time passage — ages advance against the saved t=0 anchor — so a sufficiently old save routes to **recompute** via this unit's existing re-run rule, never re-presents as current). Act-4 U17's inverted stale-rec rule is **unchanged** (a saved *recommendation* still re-solves under current fixtures; the date is an answer, not an executed action).
- **Absent-stamp default:** a spine-only vault (saved before the stamps existed, or by a user who never opened a control) has no tax/health stamp → `staleness.ts` treats an **absent** stamp as **"not applicable"** (no false stale), never "infinitely stale." Stamps live on the model so staleness is computable offline.

**Test scenarios.**
