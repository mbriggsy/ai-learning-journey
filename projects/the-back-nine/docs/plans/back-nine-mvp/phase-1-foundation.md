# Phase 1 — Foundation

**Goal.** Stand up the buildable PWA skeleton, the deterministic Monte Carlo engine validated against known-good reference cases, the **two-control substrate** every recommendation will stand on (pluggable withdrawal-sequencing policy + the tax-and-accounts overlay), the **income-aware healthcare overlay** that makes ACA-PTC / IRMAA / HSA visible across the Medicare line, and the encrypted local store that makes the at-rest promise provable. Nothing user-facing ships in this phase — but the engine's answer must be *right*, the overlays must reduce **byte-identically** to the validated spine when off, and the store's guarantee must be *proven* before any surface consumes them.

**Why this is Phase 1.** The two hardest, highest-risk surfaces — *correctness* (a calm-but-wrong number, and later a calm-but-wrong **recommendation**, fail the bar worse than no tool — R25) and *trust* (R16: provable before spoken) — are foundations everything else stands on. The thesis reset transferred the load onto honesty + engine validation, so the substrate the solver will later search (sequencing policy, tax overlay, healthcare overlay) is built and validated **here, before any control surface or solver exists** — the controls (P3) and the solver (P4) *drive* this substrate; they never re-implement decumulation. U1–U3 are independent of U4 (parallelizable) and have zero monorepo precedent, so they carry the most risk and must be locked first.

## Phase-1 cross-cutting contracts

*These contracts span the units below (six at ratification; **#7 added by the 2026-06-08 accumulation amendment**). They are named once here so a reader sees the seams, then enforced in the unit that owns each. Several are seams later phases (Controls, Solver) explicitly consume; this section is their producer.*

1. **The determinism / CRN contract (owned by U1; consumed by U2, U3, every P3 control, and the P4 solver).** The engine is a pure function of `(params, seed)`. The seed is a single integer in `mulberry32`'s signed-32-bit domain, **injected by the caller** (never generated inside `src/engine`), and stored as a first-class field of the saved model. The **draw schedule** — the count and ordering of normal draws per path/year — is a pure function of the path/horizon **dimensions only, never of the financial inputs**: the normals matrix is allocated to the **maximum** cohort horizon up front and indexed by **absolute year**, and the Box-Muller transform is **stateless** (no cached spare — the textbook cached-spare pattern makes the Nth normal depend on call parity, silently desynchronizing two CRN candidates). A fixed seed therefore reproduces a byte-identical matrix of normals **regardless of which input changes** — so financial / longevity inputs select *which* draws are consumed, never *how many* are generated or their order. The **CRN-safe regime-shifters** — the inputs that change *which* draws are read but never the schedule — are an enumerated, exhaustive set: **{the joint→survivor two-regime boundary, the earned-income bridge, the tax-and-accounts overlay (U2), the healthcare overlay (U3), the death-order conditional filter}**. Each earns concrete CRN tests in its owning unit. The seed must survive U4's encrypt → persist → decrypt round-trip **bit-identically**. **Seed-stability** (same inputs + same seed → identical raw distribution and identical raw rounded headline) is U1's pure guarantee **on a single JS engine** — byte-identical normals + raw distribution hold within one browser build, but plain-TS transcendentals (`exp`/`log`/`pow`) are **not** bit-identical across engines, so the *displayed* `X of 10` is made cross-engine-robust by `confidence.ts` **quantizing the headline statistic to a coarse grid before the band-edge decision** (below), not by relying on bit-identical floats; **rounding hysteresis** is a *stateful* property (it needs the prior displayed value) and lives in the P2 recompute orchestration (`memoryModel.ts`), **not** in pure `confidence.ts`. This is the structural fact that lets the P4 solver rank K candidate strategies on **identical futures** — signal, not RNG luck.

2. **The single-shared-market-draw rule (owned by U1; enforced in U1/U2/U3; now more load-bearing).** **All account buckets — pre-tax / Roth / taxable / HSA — share ONE market-return draw per simulated year** (the same normals stream as the spine). Buckets differ **only** in tax treatment, never in return assumption. Splitting the portfolio into buckets tempts an implementer to shock each bucket with its own draw — which would multiply draws-per-year, change the draw-schedule **dimension**, and silently break CRN. Per-bucket draws are **forbidden**. Tax / RMD / conversion / healthcare effects are all deterministic **post-draw arithmetic**. This makes "no asset-location" a *structural* guarantee (not a copy promise — the chapter-two asset-location capability, if ever wanted, must be a *deterministic per-bucket tilt on the one shared draw*, never a separate draw), and it is what lets the solver rank candidates on identical per-path returns.

3. **The shared per-year-cash-term transform seam (owned by U1; populated by the bridge in U1, the tax overlay in U2, the healthcare overlay in U3).** There is **one** per-year update function the validated decumulation uses; everything else is a **deterministic transform of the cash-flow term, indexed by absolute year, consuming ZERO random draws**, fed into that same function so within-year order-of-operations (withdrawal vs return application vs rebalance) is shared by construction and can never drift between the spine and an overlay. The transforms compose: the **earned-income bridge nets the withdrawal DOWN** (`netWithdrawal = max(0, spending − earnedIncome)`, never crediting a dead earner, never contributing surplus back); the **tax overlay grosses it UP** (tax + RMD + conversion increase the cash needed); the **healthcare overlay grosses it UP further** (net ACA premium / IRMAA surcharge are spending). **The reduce-to-spine golden invariant binds every transform:** when an overlay is OFF it reduces **byte-identically (same seed) to the Trinity/Bengen-validated decumulation distribution** — the golden cases are **never** perturbed. Each unit states its own exhaustive OFF condition and owns the byte-identical test.

4. **The in-memory → encrypted-persistence seam (owned by U4; consumed by P2 intake).** Nothing touches disk until the user saves and sets a passphrase. This is enforced **structurally** — the store exposes no write path reachable before a key exists — not by caller discipline. At rest, the AES-GCM ciphertext (protected by the PBKDF2-600k passphrase derivation) guards the disk; the cleartext model held in JS memory during an unlocked session is guarded by U0's CSP. The P1 store proves the seam at its own layer; P2 adds the end-to-end intake assertion. (Gates R15/R16.)

5. **The R19 split (engine numeric half owned by U1; intake semantic half handed to P2).** The **engine** guards its own numeric domain — no `NaN`/`Infinity` escapes a percentile; degenerate-but-coherent inputs return an honest extreme (or the defined indeterminate state), never a crash. **Semantic plausibility** (retirement age < current age, spending beyond any plausible portfolio, the control/budget/health input surfaces) is the R19 **intake / control-layer** concern owned by P2/P3. Neither layer assumes the other validated. The control surfaces (P3·U10 conversion clamp, P3·U9 budget, P3·U11 health inputs) are downstream R19 surfaces this contract names but does not own.

6. **The canonical year-keyed constants module (owned by U0; read by U1/U2/U3, the plan, every test, and the copyGuard allowlist).** Every dated tax/health constant — 2026 brackets, the standard deduction + age-65 addition + senior-bonus, RMD birth-year ages, SS provisional-income thresholds, ACA applicable-% + FPL cliff + SLCSP handling, IRMAA brackets + 2-yr lag, HSA limits, Part B premium — lives in **one** year-keyed module `src/engine/constants/`, each figure carrying its **source citation** (`findings §Strand 5` / the healthcare doc) and a **`directional-until-pinned`** marker (and, for the ACA legislative item, a **re-verify-every-build** gate). Plan, engine, tests, and the copyGuard allowlist all read this module — a constant is **never re-typed** (`burned/057,061,063`: one canonical table, no hand-duplication). The reduce-to-spine invariant means the spine itself reads **no** constant from this module (it is tax-free) — the module is consumed only by the overlays, so a constants change can never perturb a golden case.

7. **The signed contribution-inflow on the ONE continuous timeline (added by the 2026-06-08 amendment; owned by C2; consumed by the date-search C3 and the P2 intake reshape D1; decision record: the accumulation plan §1/§2/§7).** The accumulation phase extends the **same** absolute-year timeline contract #1 owns (t=0 = today; the earned-income bridge already occupies the working years): a per-bucket **contribution inflow** lands in existing working-year slots — **never** a separate pre-phase draw stream, never a `maxHorizon`/dimension change (contract #1 holds by construction; CRN across candidate date-offsets follows by the same argument as the solver's K-candidate CRN). **`stepYear` is the ONE crediting owner** (contract #3): the contribution is credited **END-OF-YEAR at face value** (a contributed dollar earns no growth in its arrival year — the conservative direction; full-year crediting would overstate the retirement-onset balance → a falsely-early date, the calm-but-wrong-optimistic sin), and the overlay fold is **AFTER the bucket-scale, at face value**, with the per-person pretax-ledger owner credit. **The reduce-to-spine OFF condition is PRESENCE-keyed:** the accumulation construct **ABSENT** from params ⇒ byte-identical to the spine — asserted on **both** the MC `simulate` path AND the historical/Trinity backtest path; a **zero-valued-but-constructed** run is deliberately **NOT** byte-identical (the §7 working-year withdrawal clamp is live whenever the construct is present — presence, never value, owns byte-identity); the empty phase (`Y == 0`) consumes zero extra draws and is byte-identical at the same dimensions.

- [ ] **Unit 1: Monte Carlo engine core + validation contract + sequencing substrate** *(the correctness unit)*

**Goal:** A pure, deterministic TypeScript Monte Carlo engine that models a married couple's joint-and-survivor longevity, decumulates through a **pluggable per-year drawdown policy** (the second control's substrate), and emits a distribution the UI reads as "X of 10" + the dollar adjustment — validated via **two distinct modes**: a deterministic historical-sequence backtest (a self-consistent oracle + a directional check on the published Trinity/Bengen figures) and the Monte Carlo path (asserted as a band strictly below the historical anchor). U1 owns the CRN seam, the shared cash-term transform seam, longevity-with-survivor-identity, the earned-income bridge, and the pluggable-policy substrate that U2 (tax) and U3 (health) hang on and that the P4 solver searches.

**Requirements:** R3 (distribution of futures), R9 (sequencing-as-a-control substrate), R14 (plain-language reading), R19 (engine's numeric-domain half), the correctness success criterion.

**Dependencies:** U0.

**Files:**
- Create: `src/engine/rng.ts` (vendored mulberry32 + stateless Box-Muller), `src/engine/longevity.ts` (cohort joint-survivor, retains per-path survivor identity), `src/engine/sequencing.ts` (the named drawdown policies — the second control's substrate), `src/engine/simulate.ts` (MC spine + pluggable policy + the shared cash-term seam), `src/engine/historical.ts` (the deterministic backtest oracle), `src/engine/confidence.ts` (distribution → X-of-10 + dollar + outcome-state, pure), `src/engine/engine.worker.ts` (Comlink boundary), `src/shared/model.ts` (the single plaintext shape + the outcome-state enum)
- Create: `src/engine/reference/` (Trinity/Bengen fixtures — **committed**, generated via cFIREsim-open on a pinned dataset; self-consistent + directional, not published-exact)
- Test: `src/engine/__tests__/{rng,simulate,longevity,sequencing,confidence,historical,worker}.test.ts`, `src/engine/reference/__tests__/validation.test.ts`

**Approach:**
- Port `mulberry32` + the CSPRNG/seeded split from burned's `rng.ts` (**vendored, not cross-imported**); add a **stateless** Box-Muller normal transform (absent in burned): consume two uniforms per draw and **do not cache the spare** across calls. **The engine never generates its own seed:** `crypto.getRandomValues` is called by the caller (the P2 `memoryModel` orchestration layer) and the 32-bit seed is **injected** into `simulate`/the worker; `src/engine` reads no entropy source, clock, or environment (enforced by the U0 lint). A saved scenario stores its seed in `model.ts`; the seed must round-trip through U4's encryption bit-identically (contract #1).
- Lognormal sim with **log-drift μ = arithmetic_mean − σ²/2** (the #1 MC bug is naïve arithmetic compounding — findings §Strand 4). Conservative real-return + inflation defaults (Pfau/Kitces ~3–3.5% real in high-CAPE), all user-overridable, all read from the methodology-default layer (not the tax constants module). **The σ in the σ²/2 correction is the *log-return* σ, not the simple-return σ** (they differ at equity vol); the engine seam **declares whether `arithmetic_mean`/`sigma` arrive in simple- or log-space and converts consistently** — silently mixing a simple-return mean with a log-return σ biases every percentile (a second-order sibling of the naïve-compounding bug).
- **CRN seam (contract #1):** `simulate` allocates its normals matrix to the **maximum** cohort horizon up front, indexed by **absolute year**, so the draw schedule is a pure function of path/horizon **dimensions only**. The enumerated CRN-safe regime-shifters (survivor boundary, bridge, tax overlay, health overlay, death-order filter) select *which* draws are consumed, never *how many* or their order. Two parameter sets under one shared seed consume identical normals path-for-path — the substrate the solver ranks K candidates on.
- **Joint-and-survivor longevity from COHORT tables (not period):** `P(last survivor alive) = pₓ + pᵧ − pₓ·pᵧ`. **HARD requirement (contract #1):** longevity must **sample per-path, per-spouse death years AND retain which spouse dies first per path** (or expose per-path death-order). The closed-form mixture **alone does NOT retain survivor identity** — and the death-order conditional filter (P3·U10 / P4) is unbuildable without it. SSA cohort source = `table4c7.html` (explicitly **not** the period table `table4c6.html`). Two-regime horizon (joint → survivor): survivor-SS step-down (keep larger benefit) + survivor-spending ratio. **The survivor-spending ratio is grounded, not guessed** — because it scales the survivor's spending and so rides the **Tier-1 survival floor** (the solver's hero metric), it must be **grounded to a citable retirement-research range** (e.g. the Blanchett survivor-spending / "two-thirds-to-three-quarters" literature), **source-stamped like every other constant** with a `directionalUntilPinned` marker, and ships a defensible default near **~75%**. It stays **editable**, but its **dangerous direction is documented**: too *low* understates the survivor's need — the unsafe direction for the survivor product — so a low edit carries a calm note, and the default is never a silent un-sourced number under the hero metric. Never a fixed "to-age-90". **The couple survival figure is derived from the two *sex-specific* cohort curves through the formula — never a hardcoded couple number:** a single symmetric individual rate is arithmetically inconsistent (0.25 + 0.25 − 0.0625 = 0.4375, not the ~0.53 a sex-differentiated pair yields), so the longevity test asserts *internal consistency* (couple prob = the formula applied to the two shipped curves), not a constant. Independence is assumed (real spousal mortality is positively correlated), which **mildly overstates** last-survivor probability — acceptable because it errs *safe* for a survival floor, documented so it isn't mistaken for precision.

**Approach:**
- **The overlay is the structural sibling of the earned-income bridge (contract #3):** a per-year **deterministic transform of the cash-flow term, indexed by absolute year, fed into the SAME per-year update function**, consuming **ZERO** random draws — CRN-safe by the bridge's identical argument. The bridge **nets down**; the overlay **grosses up** (tax increases the cash needed; a conversion adds a tax bill paid from the taxable bucket).
- **Per-person buckets: pre-tax / Roth / taxable.** Ordinary-income tax on pre-tax withdrawals + RMDs + the conversion; tax-free Roth growth; capital-gains/qualified-dividend stacking from taxable withdrawals (§Strand 5 IN-scope). **All buckets share the ONE existing per-year market draw (contract #2)** — buckets differ only in tax treatment, never return assumption; tax/RMD/conversion are deterministic post-draw arithmetic. This is what makes `bracket-fill` (U1's tax-aware policy) computable and structurally forecloses asset-location.
- **RMD age is birth-year-derived, NEVER a flat 73** (§Strand 5, SECURE 2.0): 72 (≤1950) / 73 (1951–1959) / 75 (1960+, effective 2033). Per person, keyed off the model's birth-year field (derived in P2 intake from calendar year − age; a ±1yr birth-month approximation is sufficient for the discrete threshold). RMD = the IRS Uniform Lifetime Table divisor on the prior-year-end pre-tax balance. RMD is a **forced-distribution mechanic, not a tax** — so "taxes off" alone does **not** silence it (see the OFF condition). **The Uniform Lifetime Table is not universal:** when the sole beneficiary is a spouse **more than 10 years younger**, the IRS Joint Life & Last Survivor table (Pub 590-B Table II) applies and yields a *smaller* RMD — flat Uniform Lifetime overstates forced income for the age-gapped couples this product explicitly models. And **the RMD is non-convertible** — past RMD age it must be distributed as ordinary income *first* and cannot be satisfied by (or reduced by) a Roth conversion; the manual control (P3·U10) and solver (P4·U15) consume this as a hard legality constraint.
- **SS provisional-income taxation as a per-year bounded FIXED-POINT.** Taxable SS depends on provisional income, which depends on the year's other ordinary income — including the **gross-up** withdrawal needed to cover spending + tax, which depends on the tax: a circularity. Resolve it per simulated year as a bounded fixed-point — **iterate provisional-income → taxable-SS → tax → gross-up → re-converge** to a stable value (a few passes), deterministic, reading **zero** draws (CRN-safe). The convergence rule is pinned in the engine seam (iterate-to-stable or a fixed small pass count). The MFJ/single thresholds are **frozen, not inflation-indexed** (§Strand 5) — constants with **no staleness clock**.
- **MFJ→single switch at the sampled first death = the joint→survivor two-regime boundary U1 already models** (NO new boundary; the empty-nest retired couple gets **no QSS grace** — files single the year after the first death, §Strand 5). The survivor's same real dollars fall into ~half-width single brackets with ~half the standard deduction — the "tax cliff" that is the recommendation's emotional headline story (rendered in P3/P4).
- **Standard deduction + age-65 addition + senior-bonus** (the senior-bonus carries its MAGI phase-out and its **2028 sunset** — a guaranteed-to-go-stale provision; §Strand 5). All figures via the constants module; none inlined.
- **GOLDEN INVARIANT — reduce-to-spine, with an EXHAUSTIVE OFF condition (contract #3).** The overlay reduces byte-identically to the spine when, and only when, **buckets collapsed to one pool AND conversion = 0 AND ordinary-tax off AND RMD-inert** (no forced distributions). RMD-inert is the fourth clause **not** because an active RMD perturbs the total — under contract #2 (one shared draw, no asset-location) a forced pre-tax→taxable relocation moves money between two *identically-growing* buckets and is provably total-neutral with tax off — but as a **clean-fixture guarantee**: it keeps the golden anchor unambiguously the spine and the auxiliary ledger trivially the single pool. An active tax-off RMD is exercised *separately* and asserted at the **ledger** level; only the M3 ordinary-income tax makes an RMD change the total. Under all four, `netWithdrawal == spending` and the terminal-value distribution is **byte-identical (same seed)** to the Trinity/Bengen-validated decumulation — the golden cases are never perturbed (the direct analogue of the bridge's `earnedIncome=0` invariant). The overlay is ON only when a control (P3) or the solver (P4) turns it on.
- **Both arms / both candidates run at identical tax fidelity** — there is no tax-blind arm. The only difference between a "with-conversion" and "without-conversion" candidate is the conversion event; both decumulate through the overlay. (A tax-blind delta is **sign-inverted** — it sees only the cash drain of paying conversion tax, so every conversion looks worse. This unit exists to prevent that.)

- **Two distinct MAGI calculators — do NOT reuse one number** (healthcare doc §4a):

  - **IRMAA-MAGI** = AGI + tax-exempt interest, **NO SS add-back**.

- **Pre-65 ACA-PTC as a per-year FIXED-POINT (the same shape as U2's SS-tax fixed-point).** `PTC = max(0, SLCSP_benchmark − applicable_pct(FPL%) × ACA-MAGI)`; **`allowed_PTC = min(PTC, enrolled_premium)`** and **`net_premium = max(0, enrolled_premium − allowed_PTC)`** — floored at zero, never cash back; `gross_wd = spending + taxes + net_premium`; `MAGI = f(gross_wd, other_income)` — MAGI on both sides. **Enrolled premium and the SLCSP benchmark are two separate inputs** (PTC keys off the benchmark; the bill is the enrolled plan — a sub-benchmark Bronze plan must not yield PTC > premium = negative net); if the MVP simplifies to enrolled = SLCSP, state it so `net_premium = applicable% × MAGI` is the documented assumption. The per-MAGI-dollar clawback is the **applicable % only on the flat 300–400% FPL band (~0.10 in 2026)** and is **larger in the sliding bands** (`p + I·dp/dI`, ~13–16%); the funding loop adds a tax gross-up (effective factor ≈ clawback ÷ (1 − marginal_rate)) — still a contraction < 1, so it converges, **but make a bisection on a monotone funding-gap residual the PRIMARY solver** (the map is non-smooth: the `max(0,·)` floor, the cliff, band-boundary kinks, the SS-torpedo and LTCG-stacking kinks). Iterating a MAGI↔PTC circularity is IRS-precedented — cite **Pub 974 / Rev. Proc. 2014-41 only as precedent that iteration is legitimate**, NOT as the method that solves *this* loop (they solve the distinct SEHI-deduction↔PTC loop).
- **DETECT-AND-BRANCH the 400% FPL cliff explicitly** (healthcare doc §4b): a naive iterator **oscillates** across the cliff (one dollar over → all PTC lost). Detect the crossing, compute the **just-under** and **just-over** funding solutions, and pick the cheaper — never rely on smooth convergence over the discontinuity. The **under-cliff branch is a constrained solve (MAGI ≤ 4.00 × FPL, optimum sitting at the threshold) that may be INFEASIBLE** once all MAGI-invisible funding (Roth/basis/cash/HSA) is exhausted — on infeasibility take the over-cliff branch, never oscillate or emit an in-range default (`burned/062`); the **over-cliff branch pins PTC = 0 → net premium = full premium → a direct linear solve**, no fixed-point iteration. The cliff-aware ceiling, not the tax bracket, is the binding constraint in ACA years — so **when the overlay is ON, `bracket-fill`'s target ceiling becomes `min(tax-bracket edge, the ACA-subsidy-aware MAGI line pre-65 / the next IRMAA step post-65)`**, never the raw bracket top (the policy consumes the overlay's binding ceiling).

The 65+ Medicare-premium privilege is keyed to the **HSA OWNER's age**, not the spouse's. - [ ] **Unit 4: Encrypted local store + key lifecycle + recovery/export/restore** *(the trust unit)*

**Goal:** The trust layer — derive an AES key from a passphrase, encrypt the model at rest in IndexedDB, lock/unlock, and provide the recovery-phrase + encrypted-export/restore mechanism. **This unit makes R16's promise provable** and hands the passphrase-strength enforcement reason forward to P2·U8.

**Requirements:** R15, R16, R17, R18; R19 (store's no-falsely-confident-restore half).

**Dependencies:** U0. (Independent of U1–U3 — **parallelizable**.)

**Files:**
- Create: `src/crypto/kdf.ts` (PBKDF2-600k + HKDF), `src/crypto/cipher.ts` (AES-GCM), `src/crypto/recoveryPhrase.ts`, `src/store/db.ts` (idb), `src/store/session.ts` (key + decrypted model in memory, lock/unlock), `src/store/backup.ts` (export/restore)
- Create/extend: `src/shared/model.ts` (the persisted record shapes + the `schemaVersion` field — shared with U1/U2/U3; the **"never depleted" persisted sentinel** decision lands here)
- Test: `src/crypto/__tests__/{cipher.roundtrip,kdf,recoveryPhrase}.test.ts`, `src/store/__tests__/{session,backup}.test.ts`

**Approach:**
- `importKey('raw', utf8(passphrase), 'PBKDF2')` → `deriveKey({PBKDF2, salt, iterations:600000, SHA-256}, …, {AES-GCM,256}, extractable:false, ['encrypt','decrypt'])`. **Keys live in memory only — never persisted unwrapped** (passphrase-each-session model). Params live in the constants/`findings §Strand 2` — do not alter.
- **The 600k-iteration derivation must never freeze the UI (the rendered-pending-state contract).** 600,000 PBKDF2-HMAC-SHA256 iterations is a ~0.5–1.5s computation on a mid-tier phone — and it runs on **every** unlock, passphrase-set, recovery-unlock, and re-derive on lock. `crypto.subtle.deriveKey` is async and most browsers run the work off the main thread, but that is **implementation-dependent, not guaranteed by spec**, so the UI contract does not rely on it: every derivation renders an explicit calm **"unlocking… / securing…" pending state** owned by the lock/unlock state machine (and P2·U8's passphrase surface), and a test asserts no silent multi-hundred-ms unresponsive window. If the U4 spike measures real main-thread jank during derivation on the reference device, the fallback is a **dedicated crypto worker** (a message boundary distinct from the engine worker) — named here so it is a decided fallback, not an implementation surprise.
- **Key hierarchy (a planning EXTENSION, not a §Strand 2 derivation).** A stable random **data key (DK)** encrypts the model; the passphrase-derived key and the recovery-derived key each **wrap DK independently**. **Why (the load-bearing reason):** there is exactly **one** copy of the model (encrypted under DK), so the recovery path can **never** recover a *stale* copy. The flat alternative — store the model twice, once per credential — risks the two copies drifting (a save updates the passphrase copy but the recovery copy lags), so the surviving spouse could restore an out-of-date plan; that is the worst failure for a product whose reason to exist is the survivor case (R17/R18). DK also makes the common save path **one** encryption, not two, and makes a passphrase change a cheap re-wrap.
- **DK handling (keep the key non-exportable).** DK = **raw random bytes** (`crypto.getRandomValues`, 256-bit) imported as a `CryptoKey` with `extractable:false`. "Wrapping" DK = **AES-GCM `encrypt()` of the raw DK bytes** under each credential key — **not** WebCrypto `wrapKey()`, which would require DK `extractable:true` and let any injected script `exportKey('raw', dk)` and exfiltrate it, bypassing PBKDF2 entirely. DK encrypts exactly one plaintext stream (the model) with random 96-bit IVs; the per-vault save count stays far below the 2³² random-IV safe bound.
- **The at-rest store schema holds THREE record types:**
  - **model:** `{ iv(12B), ciphertext }` — the model encrypted under DK (no KDF salt; DK is raw key bytes).
  - **passphraseWrap:** `{ salt(16B), iv(12B), wrappedDataKey }` — DK wrapped under the passphrase-derived key.
  - **recoveryWrap:** `{ salt(16B), iv(12B), wrappedDataKey }` — DK wrapped under the recovery-derived key.
  Each wrap carries its **own** fresh salt + IV. The plaintext-before-encrypt begins with an integer **`schemaVersion` (= 1) as its first field**, written from v1; decrypt reads `schemaVersion` before any other field and branches/refuses on an unknown version (the migration enabler — it must exist from v1 or later migration is impossible; the decrypt branch anticipates the full ladder — **v1→v2** (Phase 3: buckets / budget / vintage stamps) **→v3** (Phase 4: `seedB` / chosen-goal / saved-recommendation)).
- **The "never depleted" persisted sentinel — DECIDED HERE, before the schema locks** (`archive/do-not-disturb/009`): `Infinity`/`NaN` silently become `null` through `JSON.stringify`/IndexedDB. The engine's "portfolio never depleted across the horizon" outcome must persist as an **explicit out-of-domain integer sentinel or a tagged-union discriminant** (e.g. a defined `{ kind: 'never-depleted' }` variant), **never `Infinity`/`NaN`/`null`**. The decode path maps the sentinel back to the engine's never-depleted state; a bare `null` is treated as corruption, not as never-depleted. This pins the serialization the U1 outcome-state set round-trips through.
- **Fresh IV + salt on EVERY encryption and re-encryption.** A fresh 12-byte IV per encryption, never reused; every re-wrap (passphrase change, recovery re-wrap, restore-sets-new-passphrase) mints a **fresh 16-byte salt AND a fresh 12-byte IV** — none carried over.
- **Atomicity.** Every multi-record mutation (first save's model + both wrap records; a passphrase re-wrap that writes the new wrap and deletes the old) commits as **one IndexedDB transaction** — all-or-nothing, leaning on IndexedDB's auto-abort/rollback so a tear never leaves a half-updated vault (a partial first save that wrote the passphrase wrap but not the recovery wrap would strand the survivor — catastrophic, discovered only at recovery time). A save reports success **only after** the write commits. **Expose a model-only re-encrypt entry point** — re-write the model record under the **existing in-memory DK** with a fresh IV, **wraps untouched** (DK is unchanged by a schema migration; re-minting wraps is reserved for credential ops) — the single-record degenerate case of the transaction, so the P3 **v1→v2** and the P4 **v2→v3** vault upgrades inherit this atomicity instead of re-implementing it.
- **Honest lock (no zeroization overclaim).** JS/WebCrypto cannot byte-scrub a `CryptoKey` handle or a string. On lock the session **drops its only references** to the key(s) and the decrypted model (and any derived copies), making them GC-eligible and requiring a fresh passphrase-derived key for every subsequent decrypt/encrypt. We claim *reference-drop + mandatory re-derive*, **not** cryptographic zeroization — so no downstream R15/R16 copy overstates it.
- Wrong passphrase → GCM auth-tag failure surfaced as a calm "that passphrase didn't unlock this", not a stack trace. **No artificial lockout** — unlimited retries (in a no-server model the real protection is PBKDF2-600k + the encrypted blob; a client-side lockout adds zero real security while breaking legitimate access). **The meaningful attacker is offline:** they have extracted the IndexedDB blob and are running PBKDF2 on their own hardware, never clicking *Unlock* in the browser — so no UI-layer lockout (client or server) defends against them, only KDF hardness does. This is named explicitly so a future contributor does not "harden" by adding a server-enforced rate-limiter, which would require a server and break the local-first architecture without improving security. Distinguish "wrong passphrase" (structurally valid record, GCM fail → retry) from "data damaged" (record absent/truncated/malformed → point to restore).
- **Recovery phrase spec:** entropy source = `crypto.getRandomValues` **only** (the U0 weak-RNG lint extends to `src/crypto/**`); a named, vetted wordlist (**BIP-39 English, 2048 words**); **12 words = 128 bits**. **Recovery-key derivation (pinned):** the phrase already carries full 128-bit entropy, so derive the recovery-wrapping key with **HKDF-SHA-256** (key-*expansion*, the correct primitive for high-entropy input — PBKDF2-600k's password-*stretching* adds nothing against a 128-bit secret) with **IKM = the phrase bytes, salt = the 16-byte `recoveryWrap` salt, and a pinned `info` string for domain separation** (`info = utf8('the-back-nine/recovery-wrap/v1')`, the `/v1` enabling future rotation). The `info` parameter is **mandatory, not optional**: it is what prevents a key collision if a second HKDF use over the same phrase is ever added, and is pinned as a constant in `src/crypto/kdf.ts` alongside the PBKDF2 params. The phrase is generated **once** and is **immutable** for the life of the data in the MVP; rotation is out of scope. **Display threat:** the phrase is a full credential with a screenshot/phishing threat model — the P2 display must instruct "store offline, don't screenshot" and prefer a print/PDF presentation over selectable text. **Non-selectability is a UX defense (casual shoulder-surfing, accidental clipboard), NOT DOM isolation** — a11y-tree text is readable by OS UI-Automation and browser extensions regardless — so the real mitigation is minimizing exposure (a view-then-dismiss display) and not persisting the phrase in the JS heap after the display step; no downstream copy may present non-selectability as a cryptographic control (the a11y caveat is owned by P2·U8).
- Recovery + export + restore are one mechanism: **export = encrypted blob** carrying an explicit **format-version field** from day one; restore = import file + phrase → set new passphrase (re-wrap, fresh salt+IV). **Mandatory export at first save** — the first Save flow produces/confirms the recovery phrase and the encrypted export file as part of reaching "saved"; no "remind me later" bypass (that path is where users get burned; the export pair is the real durability backstop).
- **In-place recovery unlock (the plain survivor case).** When the local vault is **intact** but the passphrase is unknown/forgotten, the surviving spouse unlocks **in place** — derive the recovery key from the phrase → unwrap DK from `recoveryWrap` → decrypt the model → prompt to set a new passphrase (re-wrap with fresh salt+IV). This is the survivor's primary door; file-restore is only for the device-wiped case. **The set-a-new-passphrase step is a MANDATORY BLOCKING gate** — **no write path is reachable until the new `passphraseWrap` is re-minted**. Otherwise the survivor could save data while the on-disk `passphraseWrap` still encodes the forgotten passphrase, silently degrading the vault to **recovery-phrase-only** access (if the phrase is then lost, the data is unrecoverable) — the worst outcome for the survivor product.
- **The seam, enforced structurally (contract #4) — one predicate, stated once.** The persistence API is **gated by construction** on the **conjunction**: a writable store handle requires **a derived session key AND a current (or in-session-just-minted) `passphraseWrap`**. Stating it as "writable iff a key is derived" alone is the trap the recovery-unlock path exposes — recovery-unlock derives a key and decrypts the model yet writes must stay blocked until the new `passphraseWrap` is re-minted (above), so "a key exists" is true while "writable" must still be false. Binding both clauses into the **same** seam (not a second hand-enforced rule layered on top) is what makes the survivor-stranded catastrophe structurally impossible: the same gate that refuses an unkeyed write refuses a recovery-unlocked write before the new `passphraseWrap` exists. There is no reachable cleartext/unkeyed/stale-credential write path. (The P1 evidence R15/R16 require, independent of the P2 intake test. The in-memory model is additionally guarded by U0's CSP.)
- **Durability is best-effort + backstopped.** The encrypted write commits **before** `navigator.storage.persist()` is attempted; `persist()`'s boolean is **advisory only** and never rolls back a successful save. `store.load()` returns a clean **"no vault present"** result (not an exception) for both first-run and post-eviction (Safari ~7-day idle eviction) → restore is a **first-class entry point**. A `persist()` denial or `QuotaExceededError` surfaces a calm "use your export" state, never a false "saved".
- **The no-key-leak gate is single-sourced** (`burned/063`): the security assertion imports the **same** record-shape definition the serializer writes, so adding a field can't silently bypass the "no raw key material" check.
- **The passphrase-strength enforcement reason is U4's, the gate is seated in P2·U8 — name the seam handed forward.** PBKDF2-600k is the **only** brute-force defense, so a weak passphrase voids the entire at-rest story. U4 hands forward a **mandatory min-entropy gate at passphrase-set** (no weak-passphrase bypass) to P2·U8, which owns the UI estimator (`zxcvbn-ts`) + the calm inline feedback. U4 states the contract: no `deriveKey` from a passphrase below the threshold, which is **PINNED at plan level — `zxcvbn-ts` score ≥ 3 AND an independent length ≥ 12** (the library is pinned at U0; this is the sole at-rest defense, so it is a security-grade decision, not deferred). P2·U8 owns only the UI estimator and the calm inline feedback, not the threshold or library choice.
- **Multi-tab (minimal guard):** serialize vault writes with `navigator.locks` (Web Locks); single-active-vault. **The store also EXPOSES the `no-write-in-flight` signal (the interface U0 declares and P2·U8 consumes) — U4 is its producer:** the session/store API surfaces an `isWriteInFlight()` query (true during an in-flight IndexedDB transaction, false on commit), so U0's PWA update-acceptance handler can defer `skipWaiting`+reload until a write commits and never tear a mid-encrypt vault. Without U4 producing it, U0's interface and P2's wiring have nothing to read — so it is owned here, with a test (below). **Concurrent-unlock semantics (named, not left undefined):** Web Locks serializes individual write transactions but does **not** stop two tabs from each unlocking and racing a save (the second tab's write could silently clobber the first's edits — a lost save, catastrophic for the survivor). A **`BroadcastChannel` single-active-session detection** closes this: a second tab attempting to unlock an already-unlocked vault is told *"this plan is open in another tab"* and stays **read-only** rather than opening a second writable session. Fuller multi-tab coordination (live cross-tab model sync) is explicitly out of MVP scope; single-active-**writer** is not.
- **Preconditions:** a passphrase change is available only while unlocked or when supplying the recovery phrase; a lock requested during an in-flight write is queued until commit then drops the key + model; a lock requested during an in-flight **engine run** lets the run finish but **discards its result** (never rendered post-lock).

**Execution note:** Test-first on the crypto round-trip, the wrong-passphrase path, the atomic-write/tear paths, the in-place recovery unlock, the mandatory-new-passphrase gate, and the restore failure paths — these are the trust guarantees.
