# Phase 2 — First Answer (the magic moment)

**Goal.** Deliver the magic moment end-to-end on a **single total-spend figure**: a calm, one-question-at-a-time intake whose first plain-language confidence statement **resolves live** — from *indeterminate* toward a verdict as the user answers — rendered through colorblind-safe viz, honest across all six outcome states *and* the survivor case, with **nothing persisted until the user explicitly saves** (and, when they do, a trust-grade Save flow that shows the recovery phrase, forces an encrypted export, and gates a weak passphrase). The first answer is the *spine* answer — the first beat. The strategy recommendation is the second beat and lands in Phase 4; the itemized budget that splits essentials from lifestyle is the Phase-3 deepening. This phase ships exactly **one** total-spend answer.

**Why this is Phase 2.** Phase 1 proved the engine is *right* (Trinity/Bengen golden cases, joint-and-survivor longevity retaining survivor identity per path, the bridge + tax + healthcare overlays that reduce byte-identically to the spine) and the store is *safe* (encrypted-at-rest, survivor recovery, the no-unkeyed-write seam). This phase is where a financially-literate friend first meets the product and decides whether to trust it with real retirement money. It **consumes** the engine (U1), the tax overlay (U2), the healthcare overlay (U3), and the store (U4) — it does not re-open them. It is gated by the **N=1 cold-read across all six outcome states plus the survivor readout** — the human tone bar from the Success Criteria (R25: the bar *rises* for a recommender; "just for friends" never softens validation). The viz primitives (U6) can be built alongside Phase 1 since they depend only on the scaffold.

## Phase-2 cross-cutting contracts

*These six contracts span the units below. They are named once here so a reader sees the seams, then enforced in the unit that owns each — mirroring Phase 1. Phase 1 now bakes the earned-income bridge, the tax-and-accounts overlay, the healthcare overlay, and longevity-that-retains-survivor-identity-per-path as **core** engine behavior, so Phase 2 **consumes** them as plain dependencies — there is no Phase-1-cascade contract here.*

1. **The memoryModel orchestrator (owned by U5; `src/store/memoryModel.ts`).** `memoryModel.ts` is not passive data — it is the named in-memory **session/engine-client** for the magic moment, owning six obligations:
   **(a)** it holds the **single long-lived Comlink worker handle**, created once *outside React's render path* (a module-level singleton / root holder — never in a component render, a re-running `useState`/`useMemo` initializer, or per intake step; must survive StrictMode's dev double-mount) and reused across every recompute — the React-tree *enforcement* of U1's "single long-lived instance … reused" worker guarantee (`ai-journey-stats/003` "create the long-lived thing eagerly, never in render"; the `use(promise)` Suspense pattern does **not** apply — there is no fetch).
   **(b)** It **mints the per-scenario 32-bit seed exactly once** via `crypto.getRandomValues` at the first engine run (a crypto-allowed layer — U0's lint bans `getRandomValues` only inside `src/engine/**`), stores it as a first-class model field, reuses it for every recompute, and persists it **unchanged** at Save (no re-mint), so the reloaded headline is byte-identical to the number the user saw and screenshotted (U1's determinism contract; the **same seed** the Phase-3 controls and the Phase-4 solver reuse so all candidates run on the **single shared market draw** — CRN). *(Phase 4 reads this existing field as `seedA` and adds a second, held-out scenario seed `seedB` — Phase-4 contract #2 — for the solver's grade + displayed numbers; this field is never re-minted.)*
   **(c)** It exposes a **worker-vs-main-thread capability flag**, set at worker construction (in this orchestration layer, never inside `src/engine`), falling back to a main-thread run so the first answer still renders; the flag's downstream consumers (disable live recompute) are the Phase-3 control surfaces.
   **(d)** It is the **recompute home** and the **named future owner** of the rounding-hysteresis seam — but **Phase 2 builds NO sticky rounding**: during intake (back-nav edits and progressive resolve) the headline / dollar / copy-state move **freely**, so sharpening is visible. The `lastDisplayed*` fields, the resolve→verdict sticky baseline, and the margin-gating rule are seated in **Phase-3** (the first edit-of-a-complete-answer recompute); the sticky baseline is captured at the resolve→verdict transition (engine state ≠ indeterminate), `lastDisplayed*` are **session-only / NOT persisted to the vault**, and on re-entry they are re-seated from Phase 3's deterministic recompute of the saved model — so a genuinely-moved answer (staleness) is never held to a stale screenshot value. `confidence.ts` stays pure and owns the *stateless* first-answer rounding (`priorHeadline = null`).
   **(e)** It is the **one plaintext shape** — the same to-be-persisted MODEL `shared/model.ts` defines, with **no parallel intake shape** and no field-mapping layer (U5 owns the detail; U8's field-fidelity guard rests on this single-shape rule, so an intake field can never be captured on screen yet silently dropped at Save).
   **(f)** It stamps each dispatched engine run with a **monotonic request epoch** and **discards any resolved result older than the latest committed epoch**, so racing in-flight runs on a slow device never render a stale intermediate (the no-jitter guarantee on rapid commits). *(This is one elevation of an existing module — not a new module. `src/store/session.ts` remains the crypto/key session from U4, a different concern.)*

2. **The outcome-state set (engine-owned; consumed by U7).** The set is the **six** states `on-track / borderline / off-track / indeterminate / over-funded / already-failing`, a single-sourced enum in `src/shared/model.ts` (the file U1/U2/U3/U4 already share). The **engine** (`confidence.ts`, U1) is the *sole* authority that selects the state and owns **all band edges, the indeterminate selection, and the over-funded near-ceiling clamp** — the distribution arrives at the UI **already tagged** with its state. `src/ui/outcomeStates.ts` is a **pure presentation lookup** keyed by that enum (`state → {copy, nextAction, verdictSignal}`) with **zero** threshold/banding/clamp logic, exhaustive over the enum so an unhandled state is a TypeScript compile error (`burned/042` fail-loud-on-contract-drift). The Phase-3 budget split applies a **two-tier lexicographic reading** (an essentials-floor verdict + a lifestyle-surplus verdict) to these **same** six states — it is **not** a hardcoded 7th state. The clamp's *correctness* test stays in U1; U7 asserts only presentation-per-state.

3. **The non-color signal vocabulary (primitives owned by U6 `src/viz/palette.ts`; two consumers; lives in the a11y tree).** One module owns the colorblind-safe **primitives**: the luminance ramp, the named shape/marker set, the line-style set, and the rule "separate by luminance, not hue" (`burned/051`, `010`). **Two distinct consumers** map those primitives to two *different* semantic axes — never forced to render identically: **verdict-state** (U7 `verdictSignal`: six states → word + shape + magnitude) and **series-identity** (U6 two-series encoding → solid/dashed + marker + end-label). "Parity" means *both draw from the same primitive set*, not identical rendering. The `culori`/`oklab` probe widens to cover **every** color either consumer renders (including `verdictSignal`'s redundant colors), so no UI-layer color escapes CVD validation. Because the user is color **blind, not blind**, the signal must also be **programmatically available in the accessibility tree** (verdict word as text; shape/icon carries an `aria-label` = state name; band/series exposed via a text alternative), not merely grayscale-visible (`burned/045`). The six verdict icons must be **pairwise-distinct** on the non-hue channel (silhouette + luminance), not merely individually identifiable.

4. **The copy catalog + copyGuard (catalog created in U5, copyGuard born in U7; both in `src/ui`).** Every user-facing string in `src/ui` and `src/intake` lives in **one typed copy catalog** (`src/ui/copy.ts`), **created in U5** (the first copy-authoring unit) and **extended by U7** — so intake copy routes through it from the start, not as a retrofit. An **ESLint `no-restricted` rule, added in U5 and scoped to `src/ui` + `src/intake`**, bans inline user-facing strings — both **JSXText** *and* user-facing JSX attributes (`aria-label`, `aria-description`, `placeholder`, `alt`, `title`) — so a directive can't leak through an attribute (the a11y contract *requires* `aria-label`s, which are user-facing, so they route through the catalog too). This is the `burned/063` "single-source the gate" pattern applied to copy. The copyGuard test **enumerates the catalog and asserts every entry passes**, so a new string is forced through the gate by construction — making R12 / the Success-Criteria honesty test true *by construction*. The guard is **categories, not five literals**: imperative-mood advice verbs ("you should / we recommend / advise / must / need to / make sure / consider / the smartest|best move"); advice-implying superlatives; false-certainty verbs ("guaranteed / ensures / locks in / you will save"). The **certainty-hygiene** rule is made *decidable* by **slot discipline**: quantitative content appears ONLY through typed template slots (`~$X`, `~N years`, the `X of 10` natural-frequency frame), so the guard validates **slot presence/framing** rather than scanning free numerals — with a small allowlist for non-claim numerics (ages, SS claim ages 62–70, question counts, the pinned denominator 10). **RMD age is never a copy literal** — it is engine-owned and birth-year-derived (72 / 73 / 75; findings §Strand 5), supplied by the model through a slot, so it is not in the allowlist; `src/viz` stays string-free (every label arrives as a prop from `copy.ts`). The **catastrophe-lexicon** check on user-facing survivor copy is a **tone-lint that AIDS the N=1 cold-read** (the human gate is the real tone judge), explicitly *not* a regulatory shield. **Surface-scoped:** the static R13 honest-limits note ("validate big, irreversible moves with a pro") is a U0 constant **outside** the guard's input, so the disclosure-shaped note stays legal while imperative mood is forbidden in verdicts. *(Handed forward — NOT built here: the **require-the-hedge** positive lint — a require/assert that every control readout and the recommendation headline wears its probabilistic hedge — is added in **P3·U10** and extended in **P4·U16**; the Roth-conversion copy slots — a tax-bracket-% slot, the user-echoed conversion amount/years, the survivor tax-cliff `~$X` — are registered in **P3·U10** so the Roth strings pass the catalog-enumeration by construction. Phase 2 ships only the ban-list + certainty-hygiene + catastrophe-lexicon + the catalog-enumeration gate.)*

5. **The display contract (owned in this preamble; consumed by U6/U7 and the Phase-3 controls).** The **display denominator is pinned at 10**: the engine runs 1000+ paths (`confidence.ts` owns the raw→display rounding), but every user-facing natural-frequency renders as "**X of 10**" — verdict, survivor readout, and the Phase-3 "buys you ~N years" delta all use the **same** denominator so the user never re-bases between surfaces. The **top-of-scale render is coupled to U1's over-funded near-ceiling clamp**: the scale tops out at "**more than 9 of 10**" so "10 of 10" can never appear — the denominator *is* 10. **Framing direction is a copy rule** the N=1 cold-read evaluates: outcome-first for positive states ("in 9 of 10 … the money lasts"), action-first for negative states ("in 4 of 10 … you'd trim ~$X/month", the count subordinate to the dollar move — Kitces probability-of-adjustment, R2). The "more than 9 of 10" top-of-scale render is owned by the **headline render** (not a per-state copy-row clause) and can attach to **both** on-track and over-funded — so over-funded shows the near-ceiling frequency *and* its underspending-mirror copy.

6. **The magic-moment surface contract (owned by U5 + U7).** The intake architecture is **progressive, engine-gated, commit-triggered**: the confidence surface co-exists with intake and resolves from *indeterminate* toward a verdict as questions are answered (recompute fires on each question-**commit**, not live-as-you-type). The **first frame is verdict-text-first in ALL modes** (word + dollar magnitude + non-color shape) — the **ConfidenceBand is never on the first frame**; it is the on-demand "range" of R4, revealed by an explicit affordance (R2/R4 forbid a dashboard on the primary surface; a calm band is still "the range"). **Render levels (reconciled so the same set isn't described twice):** the engine RESULT transport is a **tri-state** (`pending` | `resolved-distribution` | `calm-error`); the **four render modes** are *pending*, *compute-error*, and — *within* resolved-distribution — *indeterminate* vs *resolved-verdict* (distinguished by the engine's outcome-state tag). **Pending governs ONLY the pre-first-verdict window** (cold-start → first resolved distribution, including the first indeterminate) and shows no verdict-shaped placeholder; **once any distribution has resolved, subsequent recomputes HOLD the last verdict + band visible and crossfade/morph to the new result — they never re-enter pending** (no per-commit blank/flicker). The indeterminate **wide no-median placeholder band** is what the range-reveal shows *when the answer is indeterminate* — behind the same on-demand affordance, **NOT on the first frame**. *compute-error* is a non-verdict system state whose next-action is **retry**, never "sharpen". Motion: the band **draws once** (on its first reveal) then **morphs** on every recompute (interruptible transition/spring, never a draw-from-zero replay); the headline number renders **static** (no odometer/count-up); verdict→verdict crossfades are margin-gated (the gating is *exercised* in Phase 3 — Phase-2 intake numbers move freely). **No-worker fallback:** a main-thread run blocks the event loop, so a per-commit run would contend with the step-transition slide — on the fallback flag each commit's recompute is **deferred until after the step transition paints** (yield post-paint); if profiling still shows jank, the fallback **downgrades to one compute at the minimum-viable-input point + one at completion** (instrument first, per the eye-in-loop motion lesson). All of it respects `prefers-reduced-motion`.

- [ ] **Unit 5: Guided progressive on-ramp + in-memory orchestrator + R19 sanity**

**Goal:** A calm, one-question-at-a-time intake for a married couple whose first confidence statement **resolves live** (indeterminate → verdict) on a **single total-spend figure**, with **zero persistence**, validating inputs inline, on a surface that **shines on a phone**.

**Requirements:** R5 (guided intake on a single total-spend figure), R6 (escape-hatch entry point), R8 (caveated answer fast, refinement *sharpens*), R19 (sanity checks); gates R15/R16 via the in-memory→persistence seam.

**Dependencies:** U0, U1, U2 (the tax overlay it can leave OFF for the spine answer), U3 (the healthcare overlay it can leave OFF for the spine answer).

**Files:**
- Create: `src/intake/coldStart.tsx`, `src/intake/flow.tsx`, `src/intake/questions.ts`, `src/intake/sanity.ts`, `src/intake/intakeMap.ts` (the intake→engine-param contract), `src/store/memoryModel.ts`, `src/ui/copy.ts` (the typed copy catalog — **created here** so intake copy routes through it from the start; **extended by U7** — cross-cutting #4)
- Modify: `eslint.config.js` (add the `no-restricted` **no-inline-user-facing-copy** rule scoped to `src/ui` + `src/intake`, banning JSXText *and* user-facing attribute literals `aria-label`/`placeholder`/`alt`/`title` — cross-cutting #4; lives in Phase 2, not a U0 re-open)
- Test: `src/intake/__tests__/sanity.test.ts`, `flow.test.tsx`, `coldStart.test.tsx`, `src/store/__tests__/memoryModel.test.ts`

**Approach:**
- **Progressive, engine-gated, commit-triggered architecture (cross-cutting #6).** The confidence surface co-exists with intake; as soon as the minimum-viable input set exists it renders **indeterminate** and resolves toward a verdict as questions are answered. The magic moment is "watch the answer resolve as you go" — still **one** answer, no dashboard, range/math on demand (R4). Whether inputs are "enough to compute" vs indeterminate is the **engine's** decision surfaced as the indeterminate state (U1; `confidence.ts` is the single threshold source) — intake **never** hard-codes "render after question N". Recompute fires on each question-**commit**, not per keystroke.
- **Single total-spend on-ramp (R5; the on-ramp-protection decision, north-star D-budget).** The fast first answer runs on **one total-spend figure** — the itemized essentials/discretionary budget (R20) is the **Phase-3 deepening (sharpen loop), never the on-ramp**. Intake collects a single household spend number; the engine treats it as the spending term. The Phase-3 budget builder later replaces that scalar with a categorized, time-boxed plan whose sum reconciles to it.
- **Cold-start frame ((origin: "Deferred to Planning — cold-start/zero-data first screen")).** The brand-new user's first frame is **one calm entry screen** — *not* a marketing/landing page — that presents R1's question (*"Can we retire, and how do we do it best?"*) as the product's face, states the married-couple precondition as orientation, and offers one action into question 1. This frame is the single home of the precondition line. The R13 honest-limits note is **not** re-owned here — it already lives app-wide via U0's shell.
- **`memoryModel.ts` is the in-memory orchestrator (cross-cutting #1).** It holds **one** plaintext shape — the same to-be-persisted MODEL `shared/model.ts` defines (financial inputs + per-person params + the injected seed + sim assumptions incl. survivor-spending ratio), populated incrementally during intake. **There is no parallel intake shape and no field-mapping layer**; Save is a clean serialize of that exact object (`schemaVersion` is prepended only at U4's encrypt step). Adding an intake field is one edit to the shared shape, so a field can never be captured on screen yet silently dropped at Save. It also holds the eager worker handle, mints/stores the seed, exposes the fallback flag, stamps each run with the request epoch, and carries the (Phase-3-seated) `lastDisplayed*` fields as declared-but-unused-in-P2 placeholders for the hysteresis seam.
- **Minimum-user-fact set vs methodology defaults; explicit `unknown` sentinels (R19, R5; `burned/062` no-in-range-default).** Two input classes: **(a) required user-facts** — two ages, two **sexes** (below), two incomes / SS streams + claim ages, household savings (one total-savings figure — the bucket split is deferred, below), household total spend, per-person retirement year, per-person earned-income stream to that year — gate the first compute; **(b) methodology assumptions** (real return + volatility σ, inflation, longevity tables, survivor-SS step-down, survivor-spending ratio) are **pre-defaulted and safe to default** *because* R7/U7-surfacing + Phase-3 editing make them visible + editable. The contract: `memoryModel` passes an explicit **`unknown` sentinel** (an out-of-range value, never a silent 0 / `?? 0.04`-style default that overlaps a plausible real value — `burned/062`) for any required user-fact not yet collected, and `simulate` maps any `unknown` required fact to the **indeterminate** state, never a confident headline. (This makes U1's "minimal/missing-assumption inputs → indeterminate" test authorable; it extends the engine's R19 half from *impossible* values to *absent* values.) **No "skip with a reasonable default" UI** — methodology defaults are auto-applied and surfaced.
- **The intake→engine param contract (`intakeMap.ts`).** The transitive contract between intake and U1's `model.ts`, in three buckets: **ASKED** (each question and which model param it fills); **DEFAULTED-AND-SURFACED** (R7-editable, exposed in Phase 3: real return + volatility σ, inflation, survivor-spending ratio, longevity tables — exposed as editable assumptions, **not** an allocation picker, keeping intake minimal per R5); and the **must-decides**:
  - **Per-spouse sex — collected.** Two sex fields; the joint-and-survivor longevity math `P = pₓ + pᵧ − pₓ·pᵧ` selects the **sex-specific** SSA cohort curve per spouse (findings §Strand 4; U1) and handles same-sex couples honestly. Leaving it implicit would be both a correctness bug on the product's core survivor case and a hidden R7-violating assumption.
  - **Per-person retirement year + earned-income bridge.** Intake collects each spouse's retirement year and a flat **real earned-income** stream per person until that year. The engine models the **bridge** as CORE behavior (U1): in years where one spouse still earns, earned income **nets against spending** (reduced/zero net withdrawal), with the earning window truncated at `min(retirementYear, sampledDeathYear)` per path. Default both retirement years equal → no asymmetric bridge window. MVP-minimal: flat real income, net-against-spending only — **no** salary-growth curve, **no** surplus-contribution modeling (post-MVP; surfaced as an editable assumption).
  - **Account-type buckets (pre-tax / Roth / taxable / HSA) — deliberately deferred to Phase 3 (F-handoff).** The first answer collects **one** total-savings figure to protect the ~3-min on-ramp (R5). The bucket split is gathered when the user **opens a control** (P3·U10 sequencing/Roth lever-open mini-intake; the HSA bucket at P3·U11) behind a `model.ts` field + `schemaVersion` bump, consistent with depth-on-demand and R10/R11. A deliberate deferral, not an omission. (The spine answer therefore runs with the tax + healthcare overlays **OFF** — reducing byte-identically to the validated spine — which is exactly right for the first beat.)
- **Currency entry that shines on a phone (mobile must SHINE, not survive).** The model stores each input as a **raw number**; the field **displays** a formatted string. Open-ended dollar fields use a text field summoning the numeric keypad — **not** a native number-spinner (rejects grouped digits, shows steppers) and **not** a slider (can't hit an exact figure; violates R6's "set any assumption precisely"). Sliders are reserved for **bounded** ranges (ages, percentages). **Reformat on blur**, not per keystroke (avoids caret-jump). Full-width, finger-sized fields.
- **Monthly-vs-annual: prevent at entry, test the dangerous direction (R19).** Every per-period money field carries an explicit **`$/month` vs `$/year`** segmented control (active segment by shape/weight, not hue), so the period is unambiguous by construction; the model stores one canonical period (defaults: spend = /month, income + SS = /year, editable). The implausible-magnitude check is the **second** line of defense; for a value coherent as **both** monthly and annual, intake **forces** an explicit per-period confirmation rather than silently computing on the default — so the engine can never run on 1/12 (or 12×) the real figure.
- **R19 sanity, decomposed per rule + directional re-validation (R19; engine half lives in U1).** Each rule is a discrete testable rule that blocks only **true impossibilities** (retirement age < current age; SS claim outside 62–70; survivor-spending ratio > 100%) and lets coherent-but-dire inputs ($0 portfolio + positive spend) flow to an honest "0 of 10". **Directional half:** cross-gated inputs re-fire their check when an **upstream** answer they depend on is edited via Back — an upstream edit **keeps** downstream answers (never silently wipes) but marks dependents for re-validation; if it makes a downstream answer impossible, the same calm inline message fires at the point of edit, so no stale-but-impossible combination reaches the engine. The engine's numeric-domain half (indeterminate on horizon ≤ 0) is only a backstop.
- **Validation timing (R5 "advisor-style", R11 "calm never traded for engagement").** Rules evaluate on **field blur and attempt-to-advance, never per keystroke**; a rule whose inputs aren't all present yet does not fire; an in-progress value invalid-as-prefix but valid-when-complete ("6" → "62") is never flagged mid-entry; an existing error clears the instant the field is re-edited.
- **State ownership + back-nav without loss.** Every step reads/writes through the single `memoryModel` (no per-step local copy to lose), so Back re-renders the prior step pre-filled. Mechanism left to implementation (do **not** mandate `useReducer`).
- **Accessibility contract (the stranger-trust bar; N=1 reader is color blind; mobile must shine).** On each step advance, move focus to the new step **heading** (`tabindex=-1`), **not** the input (auto-focus pops the keyboard before the user reads the question) — the heading-as-focus-target *is* the announcement (no double-announce). One visually-hidden polite live region carries only transient status, with `burned/045` clear-after-announce discipline so stale text never lingers in the a11y tree (keeps Playwright/N=1 snapshot verification honest). R19 errors associate to their field (`role="alert"` + `aria-invalid` + `aria-describedby`), clear on valid, and carry the non-color signal (word + shape + text). The focus-move/`announce()` helper is a shared a11y primitive U7 reuses to move focus to the verdict.
- **Step-transition motion (`emil-design-eng`; `ai-journey-stats/006`).** Direction encodes meaning (forward enters from the right, Back reverses); a brief, strong ease-out (duration/easing deferred to implementation, eye-in-loop); **interruptible** (transition/spring, never `@keyframes` that restart from zero) so rapid Next/Back never strands a mid-flight animation. **Focus-safe rule (load-bearing):** any step that receives programmatic focus on mount is faded with **opacity only** — never `autoAlpha`/`visibility` toggle — and the outgoing step is **unmounted**, not visibility-hidden, or `.focus()` is a silent no-op (`ai-journey-stats/006`, generalized from a modal to a wizard step). `prefers-reduced-motion` → drop the slide, keep a fast opacity fade.
- **Progress orientation + paired two-person screens (consumability wedge).** **No** "Step N of 10" chore-counter on the primary surface (reads as a form; the flow is variable-length, so a fixed denominator would be inaccurate); instead a quiet, unlabeled progress thread encoded by **fill proportion**, never hue, plus an SR-announced position. Two-person questions render as **one paired screen** ("you / your spouse"), never two near-identical sequential screens — wrap each in a `fieldset`/`legend` (or `role="group"` + `aria-labelledby`) so the pairing is programmatic. **On-ramp budget:** the required-fact count is **~12–14 facts** (two ages, two sexes, two incomes, two SS streams + claim ages, one total-savings figure, one total-spend figure, two retirement years, two earned-income streams); pairing the per-person facts two-up keeps it to **~7–8 screens** and the bar that actually matters is **<3 min, perceived-low-effort**, not a raw count (Success Criteria).
- **Copy catalog + no-inline lint (cross-cutting #4).** All intake question/error/affordance copy routes through `src/ui/copy.ts` from the first commit; the `no-restricted` ESLint rule is added here so the "by construction" guarantee holds for intake copy at U5 build time, not as a U7 retrofit. U7 extends the same catalog + adds `copyGuard`.

**Patterns to follow:** `useCallback` all handlers passed to step/slider children (`ai-journey-stats/007`); `ai-journey-stats/006` (focus-safe enter, opacity not autoAlpha); `burned/045` (clear-after-announce live region); `burned/062` (no in-range default fallback — out-of-range sentinels); `emil-design-eng` (direction/timing/reduced-motion).

**Test scenarios:**
- Happy path (progressive): minimum-viable inputs → an **indeterminate** statement renders → each subsequent answered question re-runs the engine and the statement **sharpens** → nothing persisted to IndexedDB throughout.
- Error path (R19 forward): retirement age before current age → caught inline, calm, no broken answer.
- Error path (R19 directional / back-nav): a valid retirement age, then Back → raise current age above it → the retirement-age rule **re-fires inline**, the downstream answer is **not** wiped, no impossible combo reaches the engine.
- Edge case (back-nav no loss): complete several steps → Back → every prior answer intact and pre-filled; advancing forward preserves edits.
- Error path (partial-intake false-confidence, **planted**): plant a default-to-0 spend (or defaulted income) in `memoryModel` → the surface renders **indeterminate**, *not* a defaulted rosy over-funded number (fail-loud, `burned/062`/`070`). Keep the existing **$0 *entered* spend → honest "0 of 10"** as the coherent-dire mirror, noted as distinct.
- Edge case (period false-negative): a spend value coherent as **both** monthly and annual → intake **forces** the per-period confirmation; the engine never runs on the unconfirmed default. (Keep the implausible-as-annual case as the over-count backstop.)
- Edge case (R19 per-rule pairs — fire **and** boundary-pass): retire = current−1 fires / retire = current passes; SS claim 61 & 71 fire / 62 & 70 pass; survivor ratio > 100% fires / exactly 100% passes; implausible-magnitude fires / a plausible annual figure passes.

- [ ] **Unit 8: First-Save flow + passphrase-strength gate (in-memory → keyed persistence — the trust handoff)**

**Goal:** The user-facing moment the in-memory model first reaches disk — the Save CTA, passphrase-set **gated by a min-entropy strength check**, recovery-phrase display, and mandatory export — wired to U4's mechanism. **This is the surface that makes R16/R17/R18's promise real to the user, and the strength gate is what makes PBKDF2-600k's brute-force defense actually load-bearing.**

**Why a dedicated unit.** U4 built the save/recovery/export *mechanism* and explicitly deferred the *display* ("the Phase-2 display must instruct 'store offline, don't screenshot' and prefer a print/PDF presentation"; "mandatory export at first save — no remind-me-later bypass"). It can't live in U5 (whose goal is **zero** persistence) or U7 (no save deliverable). It is the Phase-2 owner of cross-cutting #1's **end-to-end** half (U4 proves the no-unkeyed-write seam at its own layer; this unit proves it end-to-end at the real Save) and the home of the **net-new passphrase-strength gate** (north-star resolved open question).

**Requirements:** R16 (encrypted at rest + guarded local access — the strength gate is the front door), R17 (survivor recovery), R18 (export/back-up durability).

**Dependencies:** U4 (mechanism — `kdf`/`session`/`backup`/the no-write-in-flight signal), U5 (`memoryModel` + the seed), U7 (the surface the Save CTA lives on + the copy catalog).

**Files:**
- Create: `src/ui/SaveFlow.tsx`, `src/ui/RecoveryPhraseDisplay.tsx`, `src/ui/ExportConfirm.tsx`, `src/ui/passphraseStrength.ts` (the min-entropy gate wrapping the strength estimator)
- Test: `src/ui/__tests__/saveFlow.test.tsx`, `passphraseStrength.test.ts`

**Approach:**
- **Save CTA on the confidence surface (U7), reachable only after a first answer exists** — Save is a deliberate post-answer act, not an intake step.
- **Passphrase-set screen wired to U4's `kdf`/`session`** — sets the passphrase that wraps DK.
- **Passphrase-strength gate (net-new; north-star "Resolved During Planning").** A **hard min-entropy gate at passphrase-set** using a real strength estimator (e.g. `zxcvbn-ts`) with a **minimum-score threshold** and **calm inline feedback** (the non-color signal grammar; no scary red meter). **No weak-passphrase bypass** — the user cannot reach a "saved" state with a sub-threshold passphrase. The rationale is structural, not cosmetic: **PBKDF2-600k is the *only* brute-force defense** (the encrypted blob + the KDF is the at-rest boundary — `extractable:false` stops only script exfiltration, per U4), so a weak passphrase voids the entire at-rest story for real financial PII (R16). The gate runs **before** any wrap is minted. *(Exact threshold + the library pin are **deferred to implementation** — the decision here is "a hard min-entropy gate with no bypass," not the numeric score; the estimator counts against the bundle budget and the CSP `connect-src 'self'`, so it must be bundled, never a CDN call.)*
- **Recovery-phrase display honoring the §Strand 2 threat model:** the phrase is a full credential with a screenshot/phishing threat model — present **non-selectable**, **print/PDF-preferred**, with an explicit "store offline, don't screenshot" instruction; **not** a screenshot-friendly copy box.
- **Mandatory encrypted-export confirm** as part of reaching a "saved" state — **no remind-me-later bypass** (U4's R17/R18 hard gate; the export pair is the real durability backstop after Safari eviction).
- **Hand the in-memory model — including its seed — to U4's keyed write path**, so the save→reload→unlock round-trip reproduces the **identical** headline (the seed round-trip is U1+U4's contract; this unit persists *through* it).
- **Owns the PWA update-mid-write integration test** U0 deferred to "where the real save flow exists" — wiring the U0 update-acceptance handler to the store's existing "no-write-in-flight" signal.
- **Field-fidelity guard, schemaVersion-agnostic:** the decrypted plaintext model must be field-identical to the in-memory model at Save (no field that produced the on-screen answer is dropped — the single-shape contract #1 makes this structural, the test proves it). The guard asserts field-identity for **whatever shape the session produced**, not a fixed field set: a first Save of a spine-only session persists the schemaVersion-1 shape; the Phase-3 controls (which add buckets behind a `schemaVersion` bump) persist the schemaVersion-2 shape directly when opened before a first Save — the guard adapts to the session's shape.
- All copy routes through the U7 copy catalog + copyGuard; all motion respects `prefers-reduced-motion`.

**Patterns to follow:** U4 (`kdf`/`session`/`backup`); findings §Strand 2 (recovery-phrase display threat model); U7 copy catalog + non-color signal; `burned/063` (single-source the gate — the strength gate reads its threshold from one constant, not a hand-typed literal).

**Test scenarios:**
- Happy path (end-to-end first save): intake → answer → Save → passphrase-set (passes the strength gate) → recovery phrase shown per the §Strand 2 display rules (non-selectable, print/PDF) → mandatory export confirmed → vault now exists; the model **and seed** round-trip so a reload reproduces the identical headline.
- Error path (strength gate): a sub-threshold passphrase → calm inline "stronger passphrase needed" feedback, **no wrap minted, no path to "saved"**; raising it to threshold then proceeds; the gate reads its threshold from the single-sourced constant (`burned/063`), and the estimator never makes a network call (CSP).
- Edge case (field-fidelity at Save, schemaVersion-agnostic): populate `memoryModel` through full intake **including** a non-default survivor-spending override, Save, reload, decrypt → the decrypted plaintext is **field-identical** to the in-memory model at Save (including seed + override) — no on-screen field dropped; assert this holds for both a spine-only (v1) session and a controls-opened (v2) session shape.
- Integration (PWA update-mid-write): a service-worker "update ready" **accepted** during an in-flight first-save encrypt-write → the handler reads the store's no-write-in-flight signal and **defers** `skipWaiting`+reload until the write commits, with **no false "saved" before commit**; after commit the deferred reload proceeds. **Rationale (rescoped):** U4's single-IndexedDB-transaction atomicity is *already* the partial-vault / survivor-stranding backstop (a reload mid-transaction auto-aborts/rolls back); this handler exists only to avoid a **needless failed/false-"saved" first save** on a user-accepted update — a UX/honesty refinement, not a second owner of atomicity. *(Distinct from U4's store-layer atomicity backstop and U0's prompt-mode/no-`skipWaiting` test.)*
- Error path: export-confirm cannot be skipped to reach "saved" (no remind-me-later bypass); a `persist()` denial / `QuotaExceededError` surfaces the calm "use your export" state, never a false "saved".

**Verification:** A first-time user, after seeing their answer, sets a passphrase **that clears a real strength gate (no weak-passphrase bypass)**, is shown (and stores) a recovery phrase they cannot accidentally screenshot, is **forced** to export, and lands at a saved vault whose reload reproduces the exact number they saw; an accepted PWA update mid-write never tears the vault. *(This is the user-facing evidence R16/R17/R18 require, and the strength gate is what makes R16's PBKDF2-600k boundary real rather than nominal.)*
