# Phase 1 — Foundation

**Goal.** Stand up the buildable PWA skeleton, the deterministic Monte Carlo engine validated against known-good reference cases, and the encrypted local store that makes the privacy promise provable. Nothing user-facing ships in this phase — but the engine's answer must be *right* and the store's guarantee must be *proven* before any surface consumes them.

**Why this is Phase 1.** The two hardest, highest-risk surfaces — *correctness* (a calm-but-wrong number fails the bar worse than no tool) and *trust* (R15: provable before spoken) — are foundations everything else stands on. Units 1 and 2 are independent of each other (parallelizable after Unit 0) and have zero monorepo precedent, so they carry the most risk and must be locked first.

> Paths are relative to `projects/the-back-nine/`. References: `(origin: …)` → `docs/brainstorms/the-back-nine-requirements.md`; `(findings §StrandN)` → `docs/research/foundation-findings-2026-06-03.md`. Reference numbers/params live in the findings doc — never re-stated here.

## Phase-1 cross-cutting contracts

*These four contracts span the units below. They are named once here so a reader sees the seams, then enforced in the unit that owns each.*

1. **The determinism contract (owned by Unit 1, consumed by Unit 2 and Phases 2/3).** The engine is a pure function of `(params, seed)`. The seed is a single integer in `mulberry32`'s signed-32-bit domain, **injected by the caller** (never generated inside `src/engine`), and stored as a first-class field of the saved model. The **draw schedule** — the count and ordering of normal draws per path/year — is a pure function of the path/horizon **dimensions only, never of the financial inputs**: the normals matrix is allocated to the **maximum** cohort horizon up front and indexed by **absolute year**, so financial/longevity inputs (including the survivor two-regime boundary) select *which* draws are consumed, never *how many* are generated or their order — and the Box-Muller transform is **stateless** (no cached spare). A fixed seed therefore reproduces a byte-identical matrix of normals regardless of which input changes (this is what makes Common Random Numbers possible for the Phase-3 Roth arms). The seed must survive Unit 2's encrypt → persist → decrypt round-trip **bit-identically**. **Seed-stability** (same inputs + same seed → identical raw distribution and identical raw rounded headline) is Unit 1's pure guarantee; **rounding hysteresis** is a *stateful* property (it needs the prior displayed headline) and therefore lives in the Phase-2/3 recompute orchestration, **not** in pure `confidence.ts` — which still owns the *stateless* first-answer rounding rule (`priorHeadline = null`, with defined band-edge tie-breaking). See Unit 1.
2. **Two validation modes (owned by Unit 1).** A **deterministic historical-sequence backtest** is a **self-consistent oracle** — the engine reproduces *our own committed, pinned-dataset* historical run byte-for-byte — plus a **directional** check against the *published* Trinity/Bengen figures (exact equality to the published numbers waits on pinning each study's exact source series — see Unit 1). The **Monte Carlo** path is validated only against a **band** that runs *more pessimistic* than the historical anchor (findings §Strand 4). These are different assertions against different code paths — conflating them, and over-claiming the published numbers as exactly reproducible, was the plan's #1 correctness gap (see Unit 1).
3. **The in-memory → encrypted-persistence seam (owned by Unit 2).** Nothing touches disk until the user saves and sets a passphrase. This is enforced **structurally** — the store exposes no write path that can run before a key exists — not by caller discipline. (At rest, encryption guards the disk; the cleartext model held in JS memory during an unlocked session is guarded by Unit 0's CSP.) The Phase-1 store proves the seam at its own layer; Phase 2 (Unit 3) adds the end-to-end intake assertion. (Gates R15/R16.)
4. **The R19 split (owned by Unit 1 + Phase-2 intake).** The **engine** guards its own numeric domain — no `NaN`/`Infinity` escapes a percentile; degenerate-but-coherent inputs return an honest extreme, never a crash. **Semantic plausibility** checks (retirement age < current age, spending beyond any plausible portfolio) are the R19 **intake-layer** concern owned by Phase 2 (Unit 3). Neither layer assumes the other validated.

- [ ] **Unit 1: Monte Carlo engine core + validation contract** *(the correctness unit)*

**Goal:** A pure, deterministic TypeScript Monte Carlo engine that models a married couple's joint-and-survivor longevity and emits a distribution the UI reads as "X of N futures" + the dollar adjustment — validated via **two distinct modes**: a deterministic historical-sequence backtest (a self-consistent oracle + a directional check on the published figures) and the Monte Carlo path (asserted as a band).

**Requirements:** R3 (distribution of futures), R14 (plain-language reading), R19 (engine's numeric-domain half), correctness success criterion.

**Dependencies:** Unit 0.

**Files:**
- Create: `src/engine/rng.ts`, `src/engine/longevity.ts`, `src/engine/simulate.ts`, `src/engine/historical.ts` *(the deterministic backtest oracle — new)*, `src/engine/confidence.ts`, `src/engine/engine.worker.ts`, `src/shared/model.ts`
- Create: `src/engine/reference/` (Trinity/Bengen fixtures — **committed**, generated via cFIREsim-open on a pinned dataset; self-consistent + directional, not published-exact — see the two validation modes)
- Test: `src/engine/__tests__/rng.test.ts`, `simulate.test.ts`, `longevity.test.ts`, `confidence.test.ts`, `historical.test.ts`, `worker.test.ts`, `src/engine/reference/__tests__/validation.test.ts`

**Approach:**
- Port `mulberry32` + the CSPRNG/seeded split from `projects/burned/src/server/rng.ts` (**vendored, not cross-imported** — see Unit 0); add a **stateless** Box-Muller normal transform (absent in burned — confirmed): consume two uniforms per draw and **do not cache the spare** across calls (the textbook cached-spare pattern makes the Nth normal depend on call parity, silently desynchronizing the stream between two CRN arms). **The engine never generates its own seed:** `crypto.getRandomValues` is called by the caller (session/orchestration layer) and the 32-bit seed is **injected** into `simulate`/the worker; `src/engine` reads no entropy source, clock, or environment (enforced by the extended Unit 0 lint). A saved scenario stores its seed in `model.ts` so identical inputs reproduce the identical headline (seed-stability), and the seed must round-trip through Unit 2's encryption bit-identically (cross-cutting contract #1).
- Lognormal sim with **log-drift μ = arithmetic_mean − σ²/2** (the #1 MC bug is naïve arithmetic compounding — findings §Strand 4). Conservative real-return + inflation defaults, all user-overridable.
- **Common Random Numbers (Phase-1 seam):** `simulate` allocates its normals matrix to the **maximum** cohort horizon up front, indexed by **absolute year**, so the draw schedule (count + ordering) is a pure function of the path/horizon **dimensions only**. Financial and longevity inputs — including the **survivor two-regime boundary** (which moves with sampled longevity and the survivor-spending ratio) — select *which* draws are consumed for the overlapping years, never *how many* are generated or their order. Two parameter sets run under one shared seed therefore consume identical normals path-for-path — the "buys you ~N years" delta is pure signal, not RNG jitter. `roth.ts` (Phase 3) is a **consumer** of this seam; the seam itself lives in `simulate.ts`/`model.ts` in Phase 1.
- **Joint-and-survivor longevity** from **cohort** (not period) tables: P(last survivor alive) = pₓ + pᵧ − pₓ·pᵧ. SSA cohort source = `table4c7.html` (explicitly **not** the period table `table4c6.html`). Two-regime horizon (joint → survivor): survivor-SS step-down (keep larger benefit) + survivor-spending ratio (default **~75% — a product default decided in planning, editable, revisit after N=1 cold-read; NOT a findings-traced number**, param). Never a fixed "to-age-90".
- Outputs: the full terminal-value distribution + percentiles + depth-of-failure (not a binary pass/fail) → `confidence.ts` maps it to "X of N", the dollar adjustment ("trim ~$Y/month"), and the outcome state. **Never "probability of failure"** (Kitces framing). `confidence.ts` is **pure** (single run → reading): it owns the **stateless** first-answer rounding rule (given `priorHeadline = null`, with defined band-edge tie-breaking) and emits the raw continuous confidence value **plus margin metadata** (distance to the next band edge) so a stateful caller can layer sticky rounding on top — it does **not** itself implement cross-edit hysteresis (cross-cutting contract #1).
- **Two validation modes (the correctness contract):**
  - **(A) Historical-sequence backtest** (`historical.ts`) — replays fixed historical return sequences. It is the engine's *anchor*, asserted two ways: **(1) self-consistency** — the engine reproduces **our own committed golden fixture** (generated on a pinned dataset) byte-for-byte, so an engine regression fails loud; **(2) directional** against the *published* Trinity/Bengen figures (lands near them, in the right band), **not** exact equality. **Why not exact:** the golden fixtures are generated with **cFIREsim-open** (`github.com/boknows/cFIREsim-open`, **Shiller** data), and Shiller's series carries long-term **government** bonds — Trinity's published 95% uses long-term **corporate** bonds, a series cFIREsim-open does not contain. So cFIREsim-open yields a faithful *self-consistent* oracle on a known dataset but cannot reproduce Trinity's published corporate number exactly; treat the published figures as **directional until the exact source series are pinned** (same posture already applied to Bengen — see the exit gates below). *(Elevates the origin doc's "optional historical cross-check" to a required validation mode — without an anchor the MC band has nothing to be asserted below. Roadmap Output Structure updated to add `historical.ts`. The optional→required elevation wants a requirements-doc amendment — tracked.)*
  - **(B) Monte Carlo** (`simulate.ts`) — validated against a **band only**: an i.i.d. MC runs *more pessimistic* than the historical backtest (findings §Strand 4), so the MC result must land inside the asserted band **and strictly below** the historical anchor. Reserve byte-for-byte equality for mode (A)'s self-consistency check only.
- **Trinity fixture spec (vintage-locked):** the fixture carries the full definition — 1926–1995 window, S&P 500 + **long-term CORPORATE** bonds, inflation-adjusted withdrawals, success = balance > $0 at horizon end, annual rebalance (findings §Strand 4). When generating with cFIREsim-open, restrict the window to this vintage; the bond series will be Shiller **government** (see the exit gate) until a true corporate series is pinned.
- **Bengen caveats (all four, findings §Strand 4):** tag the fixture **1966 cohort** (not 1968); 50% S&P 500 / 50% **intermediate-term GOVERNMENT** bonds; **DIRECTIONAL survive/fail only** until the exact Ibbotson intermediate-government dataset is pinned ("pin before relying"); and **never cross-validate** the Trinity 50/50 (corporate) figure against the Bengen 50/50 (government) figure — the bond series legitimately makes them differ.
- **Phase-1 exit gates (not background caveats — these block calling a fixture "golden"; from findings §Strand 4 "Still-unverified"):** **(1)** the SSA cohort curves were grounded-search-verified, **not parsed from the SSA tables** (SSA bot-blocks automated fetch) → confirm against the actual `table4c7.html` via a manual fetch and commit a snapshot fixture before the longevity curves are load-bearing; **(2)** Bengen's bit-exactness depends on the exact Ibbotson intermediate-government dataset → pin before relying; **(3)** Trinity's published number depends on a long-term-corporate series cFIREsim-open lacks → pin before relying. Until each gate clears, its fixture is **directional** (marked so in code), and no downstream phase may treat it as golden. Name who/what clears each gate before Phase 1 closes.
- **Worker boundary contract:** runs in `engine.worker.ts` behind Comlink, a **single long-lived instance** created and Comlink-wrapped once and reused across recomputes (the live-recompute budget is measured against reuse, not per-run spawn). **Result shape:** the large numeric arrays (terminal-value distribution, percentile series, per-path depth-of-failure) return as typed-array buffers via `Comlink.transfer`; the small derived fields (X-of-N integers, dollar adjustment, outcome-state enum) travel by ordinary structured clone in the same object and are **not** in the transfer list. Transferred buffers are **detached** on the worker side — the worker retains none for reuse and allocates fresh per run (protects the future CRN path). **Error propagation:** a thrown engine error is caught at the worker boundary and surfaces as a defined **calm** result, never a hung promise / unhandled rejection / dead worker; the worker stays alive and reusable. **No-worker posture:** because the engine is pure TS, a worker-construction failure (CSP / old browser / module-worker unsupported) **falls back to a main-thread run** rather than a dead-end. Phase 1 proves only that the fallback returns the **same distribution** as the worker path; the UX consequence — a main-thread 1k-path run blocks the event loop, so on fallback the consuming surface must run a **one-shot** answer and **disable live recompute** (commit-on-release, not debounced drag) — is a Phase-2 concern, noted here so Phase 2 owns it.
- **Engine's R19 half (input-boundary defense):** `simulate` validates/clamps params at the worker boundary and returns the existing **indeterminate/not-enough-data** state for invalid input rather than computing — no `NaN`/`Infinity` ever escapes into a percentile or headline. Semantic plausibility is the intake layer's half (cross-cutting contract #4).

**Execution note:** Implement test-first against the reference cases — the golden fixtures are the contract. Build mode (A) `historical.ts` first so the anchor exists before the MC band is asserted below it.

**Patterns to follow:** `projects/burned/src/server/rng.ts` (determinism discipline, the load-bearing `|0` coercions); burned/055+070 (determinism gates fail loud + self-test against a planted positive); burned/042 (engine↔reader contract-drift precedent for the worker boundary).

**Test scenarios:**
- **Mode A — self-consistency:** the historical backtest reproduces **our committed Trinity-vintage golden fixture** byte-for-byte (a regression fails loud); and the result lands **directionally near** the published 50/50 95% (right band), not asserted as exact equality until the corporate series is pinned.
- **Mode A — Diagnostic (the landmine), directional:** historical 100%-bond / 4% / 30-yr lands in a **~65–75% band** — materially below the 50/50 case and far above the wrong **20–35%** range — proving inflation/volatility handling is correct. Asserted as a band, **not** exact equality to a tilde'd `~70%`.
- **Mode A — extra anchors (optional, strengthen the oracle):** historical 75/25 ≈ 100% and 100%-stock ≈ 98% (findings §Strand 4, directional) — catch allocation-handling bugs the 50/50-vs-bond pair alone would miss.
- **Mode B — MC band:** the Monte Carlo 50/50 / 4% / 30-yr lands inside the asserted band (high-80s to ~90%, findings §Strand 4) **and strictly below** the historical anchor — a result *equal to* 95% is a bug (the MC must run more pessimistic).
- **Mode B — MC bond, directional:** the Monte Carlo 100%-bond case fails materially more than the 50/50 case and is demonstrably **not "safe"** — asserted directionally, **not** as an equality to ~70%.
- Edge case: log-drift unit test — +50% then −50% yields two-year **cumulative −25%** / **annualized geometric −13.4%** (correct, distinct labels, findings §Strand 4).
- Edge case: same inputs + same seed → byte-identical raw distribution and byte-identical raw rounded headline across repeated runs (seed-stability).
- Edge case: first-answer rounding — `confidence.ts` with `priorHeadline = null` and a raw value sitting **exactly on a band edge** produces a defined, stable headline (the stateless tie-break is pinned; Phase 2/3 stickiness builds on this).
- Edge case: CRN under a **regime-shifting** input — two parameter sets differing only in the **survivor-spending ratio** (which moves the two-regime boundary), run under one shared seed, consume normals **identical path-for-path** for the overlapping years (proves the max-horizon / absolute-year allocation holds even when the survivor boundary moves — the hardest CRN case); same assertion for a Roth-relevant input.
- Edge case: $0 portfolio + positive spending → honest "0 of N" (coherent-but-dire, never a crash or NaN).
- Edge case: NaN hygiene — no `ln`/`exp` of a non-positive escapes into a percentile.
- Edge case (R19 engine half): each of {negative portfolio, `NaN` param, `Infinity` spending, horizon ≤ 0} → the defined **indeterminate** outcome, no crash, no `NaN`/`Inf` anywhere in the distribution.
- Edge case (outcome states): the **10/10-honesty clamp** — an all-paths-survive distribution renders as the honest near-ceiling **over-funded** state, never a bald "10 of 10" / 100%; and **indeterminate/not-enough-data** — minimal/missing-assumption inputs yield the indeterminate state (the *expected first answer*), not a falsely confident number (roadmap six-state + 10/10 decision).
- Error path: a forced internal sim error surfaces as the defined **calm** error result and the worker **remains alive/reusable** for the next run (no dead-worker, no unhandled rejection); a simulated worker-construction failure falls back to a main-thread run that returns the **same distribution** as the worker path (the no-white-screen / disable-live-recompute UX is a Phase-2 test).
- Integration (worker transport, `worker.test.ts`): an in-worker run with `Comlink.transfer` returns a distribution **byte-identical** to the same seeded run executed in-thread (no truncation/detachment of transferred buffers), and the transferred-buffer **layout** (offsets/lengths) that `simulate.ts` emits matches `confidence.ts`'s reader, with a `NaN`/zero sentinel so a misread channel fails loud rather than rendering "0 of N" (burned/042).
- Integration: couple longevity — at-least-one-survivor-to-90 probability materially exceeds a single life (sanity vs findings §Strand 4 ~53% figure); survivor-SS step-down lowers the verdict vs ignoring it.

**Verification:** Mode-A reproduces our committed golden fixtures byte-for-byte and lands directionally near the published figures (exact-equality gated on pinning the Trinity-corporate / Bengen-Ibbotson / SSA datasets); Mode-B MC tests land in-band and below the historical anchor; all run on CI (fail-loud, self-tested against a planted wrong number per `burned/070`). A 1k-path run completes well under the live-recompute budget in the reused Worker. The seed survives Unit 2's persistence round-trip and reproduces the identical headline after reload (asserted in Unit 2).

**Approach:**
- `importKey('raw', utf8(passphrase), 'PBKDF2')` → `deriveKey({PBKDF2, salt, iterations:600000, SHA-256}, …, {AES-GCM,256}, extractable:false, ['encrypt','decrypt'])`. **Keys live in memory only — never persisted unwrapped** (passphrase-each-session model). Params are findings §Strand 2 — do not alter.
- **Key hierarchy (a planning EXTENSION, not a §Strand 2 derivation).** §Strand 2 specifies the single passphrase-derived key + a recovery phrase that recovers both login and data; this layers a stable random **data key (DK)** on top — DK encrypts the model; the passphrase-derived key and the recovery-derived key each **wrap DK independently**. **Why (the load-bearing reason):** there is exactly **one** copy of the model (encrypted under DK), so the recovery path can **never** recover a *stale* copy. The flat alternative — store the model twice, once under each credential — risks the two copies drifting out of sync (a save updates the passphrase copy but the recovery copy lags), so the surviving spouse could restore an out-of-date plan; that is the worst failure for a product whose reason to exist is the survivor case (R17/R18). DK also makes the common save path **one** encryption, not two, and makes a passphrase change a cheap re-wrap. *(Briggsy's call, 2026-06-03, over the scope-review's "simplify to flat" challenge — kept for recovery-can-never-go-stale, not merely cheap rotation. §Strand 2 is cited for the params and the recovery model, not for the DK indirection.)*
- **DK handling (keep the key non-exportable).** DK is generated as **raw random bytes** (`crypto.getRandomValues`, 256-bit) and imported as a `CryptoKey` with `extractable:false` for model encryption. "Wrapping" DK = **AES-GCM `encrypt()` of the raw DK bytes** under each credential key — **not** WebCrypto `wrapKey()`, which would require DK to be `extractable:true` and let any injected script `exportKey('raw', dk)` and exfiltrate it, bypassing PBKDF2 entirely. One-line crypto bound: DK encrypts exactly one plaintext stream (the model) with random 96-bit IVs; the per-vault save count stays far below the 2³² random-IV safe bound, so IV-collision risk is negligible, and DK never encrypts a second plaintext domain.
- **Corrected at-rest store schema** (the old single `{salt, iv, ciphertext}` had nowhere to hold the wrapped keys). The store holds **three record types**:
  - **model:** `{ iv(12B), ciphertext }` — the model encrypted under DK (DK is raw key bytes, so no KDF salt on this record).
  - **passphraseWrap:** `{ salt(16B), iv(12B), wrappedDataKey }` — DK wrapped under the passphrase-derived key.
  - **recoveryWrap:** `{ salt(16B), iv(12B), wrappedDataKey }` — DK wrapped under the recovery-derived key.
  Each wrap carries its **own** fresh salt + IV. The plaintext-before-encrypt begins with an integer **`schemaVersion` (= 1) as its first field**, written from v1; decrypt reads `schemaVersion` before interpreting any other field and branches/refuses on an unknown version (the migration enabler — it must exist from v1 or later migration is impossible; Phase 3 already modifies `model.ts`).
- **Fresh IV + salt on EVERY encryption and re-encryption.** A fresh 12-byte IV per encryption, never reused; and **every re-wrap** (passphrase change, recovery re-wrap, restore-sets-new-passphrase) mints a **fresh 16-byte salt AND a fresh 12-byte IV** — none carried over from the prior credential.
- **Atomicity.** Every multi-record mutation (first save's model + both wrap records; a passphrase re-wrap that writes the new wrap and deletes the old) commits as **one IndexedDB transaction** — all-or-nothing, leaning explicitly on IndexedDB's auto-abort/rollback so a tear never leaves a half-updated vault (a partial first save that wrote the passphrase wrap but not the recovery wrap would strand the survivor — catastrophic and only discovered at recovery time). A save reports success **only after** the write commits.
- **Honest lock (no zeroization overclaim).** JS/WebCrypto cannot byte-scrub a `CryptoKey` handle or a string. On lock the session **drops its only references** to the key(s) **and the decrypted model** (and any derived copies), making them GC-eligible and transitioning to a locked state in which every decrypt/encrypt path **requires a fresh passphrase-derived key**. We claim *reference-drop + mandatory re-derive*, **not** cryptographic zeroization — so no downstream R15 copy overstates it. Locking does not tear down the engine worker (Unit 1), but the worker holds no persistent copy of financial inputs beyond an in-flight run.
- Wrong passphrase → GCM auth-tag failure surfaced as a calm "that passphrase didn't unlock this", not a stack trace. **No artificial lockout** — unlimited retries: in a no-server model the real protection is PBKDF2-600k + the encrypted blob, so a client-side lockout adds zero real security while breaking legitimate access. Distinguish "wrong passphrase" (structurally valid record, GCM fail → retry) from "data damaged" (record absent/truncated/malformed → point to restore).
- **Recovery phrase spec:** entropy source = `crypto.getRandomValues` **only** (the Unit 0 weak-RNG lint extends to `src/crypto/**`); a named, vetted wordlist (**BIP-39 English, 2048 words**); **12 words = 128 bits**, matching the §Strand 2-cited Evolu precedent (do not pick a different bit-count without flagging). **Recovery-key derivation:** because the phrase already carries full 128-bit entropy, derive the recovery-wrapping key with **HKDF-SHA-256** (key-*expansion*, the correct primitive for high-entropy input) keyed by the `recoveryWrap` salt — PBKDF2-600k's password-*stretching* adds nothing against a 128-bit secret but is an acceptable conservative alternative; pin one. The phrase is generated **once** and is **immutable** for the life of the data in the MVP — every export is decryptable by that single phrase; rotation is out of scope. **Display threat (carry from findings §Strand 2):** the phrase is a full credential with a screenshot/phishing threat model — the Phase-2 display must instruct "store offline, don't screenshot" and prefer a print/PDF presentation over selectable text.
- Recovery + export + restore are one mechanism: **export = encrypted blob** carrying an explicit **format-version field** from day one; restore = import file + phrase → set new passphrase (re-wrap, fresh salt+IV). Onboarding copy states the phrase + file are a **pair** (no-sync MVP: phrase alone recovers nothing *from a file* — but see in-place recovery for the intact-vault case). **Mandatory export at first save** — the first Save flow produces/confirms the recovery phrase and the encrypted export file as part of reaching a "saved" state; no "remind me later" bypass (findings §Strand 2: that path is where users get burned, and the export pair is the real durability backstop).
- **In-place recovery unlock (the plain survivor case).** Distinct from file-restore: when the local vault is **intact** but the passphrase is unknown/forgotten, the surviving spouse unlocks **in place** — derive the recovery key from the phrase → unwrap DK from the `recoveryWrap` record → decrypt the model → prompt to set a new passphrase (re-wrap with fresh salt+IV). This is the survivor's primary door; file-restore is only for the device-wiped case. Both must exist.
- **The seam, enforced structurally.** The persistence API is **gated on a key by construction** — the only way to obtain a writable store handle is through the session *after* a key has been derived; there is no reachable cleartext/unkeyed write path. (Cross-cutting contract #3 — this is the Phase-1 evidence R15/R16 require, independent of the Phase-2 intake test. The in-memory model is additionally guarded by Unit 0's CSP.)
- **Durability is best-effort + backstopped.** The encrypted write commits **before** `navigator.storage.persist()` is attempted; `persist()`'s boolean is **advisory only** and never fails or rolls back a successful save. `store.load()` returns a clean **"no vault present"** result (not an exception) for both first-run and post-eviction (Safari ~7-day idle eviction, findings §Strand 2) → restore is a **first-class entry point**, and the export pair is the durability backstop, made testable below. A `persist()` denial or a `QuotaExceededError` surfaces a calm "use your export" state, never a false "saved".
- **The no-key-leak gate is single-sourced** (burned/063): the security assertion imports the **same** record-shape definition the serializer writes, so adding a field can't silently bypass the "no raw key material" check.
- **Multi-tab (minimal guard):** serialize vault writes with `navigator.locks` (Web Locks); single-active-vault. Fuller multi-tab coordination is explicitly out of MVP scope (decision, not omission).
- **Preconditions:** a passphrase change is available only while unlocked or when supplying the recovery phrase (re-wrapping DK first requires unwrapping it); a lock requested during an in-flight write is queued until the write commits, then drops the key + model; a lock requested during an in-flight **engine run** lets the run finish but **discards its result** (never rendered post-lock) — financial output never reaches the UI after the user locks.

**Execution note:** Test-first on the crypto round-trip, the wrong-passphrase path, the atomic-write/tear paths, the in-place recovery unlock, and the restore failure paths — these are the trust guarantees.

**Patterns to follow:** Greenfield for the monorepo; `idb` (jakearchibald) for IndexedDB; findings §Strand 2 is the spec for params + the recovery model (NOT the DK indirection — that's the roadmap's extension); burned/063 (single-source the no-leak gate).

**Test scenarios:**
- Happy path: encrypt model → persist → reload → unlock with passphrase → byte-identical model (including the **seed** field — proving Unit 1's determinism survives the persistence round-trip and reproduces the identical headline).
- Error path: wrong passphrase → decrypt fails cleanly (GCM auth-tag), no partial/garbage model surfaced; Nth wrong attempt still permits attempt N+1 (no lockout), and a correct passphrase then succeeds.
- Error path: a truncated/corrupted ciphertext → GCM rejection surfaced as the calm "data damaged" state (distinct from "wrong passphrase"), never a crash.
- Edge case: passphrase change re-wraps DK without invalidating the recovery phrase (in-place recovery with the old phrase still works), and the new wrap record's salt **and** IV both differ from the old.
- Edge case: IV/salt freshness — re-encrypting the same model twice yields a different IV **and** different salt **and** different ciphertext (proves no reuse).
- Edge case: a blob whose plaintext `schemaVersion` is unknown/newer-than-supported → calm "saved by a newer version" state, never a mis-parsed model.
- Error path (atomicity): a write aborted mid-transaction leaves the prior decryptable blob intact (unlock still returns the previous model); an interrupted first save leaves **no** partial vault (the recovery phrase either fully works or the save fully failed); an interrupted passphrase swap leaves the **old** passphrase still working (never a state where neither old nor new unlocks).
- Error path (durability): a forced `persist()` = false / `QuotaExceededError` → the save reports failure with the calm "use your export" state, in-memory model intact, no partial record — never a false "saved".
- Edge case (no vault): `load()` against an empty/cleared object store → clean "no vault present" state with the restore path reachable, no throw (covers first-run and post-eviction alike).
- Integration: **in-place recovery unlock** — passphrase forgotten + **intact** local vault → the recovery phrase alone unwraps DK, decrypts the model, and prompts a new passphrase (re-wrapped with fresh salt+IV); afterward the recovery phrase still works.
- Integration: export encrypted blob → wipe IndexedDB (models Safari eviction) → restore from file + recovery phrase → set new passphrase → original model recovered; and export → change passphrase → restore the **earlier** export with the unchanged phrase still succeeds (phrase immutability).
- Error path (restore): valid file + **wrong** recovery phrase → calm "that recovery phrase doesn't match this backup" (GCM fail), no partial model; corrupted/truncated/non-Back-Nine file → calm "this backup file looks damaged" (format-version checked **before** decrypt), never a stack trace.
- Security (negative pairing — proven, not believed): recovery phrase **without** the export file recovers nothing *from a file* in the no-sync MVP; export file **without** the phrase recovers nothing.
- Security: **DK is non-exportable** — while unlocked, `exportKey('raw', DK)` is not possible (DK was imported `extractable:false`; "wrapping" uses `encrypt()` of raw bytes, never `wrapKey()`).
- Edge case: lock mid-session drops **both** the in-memory key and the decrypted model; subsequent access requires re-unlock (asserted behaviorally — no method returns/uses the prior key or model — **not** by inspecting wiped bytes). A lock issued during an in-flight engine run discards that run's result (it never renders).
- Security: the store exposes **no** write path reachable before a key exists — attempting to persist while locked / before a key is derived is impossible by construction (the Phase-1 home of the magic-moment-first seam; the Phase-2 intake flow adds the end-to-end version).
- Security assertion: no **raw/unwrapped** key material ever appears in any IndexedDB record — the store contains only the three defined record types (model `{iv,ciphertext}`, two wraps `{salt,iv,wrappedDataKey}`), asserted against the single-sourced record-shape definition (burned/063).

**Verification:** A full save→reload→unlock and an export→wipe→restore cycle both reproduce the model (including the seed); an in-place recovery-phrase unlock of an intact vault recovers the current model; an interrupted write leaves the prior vault intact; a `grep` of the persisted store shows no raw key material; `extractable:false` is used but the plan and any future copy state plainly that it prevents **script** exfiltration only and is **not** the at-rest boundary — the boundary is the AES-GCM ciphertext protected by the PBKDF2-600k passphrase derivation. *(This is the evidence R15 requires before any "we can't see your money" copy ships.)*
