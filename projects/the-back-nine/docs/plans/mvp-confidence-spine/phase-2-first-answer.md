# Phase 2 — The First Answer (the magic moment)

**Goal.** Deliver the magic moment end-to-end: a calm, one-question-at-a-time intake whose first plain-language confidence statement **resolves live** — from *indeterminate* toward a verdict as the user answers — rendered through colorblind-safe viz, honest across all six outcome states *and* the survivor case, with **nothing persisted until the user explicitly saves** (and, when they do, a trust-grade Save flow that shows the recovery phrase and forces an export).

**Why this is Phase 2.** Phase 1 proved the engine is *right* and the store is *safe*. This phase is where a stranger first meets the product and decides whether to trust it with their net worth. It consumes the engine (Unit 1) and the store (Unit 2), and is gated by the **N=1 cold-read across all six outcome states plus the survivor readout** — the human bar from the success criteria. The viz primitives (Unit 4) can be built alongside Phase 1 since they only depend on the scaffold.

## Phase-2 cross-cutting contracts

*These seven contracts span the units below. They are named once here so a reader sees the seams, then enforced in the unit that owns each — mirroring Phase 1. Several are contracts Phase 1 explicitly handed forward into a Phase-2 home; this section is that home.*

1. **The in-memory orchestrator (owned by Unit 3; `src/store/memoryModel.ts`).** `memoryModel.ts` is not passive data — it is the named in-memory **session/engine-client** for the magic moment, and it owns four obligations Phase 1 deferred to "the caller (session/orchestration layer)": **(a)** it holds the **single long-lived Comlink worker handle**, created once *outside React's render path* (a module-level singleton / root holder — never in a component render, a re-running `useState`/`useMemo` initializer, or per intake step; must survive StrictMode's dev double-mount), and reused across every recompute — this is the React-tree *enforcement* of Phase 1 Unit 1's "single long-lived instance … reused" guarantee (`ai-journey-stats/003` "create the long-lived thing eagerly, never in render"; the `use(promise)` Suspense pattern itself does **not** apply — there is no fetch). **(b)** It **mints the per-scenario 32-bit seed exactly once** via `crypto.getRandomValues` at the first engine run (a crypto-allowed layer — Unit 0's lint bans `getRandomValues` only in `src/engine/**`), stores it as a first-class model field, reuses it for every recompute, and persists it **unchanged** at Save (no re-mint), so the reloaded headline is byte-identical to the number the user saw and screenshotted (Phase-1 contract #1; the seed Phase-3's Roth CRN arms reuse). **(c)** It exposes a **worker-vs-main-thread capability flag**, set at worker construction (in the orchestration layer, never in `src/engine`), falling back to a main-thread run so the first answer still renders — the flag's consumers (disable live recompute) are the Phase-3 sliders (Unit 7/8). **(d)** It is the **recompute home** and the **named future owner** of the rounding-hysteresis seam — but **Phase 2 builds NO sticky rounding**: during intake (back-nav edits and progressive resolve) the headline/dollar/copy-state move **freely**, so sharpening is visible. The `lastDisplayed*` fields and the sticky rule are seated in **Phase-3 Unit 7** (the first edit-of-a-complete-answer recompute); `confidence.ts` stays pure and owns the *stateless* first-answer rounding (`priorHeadline = null`). **(e)** It is the **one plaintext shape** — the same to-be-persisted MODEL `shared/model.ts` defines, with **no parallel intake shape** and no field-mapping layer (Unit 3 owns the detail; Unit 6's field-fidelity guard rests on this single-shape rule, so an intake field can never be captured on screen yet silently dropped at Save). **(f)** It stamps each dispatched engine run with a **monotonic request epoch** and **discards any resolved result older than the latest committed epoch**, so racing in-flight runs on a slow device never render a stale intermediate (the no-jitter guarantee on rapid commits). *(Absorbs the engine-client-lifecycle obligations from Phase-1 Unit 1's "No-worker posture," seed injection, and worker-reuse notes; this is one elevation of an existing module, not a new module — `src/store/session.ts` remains the crypto/key session, a different concern.)*

2. **The OutcomeState single-source (engine-owned; consumed by Unit 5).** The six-state enum is a single-sourced type in `src/shared/model.ts` (the file Units 1 and 2 already share). The **engine** (`confidence.ts`, Phase 1 Unit 1) is the *sole* authority that selects the state and owns **all band edges, the indeterminate selection, and the 10/10-honesty clamp** — the distribution arrives at the UI **already tagged** with its state. `src/ui/outcomeStates.ts` is a **pure presentation lookup** keyed by that enum (`state → {copy, nextAction, verdictSignal}`) with **zero** threshold/banding/clamp logic, exhaustive over the enum so an unhandled state is a TypeScript compile error (`burned/042` fail-loud-on-contract-drift). The clamp's *correctness* test stays in Phase 1 Unit 1; Unit 5 asserts only presentation-per-state.

3. **The non-color signal vocabulary (primitives owned by Unit 4 `src/viz/palette.ts`; two consumers; lives in the a11y tree).** One module owns the colorblind-safe **primitives**: the luminance ramp, the named shape/marker set, the line-style set, and the rule "separate by luminance, not hue" (`burned/051`, `010`). **Two distinct consumers** map those primitives to two *different* semantic axes — never forced to render identically: **verdict-state** (Unit 5 `verdictSignal`: six states → word + shape + magnitude) and **series-identity** (Unit 4 two-series encoding → solid/dashed + marker + end-label). "Parity" means *both draw from the same primitive set*, not identical rendering. The `culori` oklab probe widens to cover **every** color either consumer renders (including `verdictSignal`'s redundant colors), so no UI-layer color escapes CVD validation. Because the user is color **blind, not blind**, the signal must also be **programmatically available in the accessibility tree** (verdict word as text; shape/icon carries an `aria-label` = state name; band/series exposed via a text alternative), not merely grayscale-visible (`burned/045`: observers read the a11y tree, not pixels). The six verdict icons must be **pairwise-distinct** on the non-hue channel (silhouette + luminance), not merely individually identifiable.

4. **The copyGuard catalog (owned by Unit 5 `src/ui/copyGuard.ts`; consumed by Phase-3 Roth).** Every user-facing string in `src/ui` and `src/intake` lives in **one typed copy catalog** (`src/ui/copy.ts`), **created in Unit 3** (the first copy-authoring unit) and **extended by Unit 5** — so intake copy routes through it from the start, not as a Unit-5 retrofit. An **ESLint `no-restricted` rule, added in Unit 3 and scoped to `src/ui` + `src/intake`**, bans inline user-facing strings — both **JSXText** *and* **user-facing JSX attributes** (`aria-label`, `aria-description`, `placeholder`, `alt`, `title`) — so a directive can't leak through an attribute (the a11y contract *requires* `aria-label`s, which are user-facing, so they must route through the catalog too). This is the `burned/063` "single-source the gate" pattern applied to copy — the same burden-of-proof Phase 1 Unit 2 applied to the no-key-leak gate. The copyGuard test **enumerates the catalog and asserts every entry passes**, so a new string is forced through the gate by construction — making R12 / the Success-Criteria "**No string** issues a directive" true *by construction*. The guard is **categories, not five literals** (imperative-mood advice verbs; advice-implying superlatives; false-certainty verbs). The **certainty-hygiene** rule is made *decidable* by **slot discipline**: quantitative content appears ONLY through typed template slots (`~$X`, `~N years`, the `X of 10` natural-frequency frame), so the guard validates **slot presence/framing** rather than scanning free numerals — with a small allowlist for non-claim numerics (ages, SS claim ages 62–70, RMD age 73, question counts, the pinned denominator 10). The **catastrophe-lexicon** check on user-facing survivor copy is a **tone-lint that AIDS the N=1 cold-read** (the human gate is the real tone judge), explicitly *not* a regulatory shield. **Surface-scoped:** the static R13 "consult a licensed professional" disclaimer is a Unit-0 constant **outside** the guard's input (so the mandatory directive-shaped disclaimer stays legal while imperative mood is forbidden in verdicts). copyGuard is the string-level *last line* — **not** the primary regulatory shield (per findings §Strand 3 the categorical-surface / user-initiated / no-verdict architecture is the load-bearing IAA defense).

5. **The display contract (owned in this preamble; consumed by Units 4/5 and Phase-3 Roth).** The **display denominator is pinned at 10**: the engine runs 1000+ paths (`confidence.ts` owns the raw→display rounding), but every user-facing natural-frequency renders as "**X of 10**" — verdict, survivor readout, and the Phase-3 "buys you ~N years" delta all use the **same** denominator so the user never re-bases between surfaces. The **top-of-scale render is coupled to Phase 1's 10/10 clamp**: the scale tops out at "**more than 9 of 10**" (the over-funded near-ceiling render), so "10 of 10" can never appear — the denominator *is* 10. **Framing direction is a copy rule** the N=1 cold-read evaluates: outcome-first for positive states ("in 9 of 10 … the money lasts"), action-first for negative states ("in 4 of 10 … you'd trim ~$X/month", the count subordinate to the dollar move — Kitces probability-of-adjustment, R2). The "**more than 9 of 10**" top-of-scale frequency render is owned by the **headline render** (not a per-state copy-row clause) and can attach to **both** on-track and over-funded — so over-funded shows the near-ceiling frequency *and* its underspending-mirror copy.

6. **The magic-moment surface contract (owned by Units 3 + 5).** The intake architecture is **progressive, engine-gated, commit-triggered**: the confidence surface co-exists with intake and resolves from *indeterminate* toward a verdict as questions are answered (recompute fires on each question-**commit**, not live-as-you-type). The **first frame is verdict-text-first in ALL modes** (word + dollar magnitude + non-color shape) — the **ConfidenceBand is never on the first frame**; it is the on-demand "range" of R4, revealed by an explicit affordance (R2 forbids a dashboard; a calm band is still "the range"). **Render levels (reconciled so the same set isn't described at two levels):** the engine RESULT transport is a **tri-state** (`pending` | `resolved-distribution` | `calm-error`); the **four render modes** are *pending*, *compute-error*, and — *within* resolved-distribution — *indeterminate* vs *resolved-verdict* (distinguished by the engine's outcome-state tag). **Pending governs ONLY the pre-first-verdict window** (cold-start → first resolved distribution, including the first indeterminate) and shows no verdict-shaped placeholder; **once any distribution has resolved, subsequent recomputes HOLD the last verdict + band visible and crossfade/morph to the new result — they never re-enter pending** (no per-commit blank/flicker). The indeterminate **wide no-median placeholder band** is what the range-reveal shows *when the answer is indeterminate* — it lives behind the same on-demand affordance, **NOT on the first frame**. *compute-error* is a non-verdict system state whose next-action is **retry**, never "sharpen". Motion: the band **draws once** (on its first reveal) then **morphs** on every recompute (interruptible transition/spring, never a draw-from-zero replay); the headline number renders **static** (no odometer/count-up); verdict→verdict crossfades are margin-gated (the gating is *exercised* in Phase 3 — Phase-2 intake numbers move freely). **No-worker fallback:** a main-thread run blocks the event loop, so a per-commit run would contend with the step-transition slide — on the fallback flag each commit's recompute is **deferred until after the step transition paints** (yield post-paint); if profiling still shows jank, the fallback **downgrades to one compute at the minimum-viable-input point + one at completion** (instrument first, per the eye-in-loop motion lesson). All of it respects `prefers-reduced-motion`.

7. **The Phase-1 cascade (tracked — this deepening re-opens deepened Phase 1).** Two Phase-2 decisions touch the deepened + doc-reviewed Phase 1 and are tracked here so the cross-phase change is never silent: **(a)** the **earned-income bridge regime** (per-person retirement timing, one spouse earning while the other is retired — Briggsy's call, 2026-06-03) is an *income-phase overlay* on `simulate.ts` (a pre-withdrawal adjustment to the single per-year withdrawal term — `netWithdrawal = max(0, spending − earnedIncome)` into the same update function), orthogonal to the joint→survivor longevity regimes and CRN-safe under contract #1; each earner's income window truncates at `min(retirementYear, sampledDeathYear)` **per path** (never credit a dead earner). Phase 1 Unit 1 gains the bridge + a validation note that it **reduces exactly to the Trinity/Bengen decumulation when no spouse has earned income in any simulated year** (the pure-retiree case — **not** merely "equal retirement years", which only removes the asymmetric window). **(b)** Phase-1 contract #1's hysteresis/margin emission widens from "the headline" to "**every rounded continuous display output**" — the X-of-N **and** the dollar-adjustment figure (margin = distance to the next display-rounding step, not a band edge). Both are tracked Phase-1 amendments (the same posture Phase 1 used for its own optional→required elevation).

- [ ] **Unit 3: Guided progressive on-ramp + in-memory orchestrator + R19 sanity**

**Goal:** A calm, one-question-at-a-time intake for a married couple whose first confidence statement **resolves live** (indeterminate → verdict) with **zero persistence**, validating inputs inline, on a surface that **shines on a phone**.

**Requirements:** R5 (guided intake), R6 (escape-hatch entry point), R8 (caveated answer fast, refinement rewarding), R19 (sanity checks); gates R15/R16 via the in-memory→persistence seam.

**Dependencies:** Units 0, 1, 2.

**Files:**
- Create: `src/intake/coldStart.tsx`, `src/intake/flow.tsx`, `src/intake/questions.ts`, `src/intake/sanity.ts`, `src/intake/intakeMap.ts` (the intake→engine-param contract), `src/store/memoryModel.ts`, `src/ui/copy.ts` (the typed copy catalog — **created here** so intake copy routes through it from the start; **extended by Unit 5** — cross-cutting #4)
- Modify: `eslint.config.js` (add the `no-restricted` **no-inline-user-facing-copy** rule scoped to `src/ui` + `src/intake`, banning JSXText *and* user-facing attribute literals `aria-label`/`placeholder`/`alt`/`title` — cross-cutting #4; lives in Phase 2, not a Phase-1 Unit-0 re-open)
- Test: `src/intake/__tests__/sanity.test.ts`, `flow.test.tsx`, `coldStart.test.tsx`, `src/store/__tests__/memoryModel.test.ts`

**Approach:**
- **Progressive, engine-gated, commit-triggered architecture (cross-cutting #6).** The confidence surface co-exists with intake; as soon as the minimum-viable input set exists it renders **indeterminate** and resolves toward a verdict as questions are answered. The magic moment is "watch the answer resolve as you go" — still **one** answer, no dashboard, range/math on demand (R4). Whether inputs are "enough to compute" vs indeterminate is the **engine's** decision surfaced as the indeterminate state (Phase-1 contract #4; `confidence.ts` is the single threshold source) — intake **never** hard-codes "render after question N." Recompute fires on each question-**commit**, not per keystroke.
- **Cold-start frame (resolves the requirements deferral; (origin: "Deferred to Planning — cold-start/zero-data first screen")).** The brand-new user's first frame is **one calm entry screen** — *not* a marketing/landing page — that presents R1's question ("Can I retire, and when?") as the product's face, states the married-couple precondition as orientation, and offers one action into question 1. This frame is the single home of the precondition line (it replaces the "one-line framing at the top"). The R13 disclaimer is **not** re-owned here — it already lives app-wide via Unit 0's shell.
- **`memoryModel.ts` is the in-memory orchestrator (cross-cutting #1).** It holds **one** plaintext shape — the same to-be-persisted MODEL that `shared/model.ts` defines (financial inputs + per-person params + the injected seed + sim assumptions incl. survivor-spending ratio), populated incrementally during intake. **There is no parallel intake shape and no field-mapping layer**; Save is a clean serialize of that exact object (`schemaVersion` is prepended only at Unit 2's encrypt step). Adding an intake field is one edit to the shared shape, so a field can never be captured on screen yet silently dropped at Save. It also holds the eager worker handle, mints/stores the seed, exposes the fallback flag, and carries `lastDisplayed*` for the Phase-3 hysteresis seam.
- **Minimum-user-fact set vs methodology defaults; explicit `unknown` sentinels (R19, R5).** Two input classes: **(a) required user-facts** — two ages, two **sexes** (see below), two incomes/SS streams + claim ages, household savings, household spending, per-person retirement year — gate the first compute; **(b) methodology assumptions** (real return + volatility, inflation, longevity tables, survivor-SS step-down, survivor-spending ~75%) are **pre-defaulted and safe to default** *because* R7/Unit 7 make them visible + editable. The contract: `memoryModel` passes an explicit **`unknown` sentinel** for any required user-fact not yet collected — **never a silent 0 or default** — and `simulate` maps any `unknown` required fact to the indeterminate state, never a confident headline. (This is what makes Phase-1's "minimal/missing-assumption inputs → indeterminate" test authorable; it extends contract #4 from *impossible* values to *absent* values.) **No "skip with a reasonable default" UI** — methodology defaults are auto-applied and surfaced by Unit 7.
- **The intake→engine param contract (`intakeMap.ts`).** Phase 2's transitive contract between intake and Phase 1's `model.ts`, in three buckets: **ASKED** (the questions and which model param each fills); **DEFAULTED-AND-SURFACED** (R7-editable, handed to Phase-3 Unit 7: real return + volatility σ, inflation, survivor-spending ratio, longevity tables — exposed as editable assumptions, **not** an allocation picker, keeping intake minimal per R5); and the **must-decides**:
  - **Per-spouse sex — collected (Briggsy's call, 2026-06-03).** Two sex fields; the joint-and-survivor longevity math `P = pₓ + pᵧ − pₓ·pᵧ` selects the **sex-specific** SSA cohort curve per spouse (findings §Strand 4; Phase 1 Unit 1) and handles same-sex couples honestly. Leaving it implicit would be both a correctness bug on the product's core survivor case and a hidden R7-violating assumption.
  - **Per-person retirement year + earned-income bridge (Briggsy's call, 2026-06-03; Phase-1 cascade #7a).** Intake collects each spouse's retirement year and a flat **real earned-income** stream per person until that year. The engine models the **bridge**: in years where one spouse still earns, earned income **nets against spending** (reduced/zero net withdrawal). Default both retirement years equal → no bridge → the Trinity/Bengen-validated decumulation. MVP-minimal: flat real income, net-against-spending only — **no** salary-growth curve, **no** surplus-contribution modeling (post-MVP; surfaced as an editable assumption).
  - **Account-type buckets (pre-tax / Roth / taxable) — deliberately deferred to Phase 3 (F-handoff).** The first answer collects **one** total-savings figure to protect the ~3-min / ~8-input on-ramp (R5). The pre-tax/Roth/taxable split is gathered when the user **opens the Roth lever** (Phase-3 Unit 8 — a lever-open mini-intake + a `model.ts` field behind a `schemaVersion` bump), consistent with depth-on-demand and R10/R11. A deliberate deferral, not an omission.
- **Currency entry that shines on a phone (mobile must SHINE, not survive).** The model stores each input as a **raw number**; the field **displays** a formatted string. Open-ended dollar fields use a text field summoning the numeric keypad — **not** a native number-spinner (rejects grouped digits, shows steppers) and **not** a slider (can't hit an exact figure; violates R6's "set any assumption precisely"). Sliders are reserved for **bounded** ranges (ages, percentages). **Reformat on blur**, not per keystroke (avoids caret-jump). Full-width, finger-sized fields.
- **Monthly-vs-annual: prevent at entry, test the dangerous direction (R19).** Every per-period money field carries an explicit **`$/month` vs `$/year`** segmented control (active segment by shape/weight, not hue), so the period is unambiguous by construction; the model stores one canonical period (defaults: spending = /month, income + SS = /year, editable). The implausible-magnitude check is the **second** line of defense; for a value coherent as **both** monthly and annual, intake **forces** an explicit per-period confirmation rather than silently computing on the default — so the engine can never run on 1/12 (or 12×) the real figure.
- **R19 sanity, decomposed per rule + directional re-validation (R19; contract #4 intake half).** Each rule is a discrete testable rule that blocks only **true impossibilities** (retirement age < current age; SS claim outside 62–70; survivor-spending ratio > 100%) and lets coherent-but-dire inputs ($0 portfolio + spending) flow to an honest "0 of 10". **Directional half:** cross-gated inputs re-fire their check when an **upstream** answer they depend on is edited via Back — an upstream edit **keeps** downstream answers (never silently wipes) but marks dependents for re-validation; if it makes a downstream answer impossible, the same calm inline message fires at the point of edit, so no stale-but-impossible combination reaches the engine. The engine's numeric-domain half (indeterminate on horizon ≤ 0) is only a backstop.
- **Validation timing (R5 "advisor-style", R11 "calm never traded for engagement").** Rules evaluate on **field blur and attempt-to-advance, never per keystroke**; a rule whose inputs aren't all present yet does not fire; an in-progress value invalid-as-prefix but valid-when-complete ("6" → "62") is never flagged mid-entry; an existing error clears the instant the field is re-edited.
- **State ownership + back-nav without loss.** Every step reads/writes through the single `memoryModel` (no per-step local copy to lose), so Back re-renders the prior step pre-filled. Mechanism left to implementation (do **not** mandate `useReducer`).
- **Accessibility contract (the stranger-trust bar; N=1 reader is color blind; mobile must shine).** On each step advance, move focus to the new step **heading** (`tabindex=-1`), **not** the input (auto-focus pops the keyboard before the user reads the question) — the heading-as-focus-target *is* the announcement (no double-announce). One visually-hidden polite live region carries only transient status (e.g., "question N of M"), with `burned/045` clear-after-announce discipline so stale text never lingers in the a11y tree (keeps Playwright/N=1 snapshot verification honest). R19 errors associate to their field (`role="alert"` + `aria-invalid` + `aria-describedby`), clear on valid, and carry the non-color signal (word + shape + text). The focus-move/`announce()` helper is a shared a11y primitive Unit 5 reuses to move focus to the verdict.
- **Step-transition motion (`emil-design-eng`; insight 006).** Direction encodes meaning (forward enters from the right, Back reverses); a brief, strong ease-out (duration/easing deferred to implementation, eye-in-loop); **interruptible** (transition/spring, never `@keyframes` that restart from zero) so rapid Next/Back never strands a mid-flight animation. **Focus-safe rule (load-bearing):** any step that receives programmatic focus on mount is faded with **opacity only** — never `autoAlpha`/`visibility` toggle — and the outgoing step is **unmounted**, not visibility-hidden, or `.focus()` is a silent no-op (`ai-journey-stats/006`, generalized from a modal to a wizard step). `prefers-reduced-motion` → drop the slide, keep a fast opacity fade.
- **Progress orientation + paired two-person screens (consumability wedge).** **No** "Step N of 10" chore-counter on the primary surface (reads as a form; the flow is variable-length, so a fixed denominator would be inaccurate); instead a quiet, unlabeled progress thread encoded by **fill proportion**, never hue, plus an SR-announced position. Two-person questions render as **one paired screen** ("you / your spouse"), never two near-identical sequential screens — wrap each in a `fieldset`/`legend` (or `role="group"` + `aria-labelledby`) so the pairing is programmatic. **On-ramp budget (reconciled with the deepened input set):** the required-fact count grew to **~12–14 facts** (two ages, two sexes, two incomes, two SS streams + claim ages, savings, spending, two per-person retirement years, two earned-income streams — the collect-sex / per-person-retirement / bridge-income decisions); pairing the per-person facts two-up keeps it to **~7–8 screens** and the bar that actually matters is **<3 min, perceived-low-effort**, not a raw count. *(The origin Success-Criteria "~8 inputs" number predates these decisions and wants a **tracked requirements-doc amendment** to a screen-count/time metric — same posture as the "all three outcomes → six states" amendment.)*

- **Copy catalog + no-inline lint (cross-cutting #4).** All intake question/error/affordance copy routes through `src/ui/copy.ts` from the first commit; the `no-restricted` ESLint rule (banning inline JSXText + user-facing attribute literals in `src/ui`/`src/intake`) is added here so the "by construction" guarantee holds for intake copy at Unit-3 build time, not as a Unit-5 retrofit. Unit 5 extends the same catalog + adds `copyGuard`.

**Patterns to follow:** `useCallback` all handlers passed to step/slider children (`ai-journey-stats/007`); `ai-journey-stats/006-gsap-autoalpha-breaks-focus.md` (focus-safe enter); `burned/045-aria-live-region-staleness…` (clear-after-announce); `emil-design-eng` (direction/timing/reduced-motion).

**Test scenarios:**
- Happy path (progressive): minimum-viable inputs → an **indeterminate** statement renders → each subsequent answered question re-runs the engine and the statement **sharpens** → nothing persisted to IndexedDB throughout.
- Error path (R19 forward): retirement age before current age → caught inline, calm, no broken answer.
- Error path (R19 directional / back-nav): a valid retirement age, then Back → raise current age above it → the retirement-age rule **re-fires inline**, the downstream answer is **not** wiped, no impossible combo reaches the engine.
- Edge case (back-nav no loss): complete several steps → Back → every prior answer intact and pre-filled; advancing forward preserves edits.
- Error path (partial-intake false-confidence, **planted**): plant a default-to-0 spend (or defaulted income) in `memoryModel` → the surface renders **indeterminate**, *not* a defaulted rosy over-funded number (fail-loud, `burned/070`). Keep the existing **$0 *entered* spend → honest "0 of 10"** as the coherent-dire mirror, noted as distinct.
- Edge case (period false-negative): a spending value coherent as **both** monthly and annual → intake **forces** the per-period confirmation; the engine never runs on the unconfirmed default. (Keep the implausible-as-annual case as the over-count backstop.)
- Edge case (R19 per-rule pairs — fire **and** boundary-pass): retire = current−1 fires / retire = current passes; SS claim 61 & 71 fire / 62 & 70 pass; survivor ratio > 100% fires / exactly 100% passes; implausible-magnitude fires / a plausible annual figure passes.
- Edge case (bridge): per-person retirement years **differ** → the bridge is modeled (the still-earning spouse's income nets against spending); years **equal** → no bridge (identical to joint-from-year-0).
- Edge case (currency): typing a large figure stores the **raw number** (not the formatted string) and never reorders the caret; the display is the formatted string.
- Integration (a11y): advancing step N→N+1 moves focus to the N+1 **heading** (`tabindex=-1`), does **not** auto-focus the input (keyboard stays down), and the a11y tree holds exactly **one** current question — no stale prior-step text (`burned/045`); an R19 error exposes `role=alert` + `aria-invalid` + `aria-describedby` and clears on correction. Focus lands on the new heading **even while the enter animation is in flight** (insight 006), asserted via a real activation, and under `prefers-reduced-motion` the slide is suppressed but focus still moves.
- Integration (privacy regression guard, references Unit 2 contract #3): the **no-IndexedDB-write** assertion holds across the **full branch set** — happy-path completion, an R19-error branch, back-navigation, and a mid-intake abandon each leave the encrypted store untouched until an explicit Save, asserted **against the seam (a stub Save boundary — the only thing available at Unit-3 build time; the real end-to-end Save is proven in Unit 6)**.
